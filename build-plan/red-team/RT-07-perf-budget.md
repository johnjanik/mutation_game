# RT-07: perf-budget

Applies from phase 0. Runs in: a worktree on branch `redteam/P{k}-RT-07`.

Before this file you have read `build-plan/RED-TEAM-COMMON.md` and `build-plan/CONTRACTS.md`. Everything there applies.

## 1. Mission

This lens attacks the performance budget of `SPEC.md` 7.6 and the measurements that are supposed to enforce it: the four per-route limits on JavaScript fetched before the first interaction, the ban on typesetting, layout and polyfill code in the client, the hydration directives, the reserved box sizes and the lab timings, the 25 ms engine benchmark, the 100 ms $E_8$ drawing test, and the drawing caps of T2, T8, T10 and T12. A build can pass every gate here while being wrong, because each check is a script the builders wrote themselves: `npm run size` can miss a script it never saw (a late dynamic import, a `modulepreload`, a path under `BASE_PATH` it maps to nothing), a Vitest `bench()` never fails on a threshold, a drawing test can time the recording of canvas commands and not the drawing, and a lab script can stop observing before the islands hydrate. If this lens misses, the reader on a mid-range phone downloads KaTeX or the whole engine on every lesson, waits on long tasks, and watches the page jump when a tool hydrates, while every gate report says green.

## 4. Attack list

Each attack names the phases in which it applies. The attacks are ordered from the most likely to find a blocker to the least: first the gate checks that may be blind or unable to fail (1 to 8), then the size and content checks of the client (9 to 17), then layout and timing (18 to 26), then the drawing caps and the remaining routes (27 to 34), then the catalogue of typeset names (35). Severity guidance follows `RED-TEAM-COMMON.md` 4: a gate check that passes while the behaviour it checks is absent (a size script blind to a script, a benchmark or drawing test that cannot fail, a lab script that does not measure what 7.6 names) is a **blocker**; a route over its limit, a typesetting or layout library in the client, a CLS or TBT or LCP over threshold at a gate that requires lab timings, a drawing cap not honoured, an engine call measured as a long task, is **major**; a misclassification that does not change a verdict, a reserved box that shifts by less than the CLS threshold, a tool chunk that carries unused engine code while within its limit, is **minor**.

1. **Independent per-route measurement against `npm run size` (phases 0 to 7).** What: every `.html` file under `site/dist` of the gate commit's preview build. How: Methods 5.2, `redteam/rt07-size.mjs`: your own static server (not `astro preview`), one Chromium context per route at 360 by 800, every request recorded with `page.on('request')` whatever its `resourceType`, plus `performance.getEntriesByType('resource')`, plus every `<link rel="modulepreload">` in the HTML, after `load` wait until 3 s pass with no new request, or 10 s in all, with no input (Methods 5.2 step 3), gzip level 9 of each distinct JavaScript file from `site/dist`. Then run `npm --prefix <wt> run size -- --json <scratch>/size.json` and compare route by route. Standard: SPEC 7.6 table and the bullet "Measured by `npm run size`"; G0 "the first two limits of section 7.6 hold"; G1 onwards "the size limits of section 7.6". Failure: a route whose independent sum exceeds its limit (15000, 60000, 90000 or 120000 bytes under the 1000-byte kB that `DECISIONS.md` records) while `npm run size` passes it (blocker: the gate check is blind), or any route over its limit in both (major). Report both sums, the list of scripts each saw, and the difference. A script that your measurement saw only because its request started after the network had gone idle is the tension of attack 2 case (a): report it as a note, not as a blindness of `npm run size`.
2. **`npm run size` misses scripts by design (phases 0 to 7).** What: `scripts/size.mjs`. How: read its browser part and test each blind spot with a fixture route committed under `redteam/fixtures/` (served by your own server or by `npm run size -- --url`): (a) a script loaded by `import()` 3 s after `load` from a `setTimeout` in an island's `onMount`; (b) a `<link rel="modulepreload">` chunk that no module then imports; (c) a script whose request's `resourceType()` is not `script`; (d) a `client:visible` island already in view at 360 by 800; (e) an `<script type="module" src>` inside a `client:idle` island's markup. Standard: SPEC 7.6 "all JavaScript the route fetches before the reader's first interaction"; "collects the URL of every script the browser fetched". Failure: any fixture script of cases (b) to (e) that the browser fetches without input, before the network goes idle, and that `size.mjs` does not count. Case (a) is not a failure of `size.mjs` (lens reading): 7.6 states the budget as "all JavaScript the route fetches before the reader's first interaction" but defines the measurement as one that "waits until the network is idle without touching the page", and the plan's settle (`P0-A6` 5.1, plan: one second after network idle) follows that definition. A script whose request starts after the network has gone idle is therefore outside the method 7.6 states. Run case (a) anyway, and report what it shows as a note for the owner: the tension between the principle and the method, the bytes such a script would add, and whether any real route of the build loads code that way (a real island doing so, and pushing its route over its limit under the principle, is the case the owner should decide). A `size.mjs` that stops observing before network idle is attack 4's failure, not this one.
3. **`npm run size` cannot fail, or the gate does not run it (phases 0 to 7).** How: first, the committed proof. `P0-A6` 5.1 and its traps say the `--limit-override` flag exists only for the unit test and "must never be used in a script body, in CI, in a gate run or by hand" (plan). So run the unit test that uses it, `npx --prefix <wt> vitest run <wt>/site/tests/unit/size-classify.test.ts`, and confirm that `a route over its limit fails and one at the limit passes` and `the limit override applies to every route` run (not skipped) and pass, and that `no script body or ci.yml line passes --limit-override` passes. Then break the comparison: in the throwaway clone of Methods 5.6 (never committed, never on `main`), invert or remove the limit check in `scripts/size.mjs` and confirm the first of those tests fails. Do not pass `--limit-override` on the command line yourself; if the committed test cannot show the failure path, the probe that would need the flag goes into the clone of Methods 5.6 as a fixture route with an incompressible script over 60 kB, served and measured there with plain `npm --prefix <scratch>/mut run size -- --dist <fixture dir>`, which must exit 1. Read `ci.yml` for the step `npm run size` after the build, and the gate report for the pasted table with every route of `site/dist`. Count the HTML files under `site/dist` (`find <wt>/site/dist -name '*.html' | wc -l`) and the rows of the table. Standard: SPEC 7.6 "fails when a sum exceeds its limit. It prints the table of sums"; 7.7 "sizes: every merge"; 9.1 G0 and G1 cells. Failure: the unit test `a route over its limit fails and one at the limit passes` missing, skipped, or still passing with the limit check broken in the clone; exit status 0 on the over-limit fixture; a `--limit-override` in a script body or in `ci.yml`; a row printed `ok` with a sum above its limit; a route of `site/dist` absent from the table; no size step in `ci.yml`; a gate report without the table (each a blocker under "a gate command that fails or was not run as written").
4. **`size.mjs` follows the method that 7.6 states (phases 0 to 7).** What: `scripts/size.mjs`, everything it imports, and the root `package.json`. How: read the script line by line, with `grep -n -E '<name>' <wt>/scripts/size.mjs` for each name below and `grep -n -E '^import|require\(' <wt>/scripts/size.mjs` for the imports, and check each property that 7.6 names for the measurement. (a) Compression: every call to `zlib` is `gzipSync` (or `gzip`) with `level: 9` (or `zlib.constants.Z_BEST_COMPRESSION`); a call with no options uses zlib's default level, which is not 9. Prove a suspected wrong level by computing the sums of the same script set at level 9 and at the level the script uses with `<scratch>/gz.mjs` (Methods 5.1). (b) Viewport: every browser context or page is created with `{ width: 360, height: 800 }`, and nothing resizes it later (`setViewportSize`). (c) No touching: no `click`, `dblclick`, `tap`, `hover`, `focus`, `press`, `type`, `fill`, `check`, `selectOption`, `dragTo`, `mouse.*`, `keyboard.*`, `touchscreen.*`, `scrollIntoViewIfNeeded`, `dispatchEvent`, `emulateMedia`, and no `page.evaluate` or `addInitScript` that scrolls, focuses or dispatches an event. (d) The wait: navigation waits for network idle (`waitUntil: 'networkidle'` or an equivalent request count) and not only for `load` or `domcontentloaded`. (e) The files: every collected URL is mapped to a file under `site/dist` (or `OUT_DIR`) and compressed from disk, not from a response body or a `Content-Length` header. (f) Imports: only `playwright` or `@playwright/test` and Node built-ins (`node:zlib`, `node:fs`, `node:path`, `node:url`, `node:http` and the like) or files of the repository that themselves import nothing else; no network call to another service, no API key, no environment variable that points at a service; the root and site `package.json` gained no dependency for the script. Standard: SPEC 7.6 "**Measured by `npm run size`**: a Playwright script opens each route of the built site at 360 by 800 pixels, waits until the network is idle without touching the page, collects the URL of every script the browser fetched, compresses those files from `site/dist` with Node's `zlib` (gzip, level 9), and fails when a sum exceeds its limit. It prints the table of sums. It needs no service and no dependency beyond Playwright." Failure: a compression level other than 9, another viewport, any call of list (c), a wait that ends before network idle, sizes not taken from `site/dist`, or an import or service outside list (f). Severity: blocker when correcting the property changes the verdict of a route (the gate check then passes a route that 7.6's method fails); major otherwise, because the method is stated behaviour; an added dependency is major in any case ("a dependency added without a record", and 7.6 "no dependency beyond Playwright"). This attack, not attack 1, is where a wrong level is caught: a level-6 sum differs from a level-9 sum only by the few bytes that Methods 5.2 does not count as a difference.
5. **Release build against preview build against `BASE_PATH` build (phases 0 to 7; release builds at G3 and G6).** How: build three times into separate directories under your scratch directory (Methods 5.1: preview; `RELEASE=1`; `BASE_PATH=/sub/path/`), run attack 1's measurement and `npm run size` on each. Standard: SPEC 7.6 applies to "the built site"; 9.1 G3 "sizes and lab timings of section 7.6 on the core path M0 to M5; a release build succeeds" and G6 "sizes and lab timings of section 7.6 on every page; a release build succeeds" (9.1 does not say on which build the sizes are taken; taking them on the release build is the plan's: `GATE` 5.5 step 11, "then `npm run size` again and `npm run lab` against that release build", and 5.7); 7.2 item 10 and CONTRACTS 1 for `BASE_PATH`. Failure: a route over its limit in the release build that passes in the preview build; `npm run size` on the `BASE_PATH` build printing sums of 0 or far below the root build's (it failed to map URLs under the base to files and did not fail the route), which is a blocker because the base-path build is what Pages serves.
6. **The benchmark exists, measures the specified case, and can fail (phases 3 to 7).** What: `packages/engine/test/bench/orbit.bench.ts` and the command that runs it. How: read the file. Check: the board is twelve nodes joined `k` to `k + 1`, 12 to 1, and 1 to 7 (positions 0 and 6), one road each way, arithmetic `Big` asserted; seeds the twelve unit vectors; `orbitGraph(board, seeds, 'mutation', 2000, 40)`; an assertion that 2000 items came back with `truncated` true; seven timed runs, the median, and an `expect` that fails above 25. Then the decisive check (Methods 5.6): in a throwaway clone, insert a 30 ms busy wait at the top of `orbitGraph`, run the benchmark command exactly as the gate report or `P3-A2`'s fragment names it, and confirm a non-zero exit. Also check that the command is in `ci.yml` or the gate, and that `npm test` does not silently exclude the file while the gate claims it ran. Standard: SPEC 7.6 "A Vitest benchmark repeats that case ... and fails above 25 ms (median of seven runs)"; CONTRACTS 3. Failure: a `bench()` call with no failing threshold; a case on the 12-cycle without the chord, on `SafeInt`, with a smaller cap, with one seed, or on a board where fewer than 2000 positions exist (each proves less than 7.6 says); exit 0 under the injected delay; no command on `main` that runs the file. Each is a blocker ("a test suite that passes while the behaviour is absent").
7. **The drawing-time test measures the drawing (phases 4 to 7).** What: `site/tests/e2e/draw-time.spec.ts`, `DrawTimeProbe.svelte`, and T10's `data-out="drawMs"`. How: read what the timed interval contains. 7.6 says "The $E_8$ root set, its Coxeter projection and 6720 edges draw in under 100 ms on the phone" and that the test "records the drawing time", without defining the interval. The plan defines it (`P4-A2` 5.10, plan): five repetitions, each timed "with `performance.now()` from before the first $y$ to after `drawScene` returns (the fetch, the parse, `euclideanBasis` and `toPopulation` are outside the timed region; plan, record it)", the median of the five being "the plan's reading of 'the drawing time'". Check the test against that plan interval: it must contain $y=Ep$ for every vertex, `project` with the Coxeter view, `buildScene` and `drawScene` on a real canvas, and `DECISIONS.md` must record the interval. Lens reading (not a SPEC or plan requirement): an interval that ends when `drawScene` returns may end before the browser has rasterized the frame; measure also to a `requestAnimationFrame` after the last stroke (attack 26) and report the difference as a note, not as a failure of the test. Check that the test asserts 6720 segments and 240 points drawn, takes the median of several runs, fails above 100, runs in `npm run e2e` without a `skip` on CI or on this machine. Then Methods 5.6: in a throwaway clone add a 120 ms busy wait inside the draw and confirm the test fails. Standard: SPEC 7.6 "a browser test records the drawing time on the CI runner and fails above 100 ms there"; 9.1 G4. Failure: an interval narrower than the plan's (one that excludes $y=Ep$, the projection or `drawScene`), or one that differs from the plan's with no `DECISIONS.md` record; a probe that draws a different picture from the T10 showpiece (other rings, fewer edges, a smaller canvas); exit 0 under the injected delay (blocker).
8. **`npm run lab` measures less than 7.6 names (phases 3 to 7).** What: `scripts/lab.mjs` and `decisions/P3-A7.md`. Standard: SPEC 7.3 "Names with a fixed spelling (boards, real forms, Cartan's labels) are typeset once at build time: `scripts/names.mjs` writes the KaTeX markup of every name of the catalogue to `site/src/generated/names.json`, and the tools that show names (T13, T14, the board pickers) look them up there"; SPEC 7.6 table, "the tool's own code with the engine functions only it uses (30 kB)" for `/tools/<id>`, and the 90 kB and 120 kB limits. 7.3 lets the tools look names up in the file and does not say whether the lookup happens at build time or in the client, so shipping the file is not by itself a finding. Failure: a route over its limit where the catalogue's bytes are what take it over (major, with those bytes and the route's sum without them); within the limit, the catalogue in a tool chunk is minor when it carries names the tool never shows (the bytes it adds, under this lens's "a tool chunk that carries unused engine code while within its limit" by analogy), and a note otherwise; KaTeX's parser arriving with it is attack 9's finding, not this one's.

## 5. Methods

In the commands below `<wt>` stands for the absolute path of your worktree and `<scratch>` for your scratch directory; write them out in full in every command. Never `cd`; never put a multi-line script on the command line: write it to a file under `<wt>/redteam/` or `<scratch>` and run the file. One Playwright run at a time. Kill every server you start.

### 5.1 Builds and gzip sizes

- Preview build: `npm --prefix <wt> run build`. Release build into its own directory: `OUT_DIR=<scratch>/dist-release RELEASE=1 npm --prefix <wt> run build`. - One file's size as 7.6 defines it: write `<scratch>/gz.mjs` that prints `zlib.gzipSync(fs.readFileSync(p), { level: 9 }).length` for each path argument, and run `node <scratch>/gz.mjs <file> ...`. For a quick look, `gzip -9 -n -c <file> | wc -c` differs from zlib by a few header bytes only; use the script for any number you report.
- kB: `DECISIONS.md` records the unit (`P0-A6` plan: 1000 bytes). Report bytes, and the limit in bytes under the recorded unit.

### 5.2 Independent size measurement (`redteam/rt07-size.mjs`)

Shape of the script (Node 22, imports `@playwright/test`'s `chromium`, `node:http`, `node:zlib`, `node:fs`, `node:path`):


### 5.3 Fingerprints in the shipped JavaScript

Minifiers rename identifiers but keep string literals, so search for literals. Before using a fingerprint, confirm it occurs in the source you attribute it to (for example `grep -rn "differs-from-minus-wX" <wt>/packages/engine/src`, or `grep -rn "KaTeX parse error" <wt>/node_modules/katex/dist/katex.mjs`) and does not occur in the HTML-producing code (names in `names.json` contain `class="katex"` markup, which is data, not KaTeX).

- Files that contain a fingerprint: `grep -l -F 'KaTeX parse error' <wt>/site/dist/_astro/*.js`.
- Which routes fetch them: look up the file names in `<scratch>/rt07-size.json`.
- Suggested sets: KaTeX (`KaTeX parse error`); golden data (`layer_growth_examples`, `bigint_test`, `twisted_affine`); engine modules (reason codes and twisted names from CONTRACTS 2.2 and the phase's source; error messages from `errors.ts`); dagre (`network-simplex`, `longest-path`); three.js (`THREE.`); polyfills (`__core-js_shared__`, `regeneratorRuntime`); `names.json` (`katex-mathml` inside a `.js` chunk, then measure the bytes it adds).

- Timings that miss a threshold by less than run-to-run noise: SPEC 5.5 says its figures "vary by a few tens of percent from run to run". A timing finding needs a median of seven (Node) or five (browser) runs over the threshold on an otherwise idle machine; a lone slow run is not one.
- Tools, routes, presets and engine functions of a later phase (sections 3, 4, 9.1). A missing benchmark before phase 3 or a missing drawing test before phase 4 is not a finding.
- Whether a lesson page is readable with JavaScript disabled (SPEC 7.6, first sentence: "A lesson page is readable with JavaScript disabled"): RT-06's lens, for every lesson page and not only for T8 and T10. This lens measures what JavaScript the page fetches when it is enabled.
- Correctness of caps inside the engine (`truncated`, `completeLayers`, the 20000-step root test): RT-03. The SVG snapshots and the no-JavaScript rendering of T8 and T10: RT-06. Whether `whereToRun` routes a call correctly: RT-06 and RT-10. This lens times those calls and counts what is drawn.
