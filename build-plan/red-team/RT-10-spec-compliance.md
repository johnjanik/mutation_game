# RT-10: spec-compliance

Applies from phase 0. Runs in: a worktree on branch `redteam/P{k}-RT-10`.

Before this file you have read `build-plan/RED-TEAM-COMMON.md` and `build-plan/CONTRACTS.md`. Everything there applies.

## 1. Mission

This lens walks the phase's checklist item by item and proves, for each item, that it is present, that it has the contracted shape, and that a test would notice its removal. The gate can be green while the phase is incomplete: a gate runs the tests the builders wrote, so a missing engine function with no golden key, an acceptance criterion that was never turned into a test, a test that asserts `toContain('stopped after')` instead of the exact message, a default that no link ever exercises, a preset that exists only in prose, or a `DECISIONS.md` entry that was never folded in all pass silently. If this lens misses, the owner receives a phase report that says "acceptance of T2 as automated tests" while the stop message, the board picker or the undo of one mode is untested and wrong, and the next phase builds on a contract that was quietly changed.

## 4. Attack list

Each attack names its phases. Severity follows `RED-TEAM-COMMON.md` 4: a gate row that passes without proving its item, or an acceptance criterion with no test or with a test that survives removal of the behaviour, is a **blocker**; a stated behaviour, string, default, preset, hook, field, `DECISIONS.md` entry or contracted signature missing or different is **major**; a name, a comment, a missing `data-out` listing is **minor**.

1. **Every acceptance criterion of the phase is an automated test that fails without its behaviour (phases 1 to 7; at phase 0 the G0 rows).** What: each bullet of "Acceptance" of every tool of the phase in SPEC 4 (split compound bullets: T2's has five checks, T4's has six), and each G0 row. How: build the table criterion → test (Methods 5.4); for every row, apply one hand mutation that removes the behaviour (stop message changed by one word, undo that pops two moves in one mode, `data-value` printed from the label, `fired_values` compared after sorting, the "game over" counter off by one), rebuild if a browser test, run only that test file, record pass or fail, revert with `git -C <wt> checkout -- <file>`. Standard: SPEC 9.2 "its acceptance criteria are automated and pass"; 7.7 row Components; 9.1 "acceptance of T1, T2, T9" (and the later gate cells); COMMON 4.3 "A test must fail when the behaviour it guards is removed". Failure: a criterion with no test (blocker), a test marked `not-automated` where SPEC does not say the check is manual (blocker), or a test still green after the mutation (blocker). Report the criterion text, the test name, the mutation and the run line.
2. **The gate ran the commands of 7.7 as written, and each row proves its item (phases 0 to 7).** What: `reports/gate-G{k}.md`, root `package.json` scripts, `ci.yml`. How: for each roster `gateItems` row, find the command and quoted output; rerun it in your worktree from a clean `npm ci` (Methods 5.6). Check the bodies: `npm test` runs both the engine suite and `site/tests/unit` (a root `vitest run` that misses one project passes vacuously); `npm run e2e` runs Playwright against `astro preview` on a built site (never `astro dev`) and includes the no-JavaScript run and the axe scans; `npm run build` runs `scripts/names.mjs` first (7.3 "runs at the start of every build"; CONTRACTS 1); `RELEASE=1 npm run build` actually sets the release mode the components read; `npm run verify` writes to a temporary file and byte-compares (5.7); `npm run report` writes "the two content reports of the table above" to `reports/` (7.7): run it after a release build in your worktree and check that both the open-items report and the `numbers-in-prose.mjs` list appear under `<wt>/reports/` with this run's timestamps (plan names `reports/open-items-report.json` and `.md`, written by the release build, and `reports/numbers-in-prose.md`; `GATE` section 4 says `npm run report` checks the first and writes the second), and (plan, `GATE` 5.5 step 10 and `P0-A6` 5.5) that it "exits 1 unless that file has mode `release` and `reports/open-items-report.md` is beside it": in your worktree's `reports/` (never the primary checkout's), run it four times and record each exit: with `open-items-report.json` absent (exit 1), with the JSON present and `mode` `preview` (exit 1), with the JSON of mode `release` and the `.md` file moved away (exit 1), and with both files of the release build in place (exit 0); a report written anywhere but `reports/`, or only one of the two, fails 7.7, and an exit 0 in any of the first three cases fails the plan rule. Failure: a script name of 7.7 or CONTRACTS 1 missing; a body that skips a part 7.7 names; a gate row whose quoted output does not show the item (for example a Playwright summary in which the spec the row depends on was skipped); a command whose exit status differs when you rerun it. How: Methods 5.2: the inventory test from the phase lists of CONTRACTS 2.4 and the column "Phase" of SPEC 5.3 and 5.4 (including the plan additions `cartanNumbers`, `mutationMatrix`, `firingMatrix`, the rational helpers `rat`, `ratAdd`, `ratSub`, `ratMul`, `ratDiv`, `ratEq`, `ratSign`, `ratToString`, `solve`, `inverse`, `CAPS`, `EngineError`), then the type-level file compiled with `tsc`. ## 5. Methods

In the commands below `<wt>` stands for the absolute path of your worktree and `<scratch>` for your scratch directory; write them out in full. Never `cd`; never put a multi-line script on the command line: write it to a file under `<wt>/redteam/` or `<scratch>` and run the file. One Playwright run at a time. Kill every server you start.
