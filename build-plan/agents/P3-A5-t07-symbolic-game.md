### 5.1 What the tool is (SPEC 4 T7)

Every clause of SPEC 4 T7, restated:

- "Two boards side by side." Side by side where the width allows; stacked (left board first) at narrow widths, because every tool is usable at 320 CSS pixels (4.0 Small screens; P11). The stacking width is yours (plan); record it.
- "On the left the reader plays the numbers game in `legal` mode from a start with all numbers positive (all ones by default)." The left board is a numbers board (`data-board="numbers"`) in legal play: only nodes whose number is positive may be fired (SPEC 2.3; T1 table: `numbers` view, `legal` mode, "game over" when no number is positive).
- "On the right the same moves are played with letters $x_1,\dots,x_n$ as the start (`symbolicPlay`)." The subscripts are node labels (E-7); on the 32 named types labels are $1,\dots,n$ in Bourbaki order, equal to position plus one.
- "Each fired entry on the right is displayed as a linear form", with `LinearForm.svelte`.
- "a side table matches it with a positive root of the reversed board." The rows of the table are `positiveRoots(transposeBoard(board))`, in the engine's order (sorted by total, then lexicographically), each shown as a population in label order. A fired form is matched to the row whose population equals its coefficient vector (positions order equals label order on these boards).
- "At the end every positive root has been used once." After a complete game every row is marked used, each by exactly one move. The table shows, for each used row, the move number at which it was fired, the form (LinearForm) and the number fired on the left at that move (read from the left board's play, not computed from the form; 7.3 "Components contain no mathematics beyond calling the engine").
- "The left board decides which moves are legal; the right board only follows." Acting is possible only on the left board. The right board's nodes are buttons (A-1: a board is a group of real `<button>` elements) with `data-can-act="false"`; activating one does nothing to the state (plan: `aria-disabled="true"`, and the name template of 5.6). Undo, redo, reset, scrubbing and links change the move list once, and both boards and the table are recomputed from it.

### 5.3 The right board and the fired forms (SPEC 2.7 F6, 5.4 `symbolicPlay`, oracle `symbolic_play`)

- The list of fired forms is `symbolicPlay(board, wordPositions)`, where `wordPositions = toPositions(board, moves)`. Entry $k$ is the coefficient vector (positions order) of the form fired at move $k+1$, recorded **before** that move. On every offered board $N\le120$ and $n\le8$, so recomputing it after each move is cheap (plan); one call per move is acceptable.
- The current entry of the right board at each node is itself a linear form. `symbolicPlay` returns only the fired forms, so compute the current symbolic position by the engine (plan): column $k$ is `applyWord(board, unit(k), wordPositions, 'firing')`, the numbers game played from the $k$-th unit start, and the entry at node $j$ is the vector of the $j$-th entries of the $n$ columns. This is $n$ engine calls per update and no arithmetic of your own. A unit test (5.10) checks that the entry at node `word[k]` before move $k$ equals `symbolicPlay(...)[k]`.
- Sign of a right-board entry (plan): every current entry has all coefficients of one sign and is never zero (each is plus or minus a positive root of the reversed board), and on an all-positive start its sign equals the sign of the left number at the same node. Encode it by the rules of 6.3 (positive filled, negative outlined, never zero), so the two boards read alike. A unit test checks the one-sign property on all 32 types along `longest_word`; if it ever fails, do not invent a sign: draw the right board's nodes neutral and report it.
- **Forms are roots of the reversed board, not of the board.** On $B_2$ from $(x_1,x_2)$ the four moves 1, 2, 1, 2 fire $x_1$, $2x_1+x_2$, $x_1+x_2$, $x_2$, which are $(1,0)$, $(2,1)$, $(1,1)$, $(0,1)$ of $C_2$; $B_2$ itself has $(1,2)$ where this list has $(2,1)$ (Appendix A.1). On $A_3$ along 1, 2, 1, 3, 2, 1 the forms are $x_1$, $x_1+x_2$, $x_2$, $x_1+x_2+x_3$, $x_2+x_3$, $x_3$ (oracle output; M5 beat 5).
- F6 relation between the boards (plan display, spec fact): from an all-positive start $\lambda$ the number fired on the left at move $k$ equals the fired form evaluated at $\lambda$ ("the numbers fired are the values $\langle\lambda,\beta^\vee\rangle$"). The table shows the left number beside the form; it never computes it from the form.

### 5.5 LinearForm.svelte (SPEC 7.3, A-12; owner of `site/src/components/math/LinearForm.svelte`)

- Purpose (7.3): "KaTeX is never sent to the reader (section 7.6), so whatever a tool typesets after the page has loaded is built from plain markup by three small components: ... `LinearForm.svelte` for the linear forms of T7 and the relations of T12, written as MathML (`<math>` with `<mi>`, `<mn>`, `<mo>`, `<msub>`), which the three browser engines render natively [U: ...]". Do not import KaTeX or any typesetting code into it.
- Props (plan; keep them general enough for T12 in phase 5): `coeffs: readonly (number | bigint)[]` (positions order), `labels: readonly number[]` (the subscripts, from `board.labels`), `letter?: string` (default `'x'`). Svelte 5 runes only (`$props`, `$derived`).
- Rendering rules (plan, consistent with the forms of A.1 and M5 beat 5): terms in label order; zero terms omitted; a coefficient 1 is not written; $-1$ is written as a minus sign; other coefficients as `<mn>`; between terms `<mo>+</mo>` or `<mo>−</mo>` (U+2212, the true minus sign of 6.3), a leading negative term with `<mo>−</mo>`; each variable as `<msub><mi>x</mi><mn>{label}</mn></msub>`; the zero form as `<mn>0</mn>`. ## 9. Traps

- **Reversed board, not the board.** The forms are positive roots of $C^{\mathsf T}$ (2.4(b), F6). On $B_2$ the form $2x_1+x_2$ is $(2,1)$ of $C_2$, where $B_2$ has $(1,2)$; on $B_3$ the table differs from $B_3$'s own roots (roster trap). Build the table from `positiveRoots(transposeBoard(board))`, never from `positiveRoots(board)`; on simply laced boards the two agree, so only the $B$, $C$, $F$, $G$ tests catch the mistake.
- **$F_4$ and $G_2$ transposed are not named types in the same numbering.** The transposed matrix is the same type numbered backwards, so the golden comparison reverses each vector (5.10 item 1); comparing with `types.F4.positive_roots` directly fails, and so would looking for a golden `F4T`.
- **Labels against positions.** `longest_word` in the golden file holds labels: convert with `toPositions` before `symbolicPlay`. Subscripts of $x$ are labels. On the 32 named types labels are positions plus one, so a stray `+ 1` hides; the LinearForm test with labels starting at 0 catches it (E-7).
- **The form is recorded before the move.** `symbolic_play` appends `M[i]` and then updates `M[j] -= C[j][i] * Mi` with a copy of the old row `Mi`; the node fired gets $-M_i$. If you derive the right board's entries yourself instead of by `applyWord` on unit starts, you will get this wrong; use the engine.
- **Which entry is fired.** The fired form at move $k$ is the right board's entry at the fired node before the move. Test 5.10 item 4 checks it.
- **Starts with zeros or negative entries.** F6 fills the whole table only from an all-positive start; from a dominant start with zeros the play is shorter and only coroots with a nonzero value appear. That is why a start that is not all positive is refused (5.2, plan).
- **Lowest node first.** Step and play to the end take the lowest position among the positive nodes (E-5), as the oracle's `play` does; the golden `longest_word` is that play from all ones.
- **Do not decide legality on the right.** The right board's entries are forms, which have a sign, but legality is the left board's number; the two agree from an all-positive start, and the code must still read the left board.
- **Colour classes are not fill.** Node fill and outline carry the sign (6.3); mark the colour classes by a glyph, a label list and a colour (A-5). `bipartition` puts the lowest position of each component in the first class; on several components the first class is not "the class of node 1" alone. It returns `null` on an odd cycle (the triangle) and works on one-way boards.
- **MathML in Svelte 5.** Server-rendered `<math>` is plain markup, but forms created on the client after a move must be in the MathML namespace; check `namespaceURI` after a move, not only in the built HTML. If Svelte creates them as HTML elements, use `<svelte:options namespace="mathml">` in a child component or the span fallback, and record it.
- **KaTeX's stylesheet hides `.katex-mathml`.** LinearForm's `<math>` must not carry a KaTeX class or sit inside a `.katex` element, or it disappears. Never import KaTeX into a `.svelte` file (7.6).
- **Browsers.** WebKit and Firefox are needed for `mathml.spec.ts` only; keep the main e2e project on Chromium (roster trap). Firefox is not installed by default on this machine (README 3.4 installs Chromium and WebKit). Do not start a second Playwright run while one is running (8 GB).
- **The bridge sentence of 2.4(a)** ("The number on node $i$ is the amount by which a mutation would lower city $i$.") belongs where populations and numbers of one board are shown together. T7 shows two numbers boards, so it does not carry it; your edit of T1 must leave T1's sentence untouched.
- **Svelte 5 and the toolchain.** Runes only; `onclick`, snippets, no `export let`, no `$:`; read installed type definitions before using an API; `astro build` then `astro preview`, never `astro dev`.
- **Big starts.** A link may carry a 40-digit start; `SafeInt` then throws `EngineOverflow`, and T1's rule reloads with `Big` with no message. Reuse it; never catch the overflow and show a wrong number.
- **Golden values in source.** Read `positive_roots`, `longest_word`, `bipartite_colouring` and `n_positive_roots` through `resolveGoldenPath` or the JSON, in the Vitest files and in the Playwright files alike (COMMON 4.4 forbids "a golden value typed into source"). The only vectors you may type are the worked examples of Appendix A.1: the $B_2$ forms $(1,0)$, $(2,1)$, $(1,1)$, $(0,1)$, the $B_2$ numbers of its table, and $(1,2)$ against $(2,1)$; plus the first two $A_3$ forms $x_1$, $x_1+x_2$ that M5 beat 5 quotes. Everything else (the $A_3$ forms as a list, the $B_3$ and $C_3$ roots, the $G_2$ roots, move counts) is read from the golden JSON or computed in the test. The vectors named in sections 2 and 5.4 of this file are for you, the reader, not for your source.
