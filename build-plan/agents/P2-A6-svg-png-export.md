Not exported: the control row, the layer of `<button>` elements over the board, the table view, the caption, the live region, the HTML text between the two boards of T1's linked view (plan reading; the roster's title says "any tool's figure").
- The export is a picture of what is on screen now. It recomputes nothing and calls no engine function; the current position is already drawn (4.0 "One state, derived views").
- SPEC 9.2, definition of done for a tool: it "obeys every rule of section 4.0 (default state with a caption, rendering without JavaScript, link, undo, reset, export as far as the current phase provides it, test hooks, stated limits)". From this phase the export every tool must provide is yours, delivered through `ToolFrame`, so no tool agent writes export code and you edit no `T{nn}` component.
- SPEC 1.2: the tertiary reader leaves with "Embeddable tools and exportable figures". SPEC 8.1 names "pictures that cannot be exported" as a pitfall of the prior art. ### 5.2 `exportSVG`

Signature (CONTRACTS 4, exactly): `export function exportSVG(svg: SVGSVGElement, footer: FooterLine | null): string;`. Add no parameter. CONTRACTS 4 has no labels parameter although SPEC 6.1 requires the option, and COMMON 4.4 forbids changing an interface in `CONTRACTS.md`, so the labels option is built without one (plan): `ToolFrame` passes a detached figure from which `withoutLabels` (5.4) has already removed the labels, and the unchanged `exportSVG` serialises it. Do not build an `options` parameter. If you still believe one is needed, propose it under `deviations` with the reason; it is built only if `MERGE` approves it.

Behaviour, in order (plan where not cited):

1. Browser only: if `typeof document === 'undefined'`, throw `Error('exportSVG needs a browser')`. The module must load in Node without touching the DOM, because `P1-A2`'s `export.test.ts` imports it under `environment: 'node'`.
2. If `svg.isConnected`, inline the computed styles: `const clone = svg.cloneNode(true)`; walk the live tree and the clone in parallel (`querySelectorAll('*')` on both gives aligned lists); for each pair, read `getComputedStyle(liveElement)` and write a `style` attribute on the clone with these properties: `fill`, `fill-opacity`, `stroke`, `stroke-width`, `stroke-opacity`, `stroke-dasharray`, `stroke-linecap`, `stroke-linejoin`, `opacity`, `font-family`, `font-size`, `font-weight`, `font-style`, `font-variant-numeric`, `letter-spacing`, `text-anchor`, `dominant-baseline`, `paint-order`, `visibility`, `color`. Add any further property the drawing code uses; never copy `cursor`, `background*`, `transition*`, `animation*` or anything that may hold a `url(...)`. After this step the file contains no `var(--...)` and no colour that depends on a class: the custom properties of CONTRACTS 8 (`--page`, `--text`, `--sign-pos-fill`, `--sign-pos-numeral`, `--sign-neg-outline`, `--sign-zero-outline`, `--edge-1` to `--edge-8`, `--road`, `--arrow`) arrive as the resolved `rgb(...)` values of the theme in force (SPEC 8.3: themes "driven by CSS custom properties"; the export carries the theme the reader is looking at). Elements whose computed `display` is `none` (hidden hint ghosts) are removed from the clone. Expose this step as `inlineStyles(live: SVGSVGElement): SVGSVGElement` (plan) because `composeFigure` needs it. If `svg` is not connected (a composite from `composeFigure`), skip this step: its styles are already inline.
3. Root and geometry (plan). The exported file never reuses the board's root as its root, because the board's `viewBox` may be in grid units and a `viewBox` clips whatever lies below its height and centres the drawing through `preserveAspectRatio`. Instead:
   - Measure the drawing in CSS pixels: `W` and `H` are `getBoundingClientRect().width` and `.height` of the live element, rounded to whole pixels. Never take them from the `viewBox`, which gives grid units when CSS sizes the board. For a detached composite from `composeFigure`, read its `width` and `height` attributes, which `composeFigure` sets in pixels.
   - Build a new root `<svg xmlns="http://www.w3.org/2000/svg" width="W" height="T" viewBox="0 0 W T">`, where `T = H + F` and `F` is the footer height of 5.3 plus the height of the exact-digits note of 5.7 (each 0 when absent). The root's user unit is one CSS pixel, so the 12-pixel font and the 8- and 16-pixel offsets of 5.3 come out at their stated size.
   - Put the drawing in it as a nested `<svg x="0" y="0" width="W" height="H">` that keeps the clone's own `viewBox` and `preserveAspectRatio` and holds the clone's children. The drawing therefore scales exactly as on screen, and nothing below `H` is clipped, because the footer is a sibling of the nested element, not its child.
   - Every later step works on this new root; `T` is final only after steps 6 and 7 have added their groups, so set `height` and the `viewBox` height at the end, together.

   The on-screen size follows SPEC 6.1 "Size on screen" (one grid unit is `u = min(64, floor((W - 16) / k))` CSS pixels, `W` the width of the board's box), so the exported size depends on the reader's viewport at the moment of export; that is accepted (plan), and the tests read the size from the exported file instead of assuming a number. Rewrite `xlink:href` to `href` and drop `xmlns:xlink` unless an `xlink:` attribute remains. Remove `aria-hidden` and `tabindex` from the clone: `P0-A5` hid the on-screen drawing because the buttons carry the semantics, but the exported file has no buttons, so the drawing must be visible to assistive technology. Add `role="img"` and, as the first child, a `<title>` with the board name when a footer is given and otherwise the words `exported figure` (SPEC 7.5 A-10: "Every figure has a text alternative").
4. Background: insert, as the first drawn child of the new root, `<rect x="0" y="0" width="W" height="T">` in pixels (not `100%`, so it covers the footer and the note however a viewer resolves percentages), filled with the computed value of `--page` read from `document.documentElement`, so that a dark-theme export does not become light numerals on a transparent, white-rendered ground. After inlining, remove every `class` attribute and every `<style>` element from the clone, so that no colour of the file depends on a class or a stylesheet.
5. Fractions (plan): wherever a node's value is a fraction (`data-value` of the form `p/q`, SPEC 4.0 "Test hooks") and section 3 found it drawn in a `<foreignObject>` or as HTML outside the SVG, the export draws it as SVG: one `<text>` at the node's numeral position with two `<tspan>` children (numerator above, denominator below, both centred) and a `<line>` as the fraction bar, coloured as the numeral, inside a `<g data-frac="p/q">` (plan hook inside the exported file). Remove the `<foreignObject>` from the clone. The digits come from the node button's `data-value` (exact `p/q`, a leading ASCII `-` shown as U+2212); pair a button with its drawn node by `data-board` and the label text, or by the stable order you found in section 3, and record which. This keeps "one value text per node" true for fractions, keeps the PNG free of `<foreignObject>` (which a canvas may refuse to draw), and loses no value. If the fractions are already SVG `<text>`, keep them as they are. This step needs the live DOM (the node buttons sit outside the SVG), so it runs inside `inlineStyles` on the live element, which finds the buttons under the nearest ancestor carrying `data-tool`; the same pass marks each shortened long number for step 6 (5.7). A composite has had both applied per board before `composeFigure` stacks it.
6. Exact digits of long numbers (5.7): when any value is shortened on screen, append the note `<g data-exact="">` to the new root at `y = H`, below the nested drawing, and add its height to `T`.
7. Footer (5.3): when `footer` is not `null`, append a `<g data-footer="">` to the new root below the drawing and below the note of step 6 when there is one, and add its height to `T`.
8. Labels (5.4): `exportSVG` itself never removes labels. When the reader leaves labels out, the `svg` it receives is the detached output of `withoutLabels(composeFigure(svgs))` (5.4, 5.6), so the labels are already absent and steps 2 to 7 run as for any composite.
9. Serialise the new root of step 3 (not the clone, which would lose the background, the note and the footer) with `new XMLSerializer().serializeToString(root)`, where `root` is the pixel-unit `<svg>` built in step 3, and prefix `<?xml version="1.0" encoding="UTF-8"?>` and a newline. The result is well-formed XML: the Playwright spec parses it with `DOMParser` as `image/svg+xml` and fails on a `parsererror`.

Several SVGs in one figure: T1's `linked` view draws two boards, one above the other (SPEC 4 T1). `composeFigure(svgs: SVGSVGElement[]): SVGSVGElement` (plan) inlines each live element with `inlineStyles`, then builds a detached root `<svg>` that stacks them as nested `<svg>` elements, each with its own `x`, `y`, `viewBox` and `preserveAspectRatio` and with `width` and `height` set to that live element's `getBoundingClientRect()` size in CSS pixels, a gap of 16 pixels between them, the root `width` the widest and the root `height` the sum plus gaps, both in pixels and with a matching `viewBox="0 0 width height"`. The fraction rewrite of step 5 applies to each board of the composite (the linked view is where fractions occur). `exportSVG` accepts that root (it is not connected, so step 2 is skipped). The two boards share identical `<marker>` definitions, so duplicate ids are harmless here; if you find they are not, prefix the ids per nested element and rewrite the `url(#...)` references.

### 5.3 The footer line (SPEC 8.3)

- The sentence, exactly: `Figures exported from the site carry the board name, the state and the site address in a footer line that can be switched off.` SPEC 8.3 is marked [D]; the format below is the plan's reading, to be recorded in your fragment.
- The type (plan, closing the gap in CONTRACTS 4):

  ```ts
  export interface FooterLine { boardName: string; link: string; }
  ```

  `boardName` is the name the tool shows for its board: `board.name` for a named board, in the spelling of SPEC 6.6 and CONTRACTS 2.2 (`A2`, `B3~`, `D4^(3)`, `pentagon`, `square`), which is "the name of the board the reader chose in pickers" (D19 default); for a custom board the words `custom board` (plan), unless the tool passes a name (a tool that recognises a board from its shape shows `B2=C2` per D19; T4 and T16 arrive in stage 2.2 and may pass it through the prop of 5.6). `link` is the absolute link that "Copy link" copies, built by the same function (SPEC 7.4: `"Copy link" always encodes the current state, whatever the address bar holds at that moment`), so that the footer's state and the Copy link never disagree. That link carries the state in the URL form of SPEC 6.6 (keys `z g v m c s w ...`, labels throughout, the instance prefix on a lesson page) and the site address (`site` and `base` of SPEC 7.2 item 10, built from `import.meta.env`, never typed). It carries no site version: SPEC 7.4 "Citing" gives the version to "Cite", which `P6-A5` builds in phase 6.
- Text (plan): `footerText(f) = f.boardName + ' · ' + f.link` (U+00B7 middle dot with a space either side). Set in the monospaced system stack with tabular figures (SPEC 6.3 "Typefaces"; SPEC 8.3 "one monospaced face with tabular figures for numbers"), 12 pixels, filled with the computed `--text`, left edge 8 pixels in, first baseline 16 pixels below the top of the footer (which is the bottom of the drawing, or of the note of 5.7), one `<text>` per line; all lengths are CSS pixels because the export root of 5.2 step 3 has one user unit per pixel. `footerLines(text, 96)` breaks the text into lines of at most 96 characters at a `&`, `.`, `/` or `,` where possible, else hard, and never drops a character: the lines joined again equal the input. There is no cap on the number of lines (plan). Reason: SPEC 8.3 requires that the figure "carry ... the state", and a PNG keeps only the visible text, so a capped footer with an ellipsis would lose the state of any long play in every PNG; the `<a href>` link does not survive in a PNG. A long play therefore gives a tall footer; that is the cost of carrying the state, and `pngSize`'s 8192-pixel cap scales the image down rather than cutting it. The whole group is also wrapped in `<a href="{link}">` so that viewers that render SVG links can follow it. Footer height `8 + 16 * lines + 8` pixels, added to `T` (5.2 step 3); the background rect of 5.2 covers it.
- Switching off: `footer: null` adds no group and no height. In `ToolFrame` the checkbox `Footer line` is checked by default; unchecked, the buttons pass `null`. Roster acceptance: "the footer can be switched off (test)".

### 5.4 Labels off in exports only (SPEC 6.1)

- The rule, exactly: `Node labels are always visible beside the nodes; they can be switched off only in exported figures.` So: the screen never loses its labels; `Board.svelte`'s `labels` prop stays `true` on the page; the option lives only beside the export buttons and acts only on the exported copy.
- Which elements: the label text that `Node.svelte` draws beside each node, identified by the marker you found in section 3 (record the selector in your fragment and in the spec's header comment). Only board node labels are removed. Numerals stay. The edge labels of orbit graphs stay, because SPEC 6.3 says coloured edges "carry the node label as text, so that the colour is never the only cue", and an export must not break A-5 (plan reading).
- Default: labels kept. In `ToolFrame` the checkbox `Node labels` is checked by default.
- How (plan, keeping CONTRACTS 4 unchanged): `withoutLabels(root: SVGSVGElement): SVGSVGElement` takes a detached root from `composeFigure` (5.2; with one live SVG, `composeFigure([svg])` gives a composite of one nested drawing at `x = 0`, `y = 0`), removes every element that matches the label marker, and returns the same root. It runs on the detached copy only, so the page keeps its labels. `inlineStyles` must therefore keep the label marker (class token or `data-*` attribute) on the clone; `exportSVG` step 4 removes the `class` attributes afterwards. With labels unchecked, `ToolFrame` calls `exportSVG(withoutLabels(composeFigure(svgs)), footer)` or `exportPNG(withoutLabels(composeFigure(svgs)), footer)`; with labels checked it passes the live SVG (one) or `composeFigure(svgs)` (several), as in 5.6.
- T2 has its own on-screen control "toggle labels" for the vertex labels of the garden (SPEC 4 T2 "Interactions"). That is T2's screen state, allowed by its own entry, and not this option: the export shows the garden as it is on screen, and your checkbox removes board node labels only.

### 5.5 `exportPNG`

Signature (CONTRACTS 4, exactly): `export function exportPNG(svg: SVGSVGElement, footer: FooterLine | null, scale?: number): Promise<Blob>;`, with no further parameter (the labels option arrives through the figure passed in, 5.4). Default `scale` 2 (plan): a figure 400 pixels wide gives an 800-pixel PNG.

Behaviour (plan): `const text = exportSVG(svg, footer)`; read `width` and `height` from the exported root; `pngSize(width, height, scale)` gives `[Math.round(width * s), Math.round(height * s)]` where `s` is `scale` reduced, if necessary, so that the larger side is at most 8192 pixels (browsers refuse very large canvases); create an `Image`, set `src` to `URL.createObjectURL(new Blob([text], { type: 'image/svg+xml;charset=utf-8' }))`, await `load` (on `error`, reject with `Error('the figure could not be rendered as an image')`); draw onto a canvas of that size with `drawImage(img, 0, 0, w, h)`; `canvas.toBlob(cb, 'image/png')` wrapped in a promise, rejecting when the callback receives `null`; revoke the object URL in `finally`. The resolved `Blob` has type `image/png`.

Canvas tainting (roster trap: "only same-origin content"): a blob URL made in the page is same-origin; the SVG must reference nothing else. No `<image href="https://...">`, no `@import`, no font `url(...)`, nothing copied in 5.2 that carries a URL. A tainted canvas makes `toBlob` throw a `SecurityError`; the Playwright PNG test would then fail, which is intended.

## 9. Traps

- **Computed styles come from the live element, never from the clone.** A detached clone has no computed style (`getComputedStyle` gives empty strings in Chromium). Walk live and clone in parallel; for a composite, inline each live SVG before building the detached root.
- **Roster trap, verbatim: "Fonts: exported SVG must not depend on the site's stylesheet; inline what is needed."** Inline the computed `font-family`, `font-size`, `font-weight`, `font-variant-numeric` on every `<text>`. No `<link>`, no `<style>` with `var(...)`, no `@import` in the file.
- **Roster trap, verbatim: "Canvas tainting: only same-origin content."** A blob URL made in the page is same-origin; any `http(s)` reference inside the SVG taints the canvas and `toBlob` throws. Never copy `cursor` or `background-image` in 5.2.
- **`width` and `height` must be explicit on the root** or the `Image` has no intrinsic size in some engines and the PNG comes out empty or at 300 by 150. Take them from `getBoundingClientRect()` (CSS pixels), never from the board's `viewBox`, which may be in grid units.
- **A `viewBox` clips**: anything appended below the `viewBox` height of the same `<svg>` is not drawn, and a `viewBox` in grid units scales a 12-pixel footer font to the wrong size. Hence the pixel-unit export root of 5.2 step 3 with the drawing nested and the footer and note as its siblings; a test that only reads the footer's DOM text would not catch this, which is why `the footer is inside the rendered picture` checks pixels.
- **The exported size is the on-screen size** (SPEC 6.1 grid unit), so it changes with the viewport: a test that hard-codes `800 by 600` breaks on another runner; read `width` and `height` from the exported SVG and derive the PNG's expected size from them.
- **`aria-hidden="true"` on the board SVG** (`P0-A5`): leave it on the page, remove it in the export, add `<title>` and `role="img"`.
- **The hyphen and the minus**: `data-value` carries the engine's decimal text with an ASCII `-` (`P0-A5` plan reading), the numeral on screen is U+2212. Map when comparing; never "fix" either.
- **Svelte's scoped class names carry a hash** (`svelte-1abc2de`) that changes between builds: identify labels by a stable token or attribute, not by the hashed class; never hard-code a hash in a test.
- **Two SVGs in the linked view**: exporting only the first loses the Numbers board. Compose.
- **Icons are SVGs too**: the view icons of SPEC 8.3 can sit inside the figure area; the size rule of 5.6 keeps them out of the export.
- **Fractions may not be in the SVG at all**: `Frac.svelte` is plain HTML markup (SPEC 7.3), so `P1-A5` may draw it in a `<foreignObject>` or as HTML positioned over the board, outside the SVG. Either way a plain serialisation drops or breaks the values: the HTML overlay is simply absent, and a `<foreignObject>` is rendered to canvas by Chromium only when self-contained and may be refused by WebKit (phase 3). Always rewrite them as SVG text (5.2 step 5); never ship a figure whose populations board is empty.
- **Long numbers are shortened on screen**: the drawn numeral `1.2345... x 10^83` is not the value; the export must also carry the exact digits (5.7), in a `<title>` and in the visible note, because a PNG has no tooltip.
- **The footer's link is the Copy link string, not `location.href`** (SPEC 7.4): the address bar is updated half a second after a burst and may lag; the Copy link function always encodes the current state. In tests the site address is `http://localhost` without the preview's port (the default of SPEC 7.2 item 10): assert the pathname and the query, never the origin or port.
- **The link can be long** (`w=` with thousands of moves): wrap the visible lines and never cap or cut them, because a PNG carries only the visible text and SPEC 8.3 requires the state in the figure (5.3); keep the link in `href` as well. A tall footer is accepted; record the tallest footer you saw.
- **The `labels` option is export-only** (SPEC 6.1): never bind it to `Board.svelte`'s `labels` prop on the page; a reader who unchecks `Node labels` must still see labels on screen.
- **`export.test.ts` runs in Node**: a top-level `document` or `XMLSerializer` in `export.ts` breaks `P1-A2`'s test and the build-time rendering of every tool.
- **Controls disabled in the server HTML, enabled on hydration**, not the other way round (SPEC 7.4); `nojs.spec.ts` checks every control.
- **No new dependency, no `console.log`, no `any` without a comment, no em-dash in any text you write** (COMMON 4.4; the footer separator is a middle dot).
- **Do not restructure `ToolFrame`**: `P6-A5` adds "Export LaTeX" and "Cite" next to your buttons in phase 6; `P2-A7` adds nothing to `ToolFrame` but edits `state.ts` in stage 2.2, so your `boardName` prop must have a working default.
- **Budget** (SPEC 7.6): the export code ships to every tool route; keep it small and measure if you can.
- **E-7**: no `+ 1`, no `toLabels` in export code; the drawing and the link already use labels.
- **Resource etiquette** (COMMON 4.5): one Playwright run at a time; kill `astro preview` when done.
