### 5.1 `Board.svelte`: the contract (CONTRACTS 5.1)

Props, exactly: `{ board: AnyBoard; values: (number|string)[]; game: 'mutation'|'firing'; canAct: boolean[]; labels?: boolean; roadStyle?: 'dynkin'|'roads'; decoration?: ...; onAct: (position: number) => void; hintFor?: (position) => string | null; name: string }`. `values` and `canAct` are indexed by position; `onAct` reports a position; `name` is the accessible name of the group (A-1: "A board is a group with an accessible name"). `labels` defaults to `true` (SPEC 6.1: "Node labels are always visible beside the nodes; they can be switched off only in exported figures"). `roadStyle` defaults to `'dynkin'`. Leave `decoration` typed as an optional object you do not read yet (T13 uses it in phase 6). Board is a controlled component: it holds no game state; the parent passes `values` and `canAct` and reacts to `onAct`. Svelte 5 runes only (`$props`, `$state`, `$derived`, `$effect`), `onclick` not `on:click`, snippets not slots, no `export let`, no `$:` (COMMON 3).

The board renders in two layers: the SVG (roads, discs, numerals, labels) with `aria-hidden="true"` (plan: the buttons carry the semantics, so the drawing is not read twice), and over it the `<div role="group" aria-label={name}>` holding one `<button type="button">` per position, absolutely positioned over the node's centre. Every button renders in the server HTML with the `disabled` attribute and is enabled only after hydration (SPEC 7.4; section 5.10).

### 5.2 Layout and size (SPEC 6.1, A-7)

- Row layout: node with label $i$ at $(i, 0)$ for $A_n$, $B_n$, $C_n$, $F_4$, $G_2$. That is all phase 0 needs; the $D_n$, $E$, affine, twisted, polygon and custom layouts of 6.1 come from `P1-A3`. Keep `GridLayout.kind` so that the keyboard resolver can tell "rows with branches" from "polygon or custom".
- Grid coordinates have $y$ growing upwards (6.1 says node 2 of $E_6$ is at $(3,1)$ "above node 4"). SVG $y$ grows downwards: flip once, in one place.
- Size rule, quoted: "One grid unit is $u=\min(64,\lfloor (W-16)/k\rfloor)$ CSS pixels, where $W$ is the width of the board's box and $k$ the number of grid columns the board occupies (for a row of nodes, the number of nodes). On a viewport narrower than 400 pixels the box runs from edge to edge of the viewport, so $W$ is the viewport width. The hit area of a node is a square of side $\min(44,u)$ centred on it; with the layouts above no two hit areas overlap." On $A_2$ at 360 pixels: $k=2$, $u=64$, hit area 44.
- The box reserves its size in the HTML so that hydration shifts nothing (SPEC 7.6: "Tools reserve their box size in the HTML so that hydration does not shift the page"). Below 400 pixels the box runs edge to edge. Fix the box's width and height in CSS in the server-rendered markup (plan: computed at build time from the layout and the grid unit, with a CSS rule for the edge-to-edge case), never by script after hydration; section 6 tests it.
- Targets (A-7): "Targets are 44 by 44 CSS pixels where the layout allows (beyond AA, by choice) and never less than 24 by 24 with no overlap". The hit area is the button; the drawn disc may be smaller. `gridUnit(320, 7)` is 43, `(320, 8)` is 38, `(320, 9)` is 33, `(320, 12)` is 25, as A-7 lists ("44 for boards with at most six nodes in a row, 43 for seven ($E_8$), 38 for eight, 33 for nine (the affine board of $C_8$) and 25 for twelve").

### 5.5 Keyboard model (A-1, A-2, 4.0 Keyboard and screen reader)

- 4.0: "Each board is one tab stop; arrow keys move between nodes; Enter or Space acts; a polite live region announces each result with the wording fixed in section 7.5."
- Roving `tabindex`: exactly one node button has `tabindex="0"` (plan: the lowest label at first, afterwards the last focused node; A-1 says only that one node is in the tab order, not which), every other node button `tabindex="-1"`. Tab enters the board on that one button and leaves it to the History buttons, which are "visible buttons after the board in the tab order" (A-1).
- Arrows, quoted from A-1: "On the standard layouts of section 6.1 that are rows with branches, an arrow moves to the nearest node whose centre lies within 45 degrees of the arrow's direction, the limit included, ties going to the smaller label; when no node lies there, Right and Down move to the next label and Left and Up to the previous one, stopping at the ends. On polygon layouts and on custom boards the arrows follow the labels and wrap round: Right and Down to the next label (clockwise on a polygon), Left and Up to the previous one. Every node is reachable on every layout. Home and End go to the first and last label; Enter or Space acts."
- `arrowTarget` is a pure function of the layout, the labels, the current label and the key. "Nearest" is Euclidean distance between centres in grid units; the angle test is inclusive with a small tolerance so that the exact 45 degrees of $E_8$ (Right from node 2 at $(3,1)$ reaches node 5 at $(4,0)$, nearer than node 6 at $(5,0)$) is included; equal distances go to the smaller label. Check your implementation against these values from 6.1's coordinates: on $A_2$, Right from 1 is 2, Right from 2 stays, Left from 1 stays, Down from 1 is 2 and Up from 2 is 1 (fallback by label). On $D_4$ (node 3 at $(3,0.6)$, node 4 at $(3,-0.6)$): Right from 2 is 3 (tie, smaller label), Down from 3 is 4, Up from 4 is 3, Right from 3 is 4 (no node within 45 degrees, next label), Left from 3 is 2, Up from 1 stays. The polygon and custom branch (wrap by label) is required by A-1 and costs a few lines; no phase-0 board exercises it, `P1-A3`'s layouts will.
- On a keydown of an arrow, Home or End: `preventDefault()`, move the roving `tabindex`, call `.focus()` on the target button. Enter and Space act through the button's native click; do not also handle them on keydown, or one press acts twice.
- After a move focus stays on the acted node; the button element must not be replaced by a re-render (keyed each block over positions).
- A-2: "A visible focus ring on the focused node, never hidden by sticky elements." Use `:focus-visible` with `var(--focus-ring)` (3 to 1, A-6) and make sure no `overflow: hidden` on the box clips it.
- `u` and `r`: "the shortcuts `u` (undo) and `r` (redo) work only while focus is inside the board". Listen on the group element, not on `document`; ignore the key when a modifier is held (plan; A-1 does not mention modifiers). Board exposes this through a callback prop pair or an event that the parent wires to History (plan); the contract's prop list is not extended, the parent connects them.
- Enter or Space on a disabled (not yet hydrated) button does nothing, which is what 7.4 wants.
- A-1: "Because the nodes are ordinary buttons, a screen reader in browse mode reaches them without the arrow-key layer. Focus is never trapped in a canvas." You draw no canvas; keep every node a real `<button>`.

### 5.6 Names and hooks (A-3, 4.0 Test hooks, CONTRACTS 4 and 5.3)

- A-3, quoted: `Node 3, value 2, can be fired`; `Node 5, value 0, cannot be fired` "(in legal play; in free play every node can be fired)"; `City 2, population 1, mutation would raise it`. So `nodeName('node', label, value, state)` gives `Node {label}, value {value}, {state}` with state `can be fired` or `cannot be fired`, and `nodeName('city', label, value, state)` gives `City {label}, population {value}, {state}` with state `mutation would raise it`, `mutation would lower it` or `mutation would change nothing`. The value is spoken through `speak()` so that a negative reads "minus 2" (plan: A-4's rule applied to A-3). The name goes on the button as `aria-label` and is recomputed after every move.
- Which state a city has (SPEC 2.4(a)): "A positive number marks a mutation that lowers, zero a mutation that changes nothing, a negative number a mutation that raises." With only phase-0 engine functions, derive it without arithmetic in the component (SPEC 7.3: "Components contain no mathematics beyond calling the engine"): compare `mutate(board, p, i)[i]` with `p[i]`; smaller means the mutation would lower it, larger would raise it, equal would change nothing (plan). On the index page at the start $(1,0)$: city 1 would be lowered, city 2 would be raised (checked against the oracle: $a=Cp=(2,-1)$).
- Hooks, quoted from 4.0: "Every node button carries `data-node` (its label), `data-board` (`populations` or `numbers`, which matters in the linked view), `data-value` (the value shown, as decimal text, or as `p/q` for a fraction) and `data-can-act` (`true` or `false`). The tool's root element carries `data-tool` and `data-moves`." On the index page: `data-node` is `1` or `2`, `data-board` is `populations`, `data-value` is the engine's decimal text (`board.arith.show(v)`, so `-1` with an ASCII hyphen, while the numeral on screen is U+2212; plan reading of "decimal text"), `data-can-act` is `true` on every node in free play. ### 5.8 History (4.0 History, A-1, A-8, P9, P10)

## 9. Traps

- Svelte 5 runes only; `onclick` not `on:click`; snippets not slots; no `export let`, no `$:`, no `writable` for local state (COMMON 3, SPEC 7.2 item 5; roster trap 1). Astro 7's integration and config keys differ from Astro 5: read `node_modules/astro` and `node_modules/@astrojs/svelte` before writing the island directive.
- A disabled control must be rendered disabled in the server HTML and enabled by the island on hydration, not the other way round (7.4; roster trap 2). Flip a `hydrated` flag in `$effect`; nothing that touches `window` or `document` may run during server rendering.
- Island props are serialised. Pass `boardName` and `start`, build the `Board` with `boardFromName` inside the island; a `Board` object carries `arith` with functions.
- The hit area is a square of side $\min(44,u)$ centred on the node; the drawn circle may be smaller (A-7; roster trap 3). The buttons are the hit areas; size them in CSS pixels, not in SVG user units that scale with the viewBox.
- SVG $y$ grows downwards; the grid of 6.1 grows upwards. Flip once. The arrow resolver works in grid coordinates, never in screen coordinates.
- "minus" is spoken, `−` (U+2212) is written on screen (6.3; roster trap 4), and `data-value` is the engine's decimal text with an ASCII hyphen. Three spellings of one sign; do not mix them.
- The roster's example announcement `Mutated city 1. Populations now 1, 0. Move 1.` is the starting position, not the result. The engine and the oracle give $(-1,0)$: `Mutated city 1. Populations now minus 1, 0. Move 1.`
- The mutation changes only entry $i$ (SPEC 2.2, oracle `mutate`); the value shown on the other city does not move. If your display shows both values changing after one mutation you are firing, not mutating, or you are transposing.
- Positions against labels (E-7): `onAct` gives a position, `moves` holds labels, `data-node` is a label. On $A_2$ a stray `+ 1` would pass every test, so write `toLabels`/`toPositions` from the start; `P0-A2`'s label test guards the engine, nothing guards your component except your discipline and RT-02.
- "May raise, lower, change nothing" comes from the sign of the number $a_i$ (2.4(a)), which in phase 0 you get by comparing `mutate(board, p, i)[i]` with `p[i]`; no Cartan arithmetic in the component (7.3).
- Enter and Space on a `<button>` fire `click`. Handle acting on `click` only; handle arrows, Home and End on `keydown` with `preventDefault()`; otherwise one press acts twice or the page scrolls.
