### 5.3 The graph (SPEC 4 T8 first paragraph; 2.6; 2.7 F5; 5.4; 5.5; E-5, E-6)

- Vertices: one call `orbitGraph(board, [rho], 'firing', CAPS.weylExplorerGroup, undefined, true)` with `rho` all ones in the board's arithmetic (`legalOnly` true: the oracle's `orbit_graph(..., legal_only=True)` as used by `legal_layers`). It must return `truncated: false` and exactly `weylOrder(board)` items on every offered board; the cap equals F4's group order, and SPEC 5.5 says the cap acts only "when the search is about to add one position more than the cap", so F4 completes (a unit test proves it). Layer of a vertex = its `depth` ("drawn in layers by the number of moves"; 2.6: "Length of $w\in W$ | least number of moves producing $w$").
- Layer sizes: from the graph's `depth`; a unit test proves they equal `legalLayers(board)` and `types[T].length_distribution`, and that they sum to `types[T].weyl_order`.
- Edges: SPEC 5.4, verbatim: "The edges of a **move graph** are not stored by `orbitGraph`, which records only the first way each position was reached. A tool that draws all of them applies every move to every position of `items` once more." For T8 the edges are the legal moves (plan reading of "reachable ... by legal play"): from each vertex $v$ and each node $i$ with $v_i>0$, an edge from $v$ to `fire(board, v, i)` labelled by node $i$. Each such edge goes from layer $d$ to layer $d+1$ (F5: "a node carries a positive number exactly when firing it lengthens the element"), so every edge is drawn once, downward, and the graph has $\lvert W\rvert\cdot n/2$ edges (A3 36, D4 384, F4 2304; the oracle confirms). Unit tests prove both.
- Order: the engine's breadth-first order (E-5: "breadth-first searches try nodes in increasing position"); you never reorder `items`, `depth`, `parent` or `node`. The order within a drawn layer is `layeredLayout`'s, deterministic, so the server render and the hydrated render are identical.
- Stated limits (4.0, verbatim): "When a computation is cut off, the tool says so in words ("stopped after 40 layers", "stopped after 100000 positions") and never presents a truncated result as complete. The words "not of finite type" are used only when `classify` has said so, never as an inference from a cap." On the fourteen offered boards no search of T8 is cut off, but the code must still honour the rule (plan, record it):
  - If `orbitGraph` returns `truncated: true`, the tool draws no layer sizes, no top-to-bottom path count and no "reaches N positions" sentence as if complete; it shows the sentence of SPEC 5.5 ("Order and truncation of a search", verbatim): "A tool says "stopped after $L$ layers" when `truncated` is false and `depthReached` equals `maxDepth` (the positions of that depth were not expanded, so more may exist), and "stopped after $N$ positions; layers 0 to $L$ are complete" when `truncated` is true." So the text is `stopped after N positions; layers 0 to L are complete`, with N the cap passed (the number of `items`) and L the result's `completeLayers`, in the form of the 4.0 example "stopped after 2000 positions; layers 0 to 10 are complete" (CONTRACTS 5.3 lists that exact string). Never shorten it to "stopped after N positions".
