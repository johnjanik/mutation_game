### 5.1 Conventions at your boundary

- `SPEC.md` section 2 is the single source of truth. $C_{ij}=\langle\alpha_i^\vee,\alpha_j\rangle$; $A_{ij}$ is the number of roads from $i$ to $j$; $C=2I-A^{\mathsf T}$. Mutation uses row $i$ of $C$; firing uses column $i$. Call `P0-A2`'s `mutate` and `fire` and `P1-A1`'s `toNumbers`; never re-implement a move.
- The bridge sentence of 2.4(a), which `SPEC.md` marks [D] and requires "with the same wording, wherever the two views are shown together", belongs to tools and lessons; it is quoted so that your signs agree with it: "**The number on node $i$ is the amount by which a mutation would lower city $i$.**" The root test lowers at a city whose number is positive; legal firing fires a positive number (2.3).
- E-7: inside the engine a node is a position $0,\dots,n-1$. Every function of yours takes positions and returns positions: `ClassifyRecord.nodes` and `bourbaki_order`, `NonfiniteSubboard.nodes`, `identify(...).order`, relabellings, the witness node, `PlayResult.word`. - E-5: "Where the oracle makes a choice, the engine makes the same one ... `identify` returns the lexicographically smallest relabelling". `playFate` takes the lowest position unless `choose` is given. Functions do not mutate their arguments; return fresh arrays and objects.

- E-2: every board you construct (affine, twisted, `pentagon`, `square`, `affineExtension`) is a `Board<bigint>` with `arith: Big` (`CONTRACTS.md` 2.4: "all return Board<bigint> with labels per E-7"). Signatures (`CONTRACTS.md` 2.4): `symmetrizer(board): Rational[] | null; gram(board): Rational[][] | null`.

### 5.4 `cartanClass`

### 5.5 `relabellings`

`relabellings(b1, b2, limit?: number): number[][]`, "lexicographic; p[i] = node of b1 playing node i of b2" (`CONTRACTS.md` 2.4); the oracle's docstring: "All tuples p with C1[p[i]][p[j]] == C2[i][j] for all i, j: node i of C2 is node p[i] of C1." 5.5, verbatim: "order the nodes of the second board so that each comes next to an earlier one; assign images one node at a time, keeping only candidates whose row and column of road counts match and whose entries against all nodes already placed agree; return all complete assignments in lexicographic order. This is the oracle's routine." Port lines 347 to 385 exactly:

1. Different sizes give `[]`.
2. Signature of node $i$: $(C_{ii}$, the sorted off-diagonal entries of row $i$, the sorted off-diagonal entries of column $i)$. If the sorted lists of signatures of the two boards differ, return `[]`.
3. Placement order: for each component of `b2` (in order of least position), a breadth-first walk from its least position, neighbours $j$ (joined either way) tried in increasing position.
4. Backtracking: for the node $i$ at step $k$, candidates $c=0,\dots,n-1$ in increasing order, unused, with the same signature, and with `C1[c][p[j]] === C2[i][j]` and `C1[p[j]][c] === C2[j][i]` for every node $j$ already placed.
5. Collect complete assignments; return them sorted lexicographically.

Limit (plan, record it): stop the search once `limit` assignments have been found, then sort what was found. When the total is at most `limit` the result equals the oracle's exactly; when it exceeds the limit the list holds the first `limit` found in the search order, sorted. E-6 says only that "`relabellings` and `symmetries` take a limit on the number of results (default 10000)"; the reason is in 5.5 "Matching two boards": "(A board with a very large symmetry group, such as a star with eleven arms, has millions of matchings with itself; hence the limit of E-6. `identify` needs only the first few.)". Works on any kind of board, one-way included (5.6 row "`components`, `bipartition`, `relabellings`, ... | work (roads in either direction join)").

### 5.14 `playFate`

`playFate<T>(board, a, choose?, cap?): PlayResult<T>`, "'ended' | 'looped' | 'cap'" (`CONTRACTS.md`); 5.4: "legal play with loop detection"; 5.5: "keep the set of positions seen; stop with `looped` at the first repeat, with `ended` when no number is positive, with `cap` otherwise. On a finite-type board the result is always `ended`." Port lines 1309 to 1325 exactly, including the order of the tests:

1. `seen` maps the key of the start (the entries joined as decimal text with `arith.show`) to 0.
2. Loop: `allowed = legalNodes(board, current)`; if empty, return `{ status: 'ended', moves, word, fired, position }`.
3. `i = choose ? choose(allowed, current) : allowed[0]` (`RangeError` if `choose` returns a node not in `allowed`, plan); push `current[i]` to `fired` and `i` to `word`; `current = fire(board, current, i)`.
4. If `current` is in `seen`, return `{ status: 'looped', ..., firstVisit: seen.get(key) }`, "the move count at which the repeated position was first seen" (0 is the start).
5. Record `seen.set(key, word.length)`; then if `word.length >= cap`, return `{ status: 'cap', ... }`.

The default `cap` is `CAPS.playMoves`, 20000 (the oracle's default and the cap of 5.6, "reported as "still running after 20000 moves""). `firstVisit` is present only with `'looped'`. Note step 5: a game whose `cap`-th move reaches a position with no positive number reports `'cap'`, not `'ended'` (oracle: on $A_2$ from $(1,1)$, `cap` 3 gives `'cap'` with 3 moves at $(-1,-1)$, `cap` 4 gives `'ended'` with 3 moves); this differs from `P1-A1`'s `play` and is the oracle's choice (trap 6). `cap` must be a positive integer (`RangeError` otherwise, plan). Works on every kind of board (5.6 first row). ## 9. Traps

1. `cartanClass` uses the leading principal minors of $B=DC$, not of $C$; the definition by all principal minors is the oracle's cross-check only (roster). Test balance first: a board that is not balanced is `'indefinite'` whatever its minors are, and `gram` exists only for balanced boards.
2. `relabellings` must return `p` with `C1[p[i]][p[j]] = C2[i][j]`: node $i$ of the second board is node `p[i]` of the first (roster). So `identify` calls `relabellings(board, standard)` and `order` maps Bourbaki node $k+1$ to a position of the board; `bourbaki_order[k] = nodes[order[k]]`. Reversing the arguments gives the inverse permutation, which is equal only by luck.
3. `A2^(2)` has a 4 in the Cartan matrix (`[[2, -4], [-1, 2]]`); the editor's road cap of 4 each way must still admit it (roster). The engine has no road cap at all.
4. Marks of twisted boards differ from comarks; reversing roads exchanges them (roster, 2.12). `marks` solves $C\delta=0$ (columns), `comarks` solves $c^{\mathsf T}C=0$ (rows): swapping them passes every simply laced test and fails `B`, `C`, `F`, `G` and the twisted boards.
5. The guards of E-11 change the behaviour of phase-1 functions on non-finite boards: finite-theory functions throw `NotFiniteType` there, while `mutate`, `fire`, `orbit`, `roots`, `play` keep working. Update the phase-1 tests only by adding cases, never by weakening (roster).
6. `playFate` tests the cap **after** recording the move, so the `cap`-th move that ends the game reports `'cap'`; `play` (`P1-A1`) checks for the end first. And a repeat is reported as `'looped'` even on the `cap`-th move, because the loop test comes first. Port the oracle's order; do not "fix" it.
7. `isRootPopulation` on a one-way board throws `NeedsTwoWayRoads`; on the triangle $e_1+k\delta$ takes $2k$ steps (roster). It negates a non-positive vector first, so a negative root is `true`; the zero vector and a mixed vector are `false`. The descent picks the **lowest** positive number; any choice would be correct mathematically, but the step count against the cap depends on it.
8. `symmetrizer` on an unbalanced board: the oracle's raw function returns numbers (`[2, 1, 2]` on the first unbalanced triangle), and only `is_symmetrizable` says no. The engine returns `null`; the golden `balanced` field comes from the same check. On a one-way board the oracle's walk divides by zero; check the kind first.
9. `formIsInvariant`: the oracle's two functions answer different questions. `form_is_invariant` compares matrices ($S^{\mathsf T}MS=M$); `form_invariance_witness` compares quadratic values $p^{\mathsf T}Mp$. For symmetric `M` they agree. The witness loops node outside, population inside, units before pairs; do not swap the loops, or T3 shows a different witness.
10. `identify` must try the candidates in the order A, B, C, D, E, F, G; trying C before B names the rank-2 board `C2`. Its affine board is `C2~` because `affineCandidates` skips `B2~`, but `boardFromName` accepts both `B2~` and `C2~`, and their matrices differ (`affine.B2.constructor_name` is `B2~`, its `name` is `C2~`).
11. Labels: the golden file's `classification_tests` boards have labels $1..n$, so a stray `+ 1` in `classify` passes every golden test. Only `labels-affine.test.ts` on boards whose labels start at 0 catches it (E-7). Vectors (`marks`, `comarks`, `symmetrizer`, `least_k...`, populations) are in label order and are never converted; node lists (`nodes`, `bourbaki_order`, words) are.
12. `smallestNonfiniteSubboard` returns `null` when the **whole** board has a one-way road, even if some component is two-way; `spectralRadius` likewise. `classify` instead judges each component on its own.
13. `spectralRadius`: keep the oracle's order of operations (estimate $x\cdot y$ before normalising; tolerance test against the previous estimate; the first step only records it), floats only here. Format with `toFixed(4)`; JavaScript and Python round the same exact binary value, and no golden value sits on a tie.
