## 1. Objective

When you are done the site has its own projector for higher-dimensional point sets, written in TypeScript with no library (SPEC 7.1): `site/src/components/draw/projector.ts` turns positions of the numbers game into Euclidean points through the engine's `euclideanBasis`, rotates them in any coordinate plane, projects them to the Coxeter plane or to three chosen coordinates with the three turning angles of SPEC 6.6, and attaches a depth cue; `canvasScene.ts` draws the points and segments on a Canvas 2D context within the edge caps of SPEC 5.6; `svgScene.ts` produces the same picture as an SVG string in Node, which is how T10 ships its default view without JavaScript (SPEC 7.4). A build-time pipeline, `scripts/presets.mjs` with the data files under `site/public/presets/T10/`, computes the vertices and edges of every T10 configuration that SPEC section 3 names, each file at most 30 kB after compression, so that no default of T10 needs the worker (SPEC 4 T10, E-9). A browser test records that the $E_8$ root set with its 6720 edges draws in the Coxeter plane in under 100 ms (SPEC 7.6). `P4-A3` builds T10 on these three modules and these files in stage 4.2.

## 5. Requirements

### 5.1 Scope and boundaries (SPEC 7.1, 5.1 E-1 and E-9, 7.3)

- SPEC 7.1, row "Drawing": "SVG for boards, diagrams, posets and small graphs; Canvas 2D for projections with many edges", "no library", "the projector for higher-dimensional point sets is a few hundred lines of our own code (rotations in coordinate planes, orthogonal projection, depth cue)". No three.js, no Threlte, no d3, no WebGL, no dependency of any kind (COMMON 3; roster trap 1). Keep `projector.ts` near that size.
- The mathematics of the games stays in the engine (SPEC 7.3: "Components contain no mathematics beyond calling the engine."). You compute nothing about boards, roots, orbits, edges, eigenvalues or the form: `euclideanBasis` gives $E$, `toPopulation` gives $C^{-1}a$, `wythoffEdges` gives the edges, `formValue` gives inner products. What is yours is linear algebra on floats in the Euclidean coordinates $y$: rotations, projections, scaling to a box, and drawing (E-1: floating point appears in the geometry functions; your code is the display side of them).
- Your modules are pure and synchronous; they know nothing about workers, the DOM (except the `Context2DLike` passed in) or Svelte state. `svgScene.ts` and `presetsT10.ts` must run in Node with no `window` or `document`. E-9: the data files exist so that T10's defaults never enumerate; nothing you write calls `engineCall` or the worker.
- Positions against labels (E-7): inside your modules a node is a position, as in the engine; everything written to a data file, a hook or a URL value is a label, converted with `toLabels` and `toPositions` only. Coordinate axes of the `j` value are "counted from 1" (SPEC 6.6) and are positions plus one inside.

### 5.2 From positions to Euclidean points (SPEC 2.14 steps 1 to 4, 5.4 Geometry table)

- `toEuclidean(board: AnyBoard, E: number[][], a: readonly number[]): number[]` draws a position $a$ of the numbers game at $y=E\,C^{-1}a$ (SPEC 2.14 step 4): call `toPopulation(board, a)`, which returns rationals (`null` only when $\det C=0$, which cannot happen on a finite board; throw a plain `Error` naming the board if it does), convert each rational to a float as `Number(num) / Number(den)`, then multiply by $E$. `toEuclideanPopulation(E, p)` does $y=Ep$ for a population (SPEC 2.14 step 3). Both take $E$ as given by `euclideanBasis(board).E` (or by `choleskyBasis(board)` in tests and in T6's kaleidoscope: "Any other factorisation $B=E^{\mathsf T}E$ is an equally valid picture, rotated.").
- Never rebuild $E$, never diagonalise anything, never use bare eigenvectors (SPEC 2.14: "The factor $\Lambda^{1/2}$ matters: projecting with the bare eigenvectors gives a distorted picture in which the rotation is not a rotation."). Never feed numbers $a$ into $E$ directly: $Ea$ is a picture of the dual object and looks plausible (roster trap, generalised; section 9).
- Vectors in the engine's order of positions; on named finite boards labels are $1,\dots,n$ in position order, so a vertex read from a data file (labels order) is also in position order. Convert node lists, not vectors.

### 5.3 Views, frames, rotations, turning angles (SPEC 4 T10 "Projection", 6.6, 2.14 "The Coxeter plane")

The projection bullet of T10, verbatim: "rank 2 flat; rank 3 as a wireframe that can be turned (points and segments with a depth cue; no shaded faces in version 1); rank 4 and above by orthogonal projection, with "Coxeter plane", "three chosen coordinates" and rotation in any coordinate plane, by buttons and keys as well as by dragging."

- **Views.** `type View = { kind: 'coxeter' } | { kind: 'xyz'; axes: readonly [number, number, number] }` with axes as positions $0..n-1$ of the Euclidean coordinates $y$. The Coxeter view is the plane of coordinates $0$ and $n-1$ of $y$ (SPEC 2.14: "spanned by the first and last coordinates of $y$ (smallest and largest eigenvalue, exponents 1 and $h-1$)"), which is what the oracle's `coxeter_plane_points` computes with rows 0 and $n-1$ of $E$. Its depth axis is coordinate 1 of $y$ for $n\ge3$ and none for $n=2$ (plan; record it). `xyz` keeps coordinates `axes[0]`, `axes[1]` as the picture and `axes[2]` as depth. Rank 2 is "flat": the picture is $(y_1,y_2)$, there is no depth axis, and `xyz` is not available because three distinct coordinates do not exist; rank 3 is the wireframe that can be turned (SPEC 4 T10) and, by the grammar of the `j` value below, accepts both `coxeter` (picture coordinates 0 and 2, depth coordinate 1) and every `xyz:a,b,c` with `a`, `b`, `c` a permutation of 1, 2, 3 (SPEC 6.6 does not limit rank 3 to one view); its default is `xyz:1,2,3` (plan, see `defaultProjection`); rank 4 and above offer both kinds of view as well.
- **Frames.** `interface Frame { u: number[]; v: number[]; w: number[] | null }`, orthonormal vectors of length $n$ in $y$-space; `w` is `null` when there is no depth axis (rank 2), never a zero vector (plan; record it). `frameFor(n, view)` returns the unit coordinate vectors; `project(frame, y)` returns `{ x: y·u, y: y·v, z: w === null ? 0 : y·w }`. Because the frame is orthonormal and the form is the dot product in $y$-space, the picture of a vector in the chosen plane has $x^2+y^2=(p,p)$: this is what "projection preserves the invariant form on the chosen plane" (roster acceptance) means here, and the test of 5.11 states it that way (plan interpretation; record it).
- **Turning angles.** `interface Projection { view: View; turn: readonly [number, number, number] }`, degrees. `turnFrame(frame, turn)` turns the frame about its horizontal axis `u` (rotating `v` and `w` in their plane by `turn[0]`), then about its vertical axis `v` (rotating `u` and `w` by `turn[1]`), then about the viewing axis `w` (rotating `u` and `v` by `turn[2]`), in that order (plan; record it). Each step is a rotation of two unit vectors in the plane they span, so the result stays orthonormal to $10^{-12}$. With no depth axis (`w === null`, rank 2) there is no third direction to turn into: `turnFrame` applies only `turn[2]` (rotating `u` and `v`) and leaves the frame unchanged by `turn[0]` and `turn[1]`, so the picture stays flat as SPEC 4 T10 says ("rank 2 flat") and `u`, `v` stay orthonormal (plan; record it). `parseProjection` still accepts all three angles on rank 2, and `formatProjection` writes back what was parsed.
- **Rotation in any coordinate plane.** `rotationInPlane(n, a, b, theta)` returns the $n\times n$ Givens rotation of the plane of coordinates `a` and `b` (positions) by `theta` radians; `compose(...R)` multiplies; `apply(R, y)` applies. These act on $y$-space before the frame, so that a rotation and the three turning angles compose; `apply(compose(R(θ), R(-θ)), y)` equals `y` to $10^{-12}$ (roster acceptance). SPEC 6.6: "a rotation of T10 in a coordinate plane beyond the three turning angles" is "not part of a link in schema 1"; your `Projection` therefore has no field for it, and T10 keeps such rotations in local state.
- **The `j` value** (SPEC 6.6, verbatim): "`coxeter`, or `xyz:` and three coordinate numbers counted from 1 (`xyz:1,2,3`); either may be followed by `@` and three whole numbers of degrees, the turn of the picture about its horizontal, vertical and viewing axes (`xyz:1,2,3@30,20,0`)". `parseProjection(text: string, n: number): Projection | null` accepts exactly that grammar: `coxeter` for $n\ge2$ (rank 3 included); `xyz:a,b,c` with `a`, `b`, `c` distinct integers in $1..n$ (so never for $n=2$, and on rank 3 any order of 1, 2, 3, for example `xyz:2,1,3`); an optional `@h,v,w` with three integers (negative allowed on input; plan); returns `null` for anything else (SPEC 6.6 validation: "a known key with a value that does not parse" makes the codec load the default state, and `null` is how you tell it). `formatProjection(p)` writes the same grammar with the angles reduced to $0..359$ and omits `@0,0,0` (plan). `formatProjection(parseProjection(s, n))` is `s` for every normalised `s`. `defaultProjection(n): Projection`: no `xyz` value exists for $n=2$, so for $n=2$ it returns `{ view: { kind: 'coxeter' }, turn: [0, 0, 0] }`, since for rank 2 the Coxeter plane is the whole plane and the picture is flat; for $n=3$, `xyz:1,2,3`; for $n\ge4$, `coxeter` (plan; `P4-A3` may fix another default per board in `registry/T10.ts`, and the state field `projection`, when present, overrides).

### 5.4 Depth cue (SPEC 4 T10 "Projection": "points and segments with a depth cue")

- `depthStyle(depth: number): { width: number; radius: number; alpha: number }` for `depth` in $[0,1]$, 0 far and 1 near, is monotone non-decreasing in each field, continuous, and returns the middle values when the scene has no depth axis. The cue works through stroke width and point radius first; if `alpha` varies, keep it at or above a floor that leaves the road colour at 3 to 1 against the page (A-6 names roads among the elements that must reach 3 to 1; a faded far segment is still a road). Record the mapping and the floor in the fragment.
- `buildScene` assigns each point `depth` from its `z` normalised over the scene's `z` range, and each segment the mean depth of its ends; segments are sorted far to near so that both renderers draw in the painter's order (plan).

### 5.5 Building a scene (SPEC 6.1 "Size on screen", 7.5 A-11, 4.0 Small screens)

- `buildScene(points: Point3[], edges: ReadonlyArray<readonly [number, number]>, box: { width: number; height: number; margin?: number; radius?: number }, options?: { depthCue?: boolean }): Scene`. The scene holds pixel coordinates in the box with $y$ growing downwards (both SVG and canvas do), the picture centred, aspect ratio preserved, and a scale that depends on `radius` and not on the current rotation: by default `radius` is the largest Euclidean norm $\sqrt{y\cdot y}$ over the points, which no rotation or turn changes, so a picture does not jump while it is turned (plan; record it). `margin` defaults to the largest point radius plus 2 pixels.
- A scene must be buildable for a box 320 CSS pixels wide (SPEC 4.0 Small screens: "Every tool is usable at a width of 320 CSS pixels."; P11). The scene is in CSS pixels; the device pixel ratio is the renderer's concern (5.6).
- `Scene` carries `width`, `height`, `points` (`x`, `y`, `z`, `depth`), `segments` (`a`, `b` indices, `depth`), `hasDepth`. ### 5.6 `canvasScene.ts` (SPEC 4 T10 "Limits", 5.6 caps, 7.6, A-5, A-6, 6.3)

- The limits bullet, verbatim: "edges are enumerated and drawn up to 70000 when the picture is at rest; while it is being turned at most 8000 are drawn; beyond 70000 only vertices, with a message. ### 5.8 Distinct dots and rings (SPEC 2.14, 5.4 row `coxeterPlanePoints`, `coxeterPlaneRings`)

- SPEC 2.14: "Different roots share a projected point for $A_3$, $A_5$, $A_7$, $B_3$, $B_6$, $D_4$, $D_5$, $D_6$, $D_7$, $D_8$, $E_6$, so a picture of those types shows fewer dots than roots, and the tool must say so." The engine's `coxeterPlaneRings(board)` answers for the root set only. For an arbitrary orbit T10 needs the same count, so `projector.ts` exports `countDistinct(points: ReadonlyArray<{ x: number; y: number }>, digits = 6): number` and `ringsOf(points, digits = 6): [number, number][]` (radius, count; innermost first) that follow the oracle's two rules (SPEC 5.4: "with radii and coordinates rounded to 6 decimals and $-0$ counted as 0"), which differ:
  - `ringsOf`, as `rings` in the oracle's `coxeter_plane_rings` (`round(math.hypot(x, y), digits)`): compute the radius `Math.hypot(x, y)` from the unrounded `x`, `y`, round the radius to 6 decimals, key by the rounded radius, count, and sort by radius ascending. The coordinates are not rounded first.
  - `countDistinct`, as `distinct` there (`round(x, digits) + 0.0, round(y, digits) + 0.0`): round each coordinate to 6 decimals, add `0` so that $-0$ becomes $0$, key by the rounded pair.
  - Round with `Math.round(x * 1e6) / 1e6` (never `toFixed`, which can print `-0.000000` for a tiny negative; section 9). This is not bit-for-bit Python: Python's `round` rounds the exact binary value half to even, while `Math.round(x * 1e6)` rounds halves up after a multiplication that can itself round. The two can differ only for a value within about $10^{-12}$ of a rounding boundary. The golden comparisons do not depend on that (radii within $10^{-5}$ under rule 3; ring sizes and distinct counts are checked in the tests of section 6); if a count ever disagrees with the golden value, report it with the value at the boundary rather than tuning the rounding (plan).
- These two helpers take the projected `x`, `y` of the Coxeter view with zero turn and no rotation, which is what the golden `coxeter_plane` describes; tested on $E_8$, $D_4$ and $A_3$ (5.11).

## 9. Traps

- **Do not add three.js** (roster; SPEC 7.1 lists it among what is not used, with the reason "no 300 kB dependency"). Nor any other package: COMMON 3.
- **The $E_8$ edges are the 6720 pairs at inner product 1 (2.14); do not compute them by nearest-neighbour search in floats** (roster). The pipeline takes them from `wythoffEdges`; the test checks `formValue` equals `1` exactly on every edge. Float distances between 240 points are a check at best, never the source.
- **Preset files are fetched by the tool; no default state may need the worker (E-9)** (roster). A configuration that is not in `PRESET_CONFIGS` is not a preset; if `P4-A3` chooses a default outside the seven, it must add it to the list and rerun the script, not enumerate on load.
- **`P4-A1` runs beside you.** `euclideanBasis`, `wythoffEdges` and `wythoffFVector` are in your `dependsOn` and in your stage. Never merge from `agent/P4-A1`, never port the functions into `site/`, never stub them in a test; report `partial` (section 3).
- **Numbers against populations.** Vertices in the files are positions of the numbers game (Dynkin labels). The picture is $y=E\,C^{-1}a$ (SPEC 2.14 step 4), so `toPopulation` comes before $E$. $Ea$ is also symmetric and also pretty; it is wrong, and no ring test on a simply laced board of determinant 1 would notice the error as loudly as the `A2` test with the fractions $2/3$, $1/3$ does. Keep that test.
- **The Coxeter plane is rows 0 and $n-1$ of $E$** after the engine's ascending sort of eigenvalues, that is coordinates `0` and `n-1` of $y$; rows 0 and 1 are not it. `types.E8.coxeter_plane.rings` catches the mistake (8 rings of 30, radii to $10^{-5}$).
- **Signs of eigenvectors and repeated eigenvalues are not unique** (SPEC 5.5). Never assert a coordinate; assert radii, counts, dot products, orthonormality, round trips. The picture may be mirrored between two implementations of Jacobi and both are right.
- **Rotations act on $y$, not on $p$.** A Givens rotation of population coordinates is not an isometry of the form. Rotate after $E$.
- **The frame is in $y$-space.** `u`, `v`, `w` are unit coordinate vectors of $y$ (turned), not rows of $E$. Rows of $E$ are neither orthogonal nor normalised.
- **Rank 2 and 3.** For $n=2$ there is no depth axis and no valid `xyz` value; for $n=3$ `xyz:1,2,3` is the whole space, so $x^2+y^2+z^2=y\cdot y$. Do not let `frameFor` index coordinate 1 as depth when $n=2$: `w` is `null` there, never a zero vector, and `turnFrame` uses only `turn[2]`, so the frame never loses length.
- **Degrees, whole, counted from 1.** The `j` value writes axes from 1 and angles as whole degrees (SPEC 6.6); inside you use positions from 0 and radians. Convert at `parseProjection` and `formatProjection` only.
- **$y$ grows downwards in SVG and on a canvas.** Flip once, in `buildScene`, so that both renderers agree and the test of the same coordinates holds.
- **The 100 ms budget is a batching problem.** 6720 `stroke()` calls miss it on a phone; eight strokes do not. Group by depth level; no `save`/`restore` per segment; no string formatting in the loop.
- **Painter's order.** Draw far segments first in both renderers; the SVG's document order is its painter's order.
- **`devicePixelRatio`.** Size the backing store by `dpr` and `setTransform` once, or the picture is blurred on phones and the hit of the 100 ms test differs between machines; never scale the scene coordinates themselves.
- **Caps are inclusive and come from `CAPS`.** 70000 edges are drawn, 70001 are not; 8000 while turning; 20000 points. Retyping `70000` in `canvasScene.ts` is a finding for RT-11; raising a cap to pass a test is forbidden (COMMON 4.5).
- **The 8000 while turning must be the same 8000 every frame**, or the picture flickers; a fixed stride through the far-to-near order, computed from the counts alone, is deterministic.
- **Colours only through tokens.** A hex literal in `canvasScene.ts` or `svgScene.ts` breaks the dark theme and is a finding for RT-05. The canvas gets strings read from `getComputedStyle`; the SVG gets `var(--road)`. A depth fade by alpha can drop a road under 3 to 1 (A-6): width and radius first, alpha floored.
- **A canvas is not a text alternative** (A-10) and must not trap focus (A-1). The probe's canvas has `role="img"` and an `aria-label`; T10 adds the table view.
- **`-0`** (SPEC 5.4: "$-0$ counted as 0"). `Math.round(-1e-9 * 1e6) / 1e6` is `-0`; `(-0).toFixed(6)` is `"0.000000"` but `(-1e-9).toFixed(6)` is `"-0.000000"`. Round first, add `0`, then key.
