# P4-A3: Tool T10 Geometry Studio

Phase 4, stage 4.2. Size L. Runs in: a worktree on branch `agent/P4-A3`.

Before this file you have read `build-plan/COMMON.md` and `build-plan/CONTRACTS.md`. Everything there applies.

## 1. Objective

When you are done the site has the Geometry Studio, tool id `geometry`, number T10, on its route `/tools/geometry` and ready to be placed by lesson M7 (`P4-A6`, stage 4.3). The reader picks one of the 32 named finite-type boards and puts a non-negative integer on each node by clicking (or presses "root polytope"); the tool draws the orbit of that position as points in Euclidean coordinates with the edges and the face table of SPEC 2.14, flat for rank 2, as a turnable wireframe for rank 3, and by orthogonal projection (Coxeter plane, three chosen coordinates, rotations in coordinate planes) from rank 4 on; it switches between the polytope graph and the move graph, offers "make uniform" in floating point, shows the $E_8$ showpiece with its 8 rings of 30 and 6720 edges from a build-time data file, states its limits in words, and ships an SVG snapshot of the default projection for readers without JavaScript. Every acceptance bullet of SPEC 4 T10 is an automated test; gate G4 checks them together with the drawing-time test of SPEC 7.6, the no-JavaScript snapshot and the size of the route.

### 5.2 Boards (SPEC 4 T10 "For the named finite types", 4.0 Board pickers, 5.6)

- The picker offers exactly the 32 named types, grouped by letter: `A1` to `A8`, `B2` to `B8`, `C2` to `C8`, `D4` to `D8`, `E6`, `E7`, `E8`, `F4`, `G2`, named as the reader chose them (D19 default). A picker change sets `board` and resets `rings` to the tool's default for that board: the root polytope of the new board (plan; record), `projection` to the default for its rank (5.5), `graph` to `polytope`.
- On load the board goes through `resolveBoard`, which calls `classify` once; a board that is not one of the 32 names (custom, affine, `pentagon`, `square`) is "a board that the tool does not offer" and loads the default with the notice. The geometry and Wythoff functions throw `NeedsTwoWayRoads` on a one-way board and `NotFiniteType` on every other non-finite board: a link must never get them called; this is a check before the call, not an error to catch and display.
- Named finite boards carry `SafeInt`; ring vectors and the positions of their orbits are small integers.

### 5.3 Input: rings and the root polytope shortcut (SPEC 4 T10 Input, 2.14 Root polytopes)

- "a board and a non-negative integer on each node (click to ring)". The ring board is `Board.svelte` with `values = rings` (label order equals position order on the 32 boards; convert anyway, 5.14), `game: 'firing'`, `canAct` all `true`, `name` an accessible name such as `Rings on B3`. `onAct(position)` on an unringed node sets its ring to 1; on a ringed node it unrings it (plan: a toggle). Every non-negative integer is reachable without a mouse: the "show as table" view (A-10) has a number input per node, and two buttons raise and lower the ring of the focused node (plan; record both). Values show the sign encoding of 6.3 (positive filled, zero outlined neutral); there are no negatives.
- The shortcut "root polytope": a button that sets `rings = toNumbers(board, highestRoot(board))`, which equals `types[T].numbers_of_highest_root` (the table of 2.14: $A_n$ 1 on nodes 1 and $n$, for $A_1$ 2 on node 1; $B_n$, $n\ge3$, 1 on node 2; $B_2$ 2 on node 2; $C_n$ 2 on node 1; $D_n$, $E_6$ 1 on node 2; $E_7$ 1 on node 1; $E_8$ 1 on node 8; $F_4$ 1 on node 1; $G_2$ 1 on node 2). "'The root polytope' on the site therefore means the orbit of $\theta$, with the short roots available as a second set of points": on $B$, $C$, $F$, $G$ the shortcut also offers "show short roots", which adds the orbit of `toNumbers(board, highestShortRoot(board))` (equals `numbers_of_highest_short_root`) as a second set of points with a distinct marker and a legend entry; they lie inside the hull (midpoints on $B$, $C$, $F$; one third of a sum on $G_2$) and get no edges of their own (plan). On simply laced boards `highestShortRoot` is `null` and the option is absent. The option is not a link field; it is off when a link opens (6.6).
- All-zero rings give an orbit of one point: draw it and say so in the caption (plan); never throw.

### 5.4 Output: points, edges, face table (SPEC 4 T10 Output, 2.14 Orbit polytopes, 5.4)

- Vertices: "the orbit of $a$ under free play of the numbers game": `orbitGraph(board, [rings], 'firing', cap)` gives `items` (positions in numbers coordinates), `parent`, `node`, from which `wordTo(graph, index)` gives a shortest word to every vertex (5.7 needs it). Their number is known before enumeration: `orbitSize(board, rings)` $=|W|/|W_U|$, $U$ the unringed nodes, which equals `wythoffFVector(board, rings)[0]`.
- Coordinates: 2.14 item 4, "A position $a$ of the numbers game is drawn at $y=E\,C^{-1}a$". Build the float matrix $P=E\,C^{-1}$ once per board with engine calls (`euclideanBasis(board).E` and `inverse(cartanNumbers(board))` as rationals turned to floats, or `toPopulation(board, a)` per vertex) and set $y=Pa$; never $y=Ea$ (for the root polytope the two agree only because $C^{-1}(C\theta)=\theta$). No matrix inversion is written in the component (7.3: "Components contain no mathematics beyond calling the engine").
- Edges: "edges by the rule of section 2.14 (`wythoffEdges`)": `wythoffEdges(board, rings, CAPS.edgesAtRest)` returns pairs of positions; map each to vertex indices with a `Map` keyed by the entries joined as decimal text (the engine's `show`). Their number is known before enumeration: `wythoffFVector(board, rings)[1]`.
- Face table: "the table of face counts by type (`wythoffFaceTypes`)": one row per face type $K$ ("a set $K$ of nodes such that every connected component of $K$ contains a ringed node"), showing $K$ as labels (`toLabels`), the dimension $|K|$, and the count $|W|/(|W_K|\,|W_{K'}|)$ as the engine's `bigint` in full digits (the largest here is 3628800, below the 12-digit rule of 4.0). Group rows by dimension and show the per-dimension totals, which equal `wythoffFVector`. The empty set is a face type (its row is the vertex count); the full node set has count 1 and is the polytope itself: show or hide that last row consistently, knowing that the golden `f_vector` has $n$ entries (dimensions 0 to $n-1$; `verify.py` stores `f[:n]`). Optionally name the type of each face's sub-board with `identify(subBoard(board, K))` (plan).
- The caption and `data-out` summary state the counts: on $B_3$ with rings `(1,0,1)`: 24 vertices, 48 edges, 26 faces (M7 beat 3), all computed.

### 5.7 Make uniform (SPEC 4 T10 Make uniform, 2.14 Edge lengths, 2.5)

- "the engine keeps, for every vertex, a shortest word from the start (`orbitGraph`, `wordTo`); the tool replaces the start by the real vector with $a_i=c/\sqrt{d_i}$ on the ringed nodes and replays those words in floating point (`applyWordFloat`)." $d=$ `symmetrizer(board)` as floats ($B_3$: $(2,2,1)$; $C_3$: $(1,1,2)$; $G_2$: $(1,3)$; $\min d_i=1$). $c>0$ is a constant (plan: choose it so that the picture keeps its size, for example $c$ equal to the largest ringed integer; record). - Display only; off by default; not a link field (a link opens with it off). ## 9. Traps

- "'The root polytope' means the orbit of $\theta$; short roots are a second set of points inside the hull (2.14)." On $B$, $C$, $F$, $G$ the hull of all roots is the orbit of $\theta$ alone; the short roots are extra points, not extra vertices. (roster)
- "On $A_3$, $A_5$, $A_7$, $B_3$, $B_6$, $D_4$ to $D_8$, $E_6$ roots coincide in the Coxeter plane; the tool must say the number of distinct dots (2.14)." (roster)
- "Rotation must have button and key equivalents (A-8); any continuous rotation has a pause control and respects reduced motion (A-9)." (roster)
- The orbit from `orbitGraph(board, [rings], 'firing', cap)` is in numbers coordinates; the drawing coordinate is $y=E\,C^{-1}a$ (2.14 item 4), never $Ea$. The two agree only for the root polytope, where $C^{-1}(C\theta)=\theta$; a mistake here passes the ring test and fails every other picture.
- $\Lambda^{1/2}$ is inside `euclideanBasis`'s $E$ (2.14: "The factor $\Lambda^{1/2}$ matters"). Do not rebuild $E$ from eigenvectors in the tool, and do not rescale coordinates before computing ring radii: the golden radii are absolute.
- Golden `f_vector` has $n$ entries (dimensions 0 to $n-1$; `verify.py`: `f[:n]`); the oracle's `wythoff_f_vector` returns $n+1$ with `f[n] = 1`. Check what `P4-A1`'s `wythoffFVector` returns before comparing by index.
- The empty set is a face type: `induced_components([])` is empty, so the oracle's `any(...)` is false and mask 0 is kept; its count $|W|/|W_U|$ is the vertex count. Do not drop it from the table, and do not count the full-set row (count 1) among the faces when comparing with `f_vector`.
- `wythoffFaceTypes` nodes are positions (E-7); the oracle's are 1-based. Convert once with `toLabels`.
- The roster's e2e example "the message above 70000 edges on a 2_41 configuration" contradicts the golden file: $2_{41}$ has 69120 edges and `edges_enumerated: true`; only $1_{42}$ (483840 edges) exceeds the cap. Test the message on $1_{42}$ and the full drawing on $2_{41}$ (69120 edges at rest, 8000 while turning).
- Decide from exact counts, never from truncation: `orbitSize` and `wythoffFVector` are exact and cheap. An enumeration that runs into a cap is a bug in the decision, not a way to find the limit.
- Rounding for distinct dots: `(-1e-9).toFixed(6)` is `"-0.000000"`, a different key from `"0.000000"`. Use `Math.round(x * 1e6) / 1e6 + 0` and `String`, as the oracle's `round(x, 6) + 0.0`.
- Move graph: every node $i$, not only the ringed ones, and no edge where $\mu_i=0$; deduplicate sorted pairs; `orbitGraph` stores only the first way each position was reached (5.4), so the move edges must be derived "once more".
- Edge colours by label from the palette of eight, never colour alone (6.3, A-5): every coloured edge carries its node label as text, on every graph size; a legend and the table view come in addition, not instead. Thinning the labels on large graphs is a deviation, not a plan choice.
- A-12: KaTeX never reaches the client (7.6, RT-07). Board names come from `names.json`; the golden polytope names (`2_21`, `4_21`, ...) are raw text in the golden file and must be turned into MathML, not shown as `4_21`. A name inside an `aria-label` or on the canvas is plain words.
- 7.6 long tasks: a 2000-item enumeration plus the face table plus a move-graph derivation in one synchronous handler can add up past 50 ms on a slow phone even when each is small; run them as separate tasks (plan: yield between them) and keep the worker for anything above 2000 items.
- `r` is dot-separated (`r=1.0.1`) while `s` and `d` are comma-separated; `j=xyz:1,2,3@30,20,0` has commas and an `@`. The codec assembles and parses these; never URL-encode them away, never parse them yourself.
- Coordinates in `xyz:` are counted from 1; the Coxeter plane is coordinates 1 and $n$ (rows `E[0]` and `E[n-1]`).
- $A_1$ has no `coxeter_plane` key (rule 7) and no Coxeter option; it is two points and one edge. "Rank 2 flat" means no turning controls at all.
- The ring board is a `Board.svelte` showing numbers-game values (`data-board="numbers"`); a click changes a ring, it is not a game move: no "Fired node", no "Game over", no legality.
- Positions against labels: $1,\dots,n$ in position order hides a stray `+1` on every board this tool offers.
- A link naming a custom or affine board must never reach the geometry functions (`NotFiniteType`, `NeedsTwoWayRoads` are errors to prevent, not to catch and show). Check the name against the 32 before any call.
- Svelte 5 runes only; `onclick` not `on:click`; snippets not slots; nothing touching `window`, `document`, `fetch`, `OffscreenCanvas` or `devicePixelRatio` runs during server rendering; the canvas is drawn in `$effect` after hydration; the snapshot path must run in Node through `svgScene.ts`.
- Astro 7: `astro build` then `astro preview` (7.2 item 9); the preset URL is built from `import.meta.env.BASE_URL` (the `BASE_PATH=/sub/path/` build of `P0-A6`'s `basepath.spec.ts` catches a leading slash).
- A link equal to a precomputed configuration (`g=E8&r=0.0.0.0.0.0.0.1`) fetches the preset file; it does not compute. Compare board and rings, not the `preset` prop.
- `bigint` crosses `postMessage` only through `engineCall`'s `{"$big": "..."}` serialisation; face types are cheap ($2^n$ masks), so compute them on the main thread and send only enumerations to the worker.
