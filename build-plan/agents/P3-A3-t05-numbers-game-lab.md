### 5.6 The wave (SPEC 4 T5 "Wave"; F8; SPEC 5.3 `bipartition`, 5.4 `wavePlay`)

- Verbatim: "**Wave**: fires one colour class per step and counts rounds."

Every firing is legal and the game ends after exactly $h$ rounds, whichever colour starts (on $A_3$: 4 rounds, 6 moves). On $A_1$ one colour class is empty and the statement degenerates to a single move."

### 5.8 Dimension calculator (SPEC 4 T5 "Dimension calculator"; F9; A.3; SPEC 5.4 `weylDimension`; E-4)

## 9. Traps

- Roster: "The tally bars are read sideways: the conjugate partition gives the exponents (F7)." The exponents are not the distinct fired values and not the bar lengths; they are, for $r=1,\dots,n$, the number of values fired at least $r$ times, sorted ascending (oracle `exponents_from_fired`). On B3 the tally `{1: 3, 2: 2, 3: 2, 4: 1, 5: 1}` reads to `1, 3, 5`. Call `exponentsFromFired`; do not reimplement it in the component.
- Roster: "Two games compared: the tapes agree after sorting, not in order (F3)." On A3 the two preset orders happen to fire the same sequence; G2 shows the difference. A test on A3 alone would not catch an unsorted comparison.
- Roster: "The dimension is a quotient of two products of bigints; never floats." The E8 product from all ones has 107 digits; `Number` loses it silently. Use `bigint` products and the engine's `weylDimension`.
- The reading sideways belongs to the finished game from all ones only. From $\omega_i$ the fired values are small (on E8 from $\omega_1$ only 1 and 2, 78 moves), and reading that tally as exponents is wrong.
- The wave on A1: the oracle's `wave_play` counts an empty round when the empty class goes first (2 rounds, verify.py line 207). The tool must say "a single move", not "2 rounds" and not "h = 2 rounds".
- Colour class 0 holds the first position of each component (label 1 on every named type); a test that expects class 0 to be the odd labels fails on E8, where `bipartite_colouring` is `[0, 1, 1, 0, 1, 0, 1, 0]`.
- Within a wave round the nodes fire in increasing position, one engine `fire` each; the class's nodes are not joined, so the order does not change the result, but the moves list and the history must hold them in that order to match `wavePlay().word`.
- Sort tally values numerically. JavaScript `sort()` without a comparator sorts `10` before `9`; `Object.keys` of the golden `fired_tally` keeps insertion order, which is numeric there, but your map must not depend on that.
- `fired` holds the number before the firing (positive in legal play), not the number after it (its negative).
- `weylDimension` takes `lambda` as numbers in label order, which for a named finite type equals position order; `highest_weight` in the golden file is in label order too. Do not add $\rho$ yourself before calling it: the engine function takes $\lambda$, as the oracle does.
- A non-dominant $\lambda$ makes $\lambda+\rho$ non-positive somewhere along the word and the oracle's assertion fails; never call `weylDimension` with a negative entry.
- Wording: "heights of coroots" (F6, `SOURCES.md` 11.5). On $B_2$ the tape `1, 3, 2, 1` contains a 3 where the roots have heights 1, 1, 2, 3; sorted they coincide only because a board and its reverse share exponents (A.1).
