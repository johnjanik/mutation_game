### 5.2 `golden.ts`: the path grammar

Signature (CONTRACTS 4): `export function resolveGoldenPath(path: string): unknown`. It is the one resolver, shared with `<Tex>`; no second parser anywhere.

- Steps are separated by dots. A step is one of:
  - a key of an object: `types.E8` (two steps); object keys may contain spaces (`heaps.A4 omega_2.moves`) and may be digit strings (`affine_names.2`, `types.E8.fired_tally.1`), which are object keys, not indices;
  - a key followed by a zero-based index into a list: `positive_roots[0]`, so `types.A2.positive_roots[0]` resolves to `[0, 1]`;
  - a key followed by a selection from a list of records, written `[field=value;field=value]`, where each value is taken literally up to the next semicolon or closing bracket and compared with the field as text; a field that holds a list of integers is compared as its entries joined by commas with no spaces. Examples that must resolve: `satake[dynkin_type=E6;real_form=e6(-14)].dim_k` (46), `folding[type=D4;order=3].folds_to` (`"G2"`), `wythoff[type=F4;rings=1,0,0,0].f_vector` (`[24, 96, 96, 24]`).
- Text comparison (plan where the specification is silent): an integer field compares as its decimal digits (`order=3`); a string field as it stands (`real_form=e6(-14)`, hyphen included); a list field as its entries joined by commas with no spaces, each entry rendered by this same rule (`rings=1,0,0,0`); a boolean as `true` or `false`; `null` as `null`. A record that lacks the field does not match.
- A selection must match exactly one record. The path must lead to exactly one value. Otherwise throw `GoldenPathError` whose message begins `path <path> resolves to <n> values` with the path as written and `n` the count (CONTRACTS 4: `GoldenPathError("path ... resolves to N values")`). An unknown key, an index out of range, an index applied to something that is not a list (`affine_names[2]`: the keys of `affine_names` are digit strings, so `affine_names.2` is the path), a selection on something that is not a list and a key applied to something that is not an object all give `n = 0`; a selection matching several records gives their number (`folding[type=D4]` resolves to 2 values; `wythoff[type=F4]` also 2). You may append one further sentence naming the failing step (plan).
- Malformed syntax (an empty step, a bracket that does not close, a step that starts with `[`, a non-integer or negative index, chained brackets such as `cartan[0][1]`, which the grammar does not allow) also throws `GoldenPathError` with a message naming the step (plan). The grammar is exactly the three step forms above; do not extend it.
- Surrounding whitespace of the whole path is trimmed (plan); whitespace inside a step is significant because object keys contain spaces.
- `GoldenPathError extends Error` with `name = 'GoldenPathError'` and the fields `path` and `count` (plan).

### 5.3 `golden.ts`: output formatting

Signature (CONTRACTS 4): `export function formatGoldenValue(v: unknown, as?: 'word' | 'count' | 'plain'): string`.

- An integer is printed in decimal digits with a true minus sign, U+2212 MINUS SIGN, never the ASCII hyphen-minus; its digits are grouped in threes from the right by narrow no-break spaces, U+202F, when it has five digits or more. So `696729600` prints as `696 729 600` (the separators being U+202F), `51840` as `51 840`, `10000` as `10 000`, `9999` as `9999`, `-1` as `−1`, `-14` as `−14`. Count digits without the sign.
- A list of integers is printed as its entries separated by commas, in round brackets. Each entry follows the integer rule above (plan: grouping and the minus sign apply inside lists; the separator is a comma followed by one ordinary space, so `[24, 96, 96, 24]` prints as `(24, 96, 96, 24)` and `[-1, 1]` as `(−1, 1)`). (plan) A list of strings, such as `affine_names.2`, follows the same rule with each string as it stands: `(A1~, A2^(2))`.
- A string is printed as it stands: `"G2"` prints `G2`; `"e6(-14)"` keeps its hyphen; the decimal strings of `bigint_test` print with no grouping and no U+2212, because they are strings (this follows from the rule; note it in a comment).
- `as="word"` prints a list of node labels separated by thin spaces, U+2009 THIN SPACE: `types.A2.longest_word`, which is `[1, 2, 1]`, prints `1 2 1` with U+2009 between the digits. The labels are printed as found; the golden file already holds labels (E-7, Appendix G).
- `as="count"` prints the length of a list, formatted as an integer: `types.E8.positive_roots` with `as="count"` prints `120`.
- `as="plain"` prints an integer without grouping (`696729600`) or a list without brackets (`24, 96, 96, 24`).
- Anything else (plan): a boolean, `null`, a floating-point number (only the ring radii), an object, a list that contains a list or an object, `as="word"` or `as="count"` on a value that is not a list, throws `GoldenPathError` with a message that says what was found and suggests `<Tex>` or a table. The build then fails, which is the intended way for an author to learn that the value is not for prose.
- Do not use U+00A0 NO-BREAK SPACE anywhere, and do not confuse the two spaces: U+202F between digit groups, U+2009 between the labels of a word.

Also export the TeX helper used by `<Tex>` (plan name): `export function substituteGoldenInTex(src: string): string`. It finds every `{{path}}` in `src` (the two braces, the path, two braces; whitespace just inside the braces is trimmed), resolves each with `resolveGoldenPath` (same paths, same failure when one does not resolve) and replaces it with the value in TeX form: an integer in decimal digits with the ASCII hyphen-minus for the sign (KaTeX sets it as a minus) and its digits grouped with `\,` (7.3) from five digits, the same threshold as in prose (plan: 7.3 fixes only the separator), so `{{types.E8.weyl_order}}` becomes `696\,729\,600` and `{{types.F4.weyl_order}}` stays `1152`; a list as its entries separated by `, ` in round brackets with the same rule per entry (plan); a string as it stands; anything else throws `GoldenPathError` (plan). A `{{` without a matching `}}` throws `GoldenPathError` naming the `src` (plan). The source is otherwise passed through unchanged, backslashes included.

### 5.4 `G.astro`

It fails the build unless the path leads to exactly one value: call the resolver in the frontmatter with no `try`; a thrown `GoldenPathError` aborts `astro build` with a non-zero exit, and the message names the path.

### 5.8 `unverifiedRegistry.ts` and `Unverified.astro`

Build mode:

- A preview build is the default (`npm run build`); a release build is `RELEASE=1 npm run build` (7.3; 7.7). (plan) `isReleaseBuild()` returns `process.env.RELEASE !== undefined && process.env.RELEASE !== ''`, read at call time, never cached at import time, so that a test can set and unset it. Any non-empty value counts, `0` included; the documented form is `RELEASE=1` (7.3; 7.7; CONTRACTS 1, `build:release`).

`Unverified.astro`:

- Usage: `<Unverified item="E4" fallback="..."> ... </Unverified>`. It wraps any sentence that rests on an open item of Appendix E, named by its number there. Props: `item` (required), `fallback` (optional). Children are the wrapped sentence.
- Preview build, every item, open or closed: "A preview build (the default) renders the wrapped sentence with a visible mark that links to the item on the page `open-items`" (7.3). The rule has no condition on the status, so a closed item is marked in a preview too; follow it literally. (plan) Markup: `<span class="unverified" data-unverified="E4"><slot /> <a class="unverified-mark" href="<base>open-items#E4" title="Rests on item E4 of Appendix E; see its status on the open-items page">[unverified E4]</a></span>`. The mark text and title are the same for an open and a closed item (plan), because the page `open-items` shows the status. If you think a closed item should render unmarked in a preview, do not build it: record it in your fragment and under `deviations` in your report as a proposal for `MERGE` and the owner (COMMON 4.4). The `<base>` is `import.meta.env.BASE_URL` joined with one slash; the anchor is the item id (plan: P1-A4 gives each item `id="<id>"` on the open-items page; put this in your fragment). Inline elements only: Astro 7's compiler rejects invalid HTML, and the sentence sits inside a paragraph.
- Release build, closed item: render the sentence unmarked, that is, the children alone with no wrapper and no mark.
- Release build, open item: render the `fallback` text in its place, as escaped text (plan: inside `<span class="unverified-fallback" data-unverified="E4">`), or nothing at all when no fallback is given. A fallback is a weaker sentence that stays true however the item turns out, for example "computed for every board of rank at most 8" in place of a statement about what a book says; quote this example in a comment so that lesson authors see it.
- A release build never fails because of an open item. The component throws nothing in either mode (roster: "never fails the build"). (plan) An `item` that is not in `unverified.json`, or does not match `E<digits>`, is treated as open: in a preview build the mark reads `[unverified <item>, not in unverified.json]`; in a release build the fallback or nothing is shown; the report lists it under `unknownItems`. This lets a lesson agent use `E18` before `MERGE` has added it (README 3.2) and makes a typo visible in every preview.
- Every usage is registered: `registerUsage(item, Astro.url.pathname)` in both modes (plan: `Astro.url.pathname` is the page identifier).

`unverifiedRegistry.ts` (plan API):

```ts
export type UnverifiedStatus = 'open' | 'closed';
export interface UnverifiedItem { id: string; status: UnverifiedStatus; statement: string; whereToCheck: string; gate: string; closedOn?: string; closedBy?: string; }
export function isReleaseBuild(): boolean;
export function itemById(id: string): UnverifiedItem | undefined;
export function decide(item: string, release: boolean, hasFallback: boolean): 'marked' | 'plain' | 'fallback' | 'nothing';
export function registerUsage(item: string, page: string): void;
export function reportPath(): string;          // <reports dir>/open-items-report.json; the .md report sits beside it
export function currentReport(): OpenItemsReport;
export function writeReport(): void;           // writes both files from the current map; a no-op in a preview build
export function openItemsReportIntegration(): AstroIntegration; // (plan) the build-start hook described below
```

- `decide`: preview → `'marked'` for every item, open, closed or unknown (7.3: the preview rule is unconditional; roster: "preview build (RELEASE unset): renders children with a visible mark linking to /open-items#E4"); release and closed → `'plain'`; release and open or unknown → `'fallback'` when a fallback is given, else `'nothing'` (7.3).
- The report (7.3: "it prints a report of the open items and the pages that use them, which the owner reads at each release"; 7.7: "a release build prints the report of open `<Unverified>` items"). (plan) The registry keeps a module-level map from item id to the set of pages. In a release build, and only then, it writes two files under the reports directory: `reports/` at the repository root (found by walking up from `process.cwd()` to the first directory containing `reference/golden_data.json`; create `reports/` if absent; the directory is gitignored except `gate-*.md`), or the directory named by the environment variable `OPEN_ITEMS_REPORT_DIR` when it is set (plan: your fixture builds and unit tests set it to a temporary directory, so that a test never overwrites the owner's release report). The report is written once per release build whether or not any page uses `<Unverified>`, because SPEC 7.3 says "A release build never fails because of an open item; it prints a report of the open items and the pages that use them" and 7.7 "a release build prints the report of open `<Unverified>` items", and G3 and G6 (9.1) need it from a release in which no page wraps a sentence (all of phase 0); P0-A6's `report.mjs` exits 1 when no release report exists. Mechanism (plan): `openItemsReportIntegration()` returns an Astro integration whose `astro:build:start` hook, in a release build, calls `writeReport()` with an empty map, so that both files exist and list all seventeen items with empty `pages` before any page renders; then, after every registration in a release build, the registry rewrites both files from its map. A build-start baseline is used rather than `astro:build:done` because the integration runs in the config's module instance, which does not see the map of the bundled server code. If you find that the registrations of one build run in more than one module instance, merge with the pages already in the file written by the same build (identified by a build id that the hook puts in `process.env.OPEN_ITEMS_BUILD_ID`) instead of overwriting them, and record it. You may not edit `site/astro.config.mjs` (section 7): write a request to `MERGE` to add `openItemsReportIntegration()` to its `integrations`, and in your fixture builds pass the integration through the inline configuration of Astro's `build()` (5.12). Until `MERGE` adds it, a release build of a site with no `<Unverified>` writes no report; say so in your report. In a preview build the registry writes no file and leaves any existing report untouched (plan: otherwise a later `npm run build`, such as the CI build or a merge check, would overwrite the release report that the owner reads at each release, and `report.mjs` refuses a preview file). The two files are: `reports/open-items-report.json`, machine-readable, for `scripts/report.mjs` and your tests, and `reports/open-items-report.md`, the same content as a short Markdown table, which is the form the owner reads at each release (7.3; 9.1 G6: "its report of open items is attached to the pull request (or left in `reports/` where there is none)"). The JSON holds `{ mode: 'release', generatedAt, items: [{ id, status, gate, pages: string[], fallbackShown: boolean }], unknownItems: [{ item, pages }] }` with every item of `unverified.json` listed, used or not. In a release build the registry also prints one line per new (item, page) pair to standard error, `open item E4 used on /modules/m1-mutation/ (fallback shown)` or `(nothing shown)`, through `console.warn` with a comment that this is the release report of SPEC 7.3 and runs only in Node at build time (COMMON 4.4 forbids stray `console.log` in shipped code; this is neither stray nor shipped). In a preview build nothing is printed and nothing is written. (`mode` stays in the JSON, always `release`, because `report.mjs` checks it.) `scripts/report.mjs` (P0-A6) copies or prints this file; tell P0-A6 and `MERGE` the path in your report under `requests`.
- Never write into `reference/`, `site/src/content/unverified.json` or `DECISIONS.md` from the registry.

## 9. Traps

- Selection values are compared as text; a field holding a list of integers is compared as its entries joined by commas with no spaces (`1,0,0,0`), not as `[1, 0, 0, 0]` and not as `1, 0, 0, 0` (roster).
- A release build must never fail because of an open item (SPEC 7.3). It prints a report instead. Do not let `<Unverified>` throw for an unknown id either; mark it and report it (roster; 5.8).

- The sources page (phase 1) renders `SOURCES.md` as Markdown, not MDX; your parser must not depend on MDX or any Markdown library (roster).
- `SOURCES.md` defines keys in three positions: at a paragraph start, in a list item, and mid-line after another entry (`**[Car14]** … **[Car26]**`). A regex anchored at the line start, even one that allows the list marker `- `, misses the twelve mid-line keys. The labels `[S]`, `[S2]`, `[V]`, `[U]` of 11.0 are never bold, but exclude them anyway, together with `[D]` of `SPEC.md` 0.3 (plan). - U+2212 (minus) in HTML text, ASCII `-` in TeX source; U+202F between digit groups in HTML, `\,` in TeX; U+2009 between the labels of a word. Never U+00A0. Grouping starts at five digits: `9999` stays, `10000` groups.
