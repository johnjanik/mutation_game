## 5. Requirements

### 5.1 The state object (`state.ts`; SPEC 6.6, 7.4, 4.0)

- Types exactly as CONTRACTS 4: `ToolId = 'board'|'garden'|'form'|'lab'|'numbers'|'mirror'|'symbolic'|'weyl'|'kostant'|'geometry'|'fold'|'rep'|'satake'|'atlas'|'affine'|'sandbox'` (the ids of the table at the head of SPEC 4); `BoardSpec = string | { cartan: number[][]; xy?: [number, number][] }`; `ToolState` with `schema: 1`, `tool`, `board`, and the optional `view`, `mode`, `coords`, `start`, `moves`, `black`, `tau`, `rings`, `projection`, `graph`, `symmetry`, `node`, `relation`, `lambda`.
- 6.6 field table: `schema` is 1; `board` is "a type name (`"E8"`), an affine name (`"B3~"`, `"D4^(3)"`), a preset (`"pentagon"`, `"square"`), or `{"cartan": [[2,-1],[-3,2]], "xy": [[0,0],[1,0]]}` for a custom board (`xy` optional)"; `view` is `populations`, `numbers`, `linked`; `mode` is `free`, `legal`, `raising`; `coords` is `populations` or `numbers`, "**which game `start` is a position of**. Required whenever `start` is present."; `start` is "integers, one per node, in the order of the board's labels", default "all ones for numbers, one Martian in the first city for populations"; `moves` are node labels.
- Integers in `start`: JSON numbers when they are safe integers, decimal strings otherwise (CONTRACTS 4: "JSON numbers when safe integers, else decimal strings (same rule as data export)"). `lambda` is `number[]` in CONTRACTS 4 and does not take decimal strings: a `d` entry that is not a safe integer does not parse (rule 1) (plan, so that the contract type holds). `moves`, `black`, `tau`, `rings`, `symmetry`, `node` hold labels or small integers and are numbers.
- Tool-specific fields, verbatim from 6.6: "`black` and `tau` (T13: labels of black nodes; the images of all nodes); `rings` and `projection` (T10: one non-negative integer per node; `coxeter` or `xyz:1,2,3`, either with three turning angles); `graph` (T10: `polytope` or `moves`); `symmetry` (T11: the images of all nodes); `node` and `relation` (T12); `lambda` (T5 dimension calculator). Options that are not listed here (the growth mode of T2, the weights typed into T3, the tab of T5, T11 or T15, the root chosen in T13, a rotation of T10 in a coordinate plane beyond the three turning angles) are not part of a link in schema 1; a link opens the tool with those at their defaults." So `ToolState` holds no field for those options, `encodeState` and `history.ts` never write them, and `decodeState` never reads them (a key for them is an unknown key and is ignored). A tool keeps such options in its own component state, outside `ToolState`.
- Instances, verbatim from 6.6: "Every tool placed on a page has an instance id, set by the page author (`id="b2"`) and unique on the page. A page holds one state object per instance." Uniqueness is enforced in `history.ts` (5.6).
- **Positions are never part of the state** (7.4: "Positions are never part of the state; they are recomputed from the start and the moves. A link can therefore never show a position the rules do not allow."). No field of `ToolState` may hold a position.
- Labels everywhere outside the engine (E-7): `start` is in label order, `moves` are labels; convert with `toPositions` and `toLabels` only, never with `+ 1` or `- 1`. Labels start at 0 on affine boards (phase 2); write nothing that assumes 1.
- `defaultState(tool, board)`: `{ schema: 1, tool, board }` plus `coords`, `start` and `moves: []` for the game tools. Plan: `coords: 'populations'` with one Martian in the first city (the entry 1 at the first label, 0 elsewhere) for `board`, `garden`, `kostant`; `coords: 'numbers'` with all ones for `numbers`, `symbolic`, `weyl`, `mirror`, `affine`, `sandbox`; T9 also gets `view: 'populations'`, `mode: 'raising'`. Export `defaultStart(board, coords)` (plan) so that tools and the codec share the rule. A tool's own defaults (from its props and presets) always override these; `defaultState` is the fallback for a tool route.
- `resolveBoard(spec)` (CONTRACTS 4): a name that `boardFromName` knows as a finite type gives that `Board<number>` with `SafeInt`; everything else gives a `Board<bigint>` with `Big` (E-2: "named finite-type boards use `SafeInt`; **every other board** (custom boards, affine boards, the sandbox) uses `Big`"). A custom matrix is checked with `boardKind` first: `not-a-board` throws `NotABoard`; more than 12 nodes throws (plan: `RangeError` with the message `board has more than 12 nodes`; 5.6 "Nodes of a custom board: 12"). A custom board is `Big` even when its matrix equals a named type's, keeps `name` undefined, and has labels $1,\dots,n$ "in order of creation" (E-7 table). `fromAdjacency` takes $A$ with $C=2I-A^{\mathsf T}$, so pass $A_{ij}=-C_{ji}$ off the diagonal; if it returns a `SafeInt` board for a matrix of a named type, convert it with `bigBoard`. An unknown name throws (`NotABoard` from `boardFromName`). Names of phase 2 (`B3~`, `D4^(3)`, `pentagon`, `square`) throw until `P2-A1` extends `boardFromName`; your code must need no change when it does.
- `bigBoard(board)` (plan, requested by `P1-A5` and `P1-A7`): the same board with `arith: Big`, entries as `bigint`, the same `labels`, `kind` and `name`. It serves T1's rule (SPEC 4 T1): "On a named finite-type board a link whose start or play leaves the safe range of `SafeInt` is reloaded with `Big` arithmetic, with no message."
- `positionsOf(state)`: the start and every position after each move, recomputed by the engine, in the game of `coords` (`populations`: `mutate`; `numbers`: `fire`), entries serialized by the integer rule above. It is a synchronous function for move lists that E-9 lets run on the main thread; the worker exposes it too (5.4) for longer lists. 7.4: "While a tool runs it keeps the list of positions of the current play in memory and extends it by one position per move, so a move costs one engine call however long the play is." `positionsOf` is for loading; say so in its doc comment.
- Linked tools (plan, because `P1-A5` and `P1-A6` look for it on `main`): 7.4 "Two tools share state only when the page says so with a `linkTo` property". Provide `publishToolState(instanceId, state)` and `followToolState(instanceId, onChange): () => void` on a Nano Store `map` keyed by instance id, holding `ToolState` only (never positions). Record the API in your fragment so that `P1-A5`, `P1-A6` and later tools reuse it. A follower receives the leader's `ToolState` (never positions) on every publish and recomputes its own positions; the function returned by `followToolState` stops the updates. Tested in `state.test.ts` > `publish and follow` (section 6).

### 5.2 Encoding (`urlCodec.ts`; SPEC 6.6 "URL form")

- `encodeState(state, opts?: { prefix?: string }): string` returns a query string without `?`. Keys and values, verbatim from 6.6: "`z` schema, `g` board, `v` view (`p`, `n`, `l`), `m` mode (`f`, `l`, `r`), `c` coords (`p`, `n`), `s` start, `w` moves, `x` black nodes, `t` tau, `r` rings, `j` projection, `e` graph (`p`, `m`), `y` symmetry, `k` node, `q` relation, `d` lambda."
- Order of keys (plan, for a stable round trip): `z g v m c s w x t r j e y k q d`, `z=1` first, a key written only when its field is present. The 6.6 example must come out exactly: the E8 state of 6.6 encodes to `z=1&g=E8&v=l&m=l&c=n&s=1,1,1,1,1,1,1,1&w=1.2.3.1`.
- Values (6.6 table): `g` "a board name (`E8`, `B3~`, `D4^(3)`, `pentagon`), or `c:` and the rows of the Cartan matrix, entries separated by commas and rows by semicolons, optionally followed by `@` and the grid coordinates of the nodes written the same way (`c:2,-1;-3,2@0,0;1,0`)"; `s`, `d` "one integer per node in label order, separated by commas"; `w` "node labels in the order played, separated by dots; empty for no move"; `x` "the labels of the black nodes, separated by dots; empty for none"; `t`, `y` "the image of every node, in label order, separated by dots"; `r` "one non-negative integer per node in label order, separated by dots"; `j` "`coxeter`, or `xyz:` and three coordinate numbers counted from 1 (`xyz:1,2,3`); either may be followed by `@` and three whole numbers of degrees, the turn of the picture about its horizontal, vertical and viewing axes (`xyz:1,2,3@30,20,0`)"; `k` "one node label"; `q` "a relation code of section 5.2 with its node labels: `ef:1,2`, `serre-e:2,3`". Satake example: `x=2.3.4.5&t=1.2.3.4.5.6`.
- "The query string is assembled by hand, so that commas, semicolons, dots, `~` and `^` stay readable". Never pass the whole string through `URLSearchParams.toString()` or `encodeURIComponent`. Escape only the characters that would break a query (`&`, `=`, `#`, `%`, `+`, space), which no valid value contains.
- Prefix: "On a tool's own route (`/tools/...`, `/embed/...`) the keys are bare. On a lesson page each key is prefixed by the instance id and a dot (`b2.g=A3&b2.w=1.2`), and only instances the reader has changed are written." `opts.prefix` is the instance id followed by a dot (`'b2.'`, as `P1-A5` passes it); accept `'b2'` too and add the dot (plan). An empty or absent prefix gives bare keys.
- "A link carries no site version": no version, commit or date in the query.
- Only the sixteen fields of the key table are encoded; the options 6.6 excludes from schema 1 (5.1) are never written, whatever the caller passes.
- Integers above $2^{53}$ in `start` are written as their full decimal digits.

### 5.3 Decoding and validation (`urlCodec.ts`; SPEC 6.6 "Validation")

- `decodeState(search, tool, defaults, opts?: { prefix?: string }): { state: ToolState; notice: string | null }`. Parse with `URLSearchParams` (6.6: "and is parsed with `URLSearchParams`"); accept `search` with or without the leading `?`.
- "A key that is absent keeps the value the page author configured for that instance (on a tool's own route: the tool's default), so a link changes only what it names." The result is `defaults` with the link's fields applied over it.
- When `g` names a board other than the defaults' board, absent `s` and `w` take the defaults of the tool for the new board (`defaultStart`, empty moves), as a picker does (4.0: "A picker changes `board` and resets `start` and `moves` to the tool's defaults for that board") (plan). When `c` is present without `s`, `start` becomes `defaultStart(board, c)` (plan). Record both in your fragment.
- "The codec validates everything it reads. An unknown key is ignored." Keys of other instances, and prefixed keys on a tool route, are unknown keys.
- On any failure the whole instance loads `defaults` and `notice` is the notice; nothing of the link is applied, never a partial play. Plan wording (the specification fixes only the meaning, "show a notice that the link could not be read"): export `LINK_NOTICE = 'The link could not be read, so the tool shows its default state.'`. Tools show it in `data-out="notice"` (through `ToolFrame`'s `notice` prop, 5.7).
- The failures, verbatim from 6.6, each with its own test (6.1 lists the tests):
  1. "a known key with a value that does not parse";
  2. "a board that is `not-a-board` or has more than 12 nodes";
  3. "a `g` parameter longer than 512 characters";
  4. "a start with an entry longer than 40 digits";
  5. "more than 20000 moves";
  6. "a move that the mode in force forbids at that point of the play";
  7. "a `t` or `y` that is not a symmetry of the board, or a `t` whose square is not the identity";
  8. "a board that the tool does not offer (section 4)";
  9. "a list (`s`, `d`, `r`, `t`, `y`) whose length is not the number of nodes";
  10. "a label in `w`, `x`, `k` or `q` that is not a label of the board";
  11. "a view and a mode that the table of T1 does not allow together";
  12. "`s` without `c`";
  13. "an unknown schema number".
- Rule details (plan where marked):
  - Parsing (rule 1): integers match `^-?\d+$`; `v` only `p n l`, `m` only `f l r`, `c` only `p n`, `e` only `p m`; `j` only the two forms above; `q` a code among `hh`, `he`, `hf`, `ef`, `serre-e`, `serre-f` (CONTRACTS `RelationCheck`), a colon and two labels separated by a comma (plan: two, as `RelationCheck` has `i` and `j`); `xyz:` coordinates distinct integers from 1 to $n$ (plan); an empty token inside a list (`1..2`, `1,,2`) does not parse; a key given twice does not parse (plan); a custom matrix whose rows differ in length does not parse.
  - Length checks run on the raw text before any parsing work (rule 3 on the value of `g` after `URLSearchParams` decoding; rule 5 by counting the tokens of `w` before converting them), so a hostile link costs nothing. The number for rule 5 is `CAPS.linkMoves` (20000; 5.6 "Moves in a link: 20000").
  - Rule 4 counts digits without the sign (plan): an entry of 40 digits passes, 41 fails.
  - Rule 2: `boardKind` on the parsed matrix, then the 12-node cap (`CAPS.customNodes`); a name `boardFromName` does not know is also a failure.
  - Rule 8: the tool's offered boards come from its registry entry (`boards: 'all' | string[]`, CONTRACTS 5.2) through `boardsOffered(tool)` of `tools/index.ts`. With a list, `g` must be one of its names and a custom board fails; with `'all'`, every board `resolveBoard` accepts is offered. Plan (no spec or plan file states it; it exists because no registry entry is on `main` until stage 1.2 and the codec must still be testable): a tool with no registry entry is treated as offering `'all'`; record it in your fragment. Tests of rule 8 use a registry fixture (section 6).
  - Rule 6 is "detected by replaying with the engine" (roster): replay `moves` from `start` with phase-0 functions and check each move before making it. Mode `free` (or no `mode` field): every move is allowed. Mode `legal`: the node's current number is positive (T1: "only nodes whose number is positive"). Mode `raising`: the node's current number is negative (T1: "only cities whose number $a_i$ is negative"). The numbers are the start itself when `coords` is `numbers` and $a=Cp$ when it is `populations`; keep them current by `fire` (firing node $i$ changes the numbers exactly as mutating city $i$ changes $Cp$, SPEC 2.4), so the check stays in integers even where the population would be fractional. Export the check as the pure `firstForbiddenMove(board, state): number | null` (plan; index of the first forbidden move).
  - The replay of rule 6 uses the board's arithmetic; on a named finite board whose `start` holds a non-safe entry, or when the replay throws `EngineOverflow`, replay on `bigBoard(board)` instead. This is never a failure and never a notice (T1, "with no message").
  - E-9 rule 2 sends "a long list of moves read from a link" to the worker. `decodeState` is synchronous (CONTRACTS 4). Under the default contract reading (`'sync'`, below) it runs `firstForbiddenMove` itself on every list of up to 20000 moves; only under the proposed `'worker'` setting does it run it itself just when `whereToRun({ board, kind: 'play', moves: n })` is `'main'` (at most 2000 moves). For a list longer than 2000 moves the synchronous signature and E-9 rule 2 conflict: CONTRACTS 4 says "Every rule of SPEC 6.6 "Validation" is enforced; on any failure the result is { state: defaults, notice: "<the sentence>" }", and E-9 forbids running that replay on the main thread. Neither you nor this instruction settles that conflict: a change to a CONTRACTS interface goes under `deviations` with the reason, and `MERGE` decides (COMMON 4.4). The reading active by default, and the one gate G1 tests, is the contract reading: `decodeState` replays every list of up to 20000 moves itself and on a forbidden move returns `{ state: defaults, notice }`, exactly as CONTRACTS 4 says. Proposed design (plan, a deviation pending `MERGE`, off by default): for a list of more than 2000 moves `decodeState` returns the parsed state with notice `null` and the optional extra field `replayCheck: true` on the returned object (the signature and the declared return type stay as they are); the tool, which must replay those moves in the worker anyway, calls `engineCall('firstForbiddenMove', ...)` (5.4) and loads `defaults` with `LINK_NOTICE` when it answers a number. Select the reading with one exported constant (plan: `LONG_LIST_REPLAY`, `'sync'` for the contract reading and the default, `'worker'` for the proposal) so that `MERGE` switches by changing one place. A test cannot reassign an ES module constant, so make the reading injectable (plan): `decodeState` keeps the signature of CONTRACTS 4 and delegates to an exported helper `decodeStateWith(query, defaults, { longListReplay = LONG_LIST_REPLAY } = {})`, used only by `decodeState` and by tests; the tests of both readings call the helper with `'sync'` and `'worker'` explicitly, so both readings are tested on the same build whatever the constant holds. ### 5.4 Where a call runs (`worker.ts`, `engine.worker.ts`; SPEC E-9)

- E-9, verbatim: "Engine functions are synchronous and know nothing about workers. At build time, when Astro renders the pages in Node, every call runs in-process and the rule that follows does not apply. In the browser the site layer (`site/src/lib/worker.ts`, built in phase 1) decides **before** a call where it runs. Everything runs on the main thread except the following, which run in a Web Worker behind a promise:
  1. an enumeration (`orbit`, `orbitGraph`, `roots`, `legalLayers`, `minusculeMatrices`, the vertices and edges of a polytope) that is not known in advance to yield at most 2000 items. Known in advance are: the roots of a board that is of finite type (at most 288 on twelve nodes); from phase 3, an orbit on a finite-type board whose size `orbitSize` gives; any search called with a cap of at most 2000;
  2. a play or a word of more than 2000 moves: `playFate`, a play to the end on a board that is not of finite type, a long list of moves read from a link. Before phase 2, when `classify` does not exist, every custom board counts as not of finite type;
  3. the counts of games and of heaps on a board whose group has more than 2000 elements; Satake data (`satake`, `satakeRecord`, `restrictedBoard`) for $E_7$ and $E_8$; the sweep over all pairs of a board."
- `whereToRun(hint: CallHint): 'main' | 'worker'` is pure; `CallHint = { board; kind: 'enumeration'|'play'|'count'|'satake'|'other'; expectedItems?; moves?; finiteKnown? }` (CONTRACTS 4). The rules as code (plan where marked, all with 2000 = `CAPS.mainThreadItems`):
  - `enumeration`: `'main'` exactly when `expectedItems` is given and at most 2000. The caller supplies `expectedItems` from one of the three sources E-9 names: the cap of the search when it is at most 2000; the number of roots of a finite-type board; from phase 3 `orbitSize`. Absent `expectedItems` means "not known in advance": `'worker'`.
  - `playFate`: E-9 rule 2 names `playFate` with no condition on the board, so it always runs in the worker. `CallHint` carries no function name, so `engineCall` checks `fn === 'playFate'` itself and routes the call to the worker whatever `whereToRun` answers for the hint (plan: the place of the check; the rule is E-9's). `playFate` arrives in phase 2 (CONTRACTS 1, `src/play.ts`); write the check now so that it holds when the function lands.
  - `play`: `'worker'` when `moves` is given and above 2000 (a word or a link's move list); `'worker'` when `moves` is absent (a play to the end, whose length is unknown) and the board is not known to be finite; otherwise `'main'`. `finiteKnown` defaults (plan) to true only for a board built by `boardFromName` from a finite type name (in phase 1, a board with `arith` `SafeInt` or a `bigBoard` copy of one, which keeps `name`); every custom board counts as not finite before phase 2, as E-9 says. `P2-A7` sets `finiteKnown` from `classify`.
  - `count`: `'worker'` when `expectedItems` (the order of the group) is above 2000.
  - `satake`: `'worker'` when `board.name` is `E7` or `E8`, or when `expectedItems` is given (plan: the number of pairs of a sweep).
  - `other`: `'main'`.
- `engineCall(fn, args, hint)` returns a promise. When `whereToRun` says `'main'`, or when running in Node (`import.meta.env.SSR`, build time), it calls the engine directly and resolves with the result. Otherwise it posts to the worker. "A call is never started in one place and continued in the other": no fallback to the main thread after a worker failure and no worker continuation of a main-thread call; a worker failure rejects the promise.
- The worker is created lazily on the first call routed to it (`new Worker(new URL('./engine.worker.ts', import.meta.url), { type: 'module' })` or the form the installed Vite 8 documents), never at import time. 7.6: "The worker's script (E-9) is fetched when a tool first needs it. No tool may need it for its default state, so it never counts toward these limits." Nothing on any route may fetch it before the first interaction (`worker-on-demand.spec.ts`).
- `EngineApi` (plan): the engine's exports plus the two site replay functions `positionsOf` and `firstForbiddenMove`, so that a long link replay runs in the worker.
- Messages (CONTRACTS 4, binding): "`{ id, fn, args: Serialized[], board: BoardSpec }` → `{ id, ok: true, result } | { id, ok: false, error: { name, message, data? } }`". Serialization: "bigint as `{ "$big": "decimal" }`; Map as `{ "$map": [[k, v], ...] }`; Board as its BoardSpec (rebuilt with resolveBoard); errors re-thrown on the main side as the same class." Plan addition: a board that is a `bigBoard` copy of a named finite board carries its arithmetic (`{ "$board": <BoardSpec>, "arith": "Big" }`) so that the worker does not rebuild it as `SafeInt`. Rationals (`{ num, den }` of `bigint`) pass through the `$big` rule. Errors: `name` selects the class among the E-10 classes exported by the engine (`NotAffine` keeps its message with the class; `NotAdmissible` carries its `Admissibility` in `data`); an unknown name becomes a plain `Error` with the same message.
- Ids are increasing integers; concurrent calls resolve independently; the worker never holds state between calls except the engine's own cache (E-11).

2. Query strings are assembled by hand so that commas, semicolons, dots, `~` and `^` stay readable (6.6); do not URL-encode them away (roster). `URLSearchParams` decodes `+` as a space: never write `+`.
3. On lesson pages keys are prefixed by the instance id and a dot (`b2.g=A3`); only instances the reader changed are written (roster). `P1-A5` passes the prefix as `'b2.'`.

5. Positions are never in the state; they are recomputed from start and moves (7.4) (roster). Do not add a cache of positions to `ToolState` or to the URL.

7. A Nano Store read as `$name` is the one store idiom allowed in Svelte 5 components (7.2 item 5) (roster). Local component state is `$state`, never `writable`.
8. Mode legality is about the numbers, also in the populations view: raising means $a_i<0$ with $a=Cp$, legal means $a_i>0$. Checking the population entry $p_i$ instead is a convention error that symmetric examples hide; test on $A_3$ with $p=(1,0,0)$, where $a=(2,-1,0)$ makes city 2 the only legal raising move.
9. The roads-versus-Cartan transposition: `fromAdjacency(A)` builds $C=2I-A^{\mathsf T}$, so a custom Cartan matrix from a link becomes $A_{ij}=-C_{ji}$.
