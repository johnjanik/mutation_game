## 2026-10-24 RT-FIX-P4-a11y: more controls that their own press makes inactive keep the focus (P4-RT-05-01)
Decision: the rule of "2026-10-17 RT-FIX-P3-follow-predict: done controls keep the focus" now also covers: T2's "Grow one layer" at the last layer and "Show total" once shown; T7's table button "Fire node k" while node k cannot be fired (every legal fire makes the fired number negative); T5's "Step B" and "Play B to the end" at the end of game B; the board editor's "Add node" at the largest board and "Remove node" at the smallest (T4, T16), with the visible reason beside them as before; and the Challenge's answer field and Check once the answer is accepted (the field is also `readonly`, since `aria-disabled` alone leaves a text field editable). Each carries `aria-disabled="true"` in that state instead of the HTML `disabled` attribute, and its handler returns at once by the same predicate ("2026-10-24 RT-FIX-P3-residual-tools: an aria-disabled control ignores activation"). The `disabled` attribute stays before hydration (7.4), while a prediction freezes the board, while the tool turns the editor off, and for T2's grow in follow mode, which another control sets. Two controls of T5 leave the page under their own press, so a focus left on them moves to an element inside the tool, as T4's keep counting moves it to its counter: "Start the wave from all ones" (gone once the wave can start) hands it to the tab panel, which takes `tabindex="-1"`; "Use this start" (gone when the custom start is all ones or a fundamental weight, which closes the custom fields) hands it to the start chooser. This replaces the word "disabled" of the entries "2026-10-10 P2-A3" (removing the last node) and "2026-10-10 P3-A5" (the table button) for the time after hydration; both controls are still announced as unavailable. What the specification left open: SPEC 7.5 A-1 (WCAG 2.4.3) names no focus target after an action. Default used: none. Reason: P4-RT-05-01; the T10 controls of the finding are the T10 fixer's.

## 2026-10-24 RT-FIX-P4-a11y: the tool frame is one column no wider than itself (P4-RT-05-02)
Decision: `.tool-frame` in ToolFrame.svelte has `grid-template-columns: minmax(0, 1fr)`. Its implicit auto column let a child's min-content width (an open "Show as table" view) set the width of the frame, so at 320 pixels the title, the figure and the controls ran off-screen; now the table scrolls inside its own box (the existing `.bare` fieldset with `overflow-x: auto`). What the specification left open: nothing (A-11). Default used: none. Reason: P4-RT-05-02; the fix is at the frame, so every child of every tool is held to the column, not only the table view.

## 2026-10-24 RT-FIX-P4-a11y: an answer Check cannot read is named in words (P4-RT-05-05)
Decision: when Predict's Check finds no answer it can read, it writes one sentence into the result line (`data-out="predictResult"`) and the tool's polite live region, and gives each field that holds the problem `aria-describedby` on the result line and, for a text field, `aria-invalid="true"` (a radio button takes no `aria-invalid`, which Svelte's check and ARIA 1.3 refuse for the role radio). The sentences: "Type a whole number." (a number question: empty, a word, a fraction, "+3"), "Type a whole number in each field." (a position question), "Choose one of the answers." (a choice question with no choice made, which also said nothing before). Editing a marked field (typing, or choosing an answer) removes its mark, and the sentence goes once no field is marked; answering or "Show me" replaces it by the result as before. The board stays frozen and Check stays usable. Check now also returns at once once the prediction is answered, so an answered Check with an empty field says nothing (RT-FIX-P3-residual-tools). What the specification left open: 4.0 Predict and 7.5 give no wording for an answer that cannot be read; WCAG 3.3.1 and 4.1.3 ask that the error be named in text and announced. Default used: none. Reason: P4-RT-05-05.

## 2026-10-24 RT-FIX-P4-a11y: one look for a control that cannot act (P4-RT-06-01)
Decision: one rule in `site/src/styles/base.css`, loaded on every page, gives every `button`, `input`, `select` and `textarea` that is `:disabled` (before hydration, and without JavaScript) or `aria-disabled="true"` (a done control, a frozen board's node) a dashed border and text toned towards the page: `color-mix(in srgb, var(--text) 65%, var(--page))`, which is 5.4 to 1 on the light page and 6.9 to 1 on the dark one, so A-6 holds for that text too. The two declarations carry `!important`, because every component sets `color` and `border` for the usable look in a scoped rule of higher specificity (and some, such as T11's selected tab, set `border` again in a state rule); no component rule overrides them, and T10 and T11 take the look without an edit to their files. The focus ring is left as it is, since a done control keeps the focus (A-1, A-2); opacity was not used for that reason. No CSS custom property was added (CONTRACTS 8). A board's drawn nodes are not buttons (the node buttons are transparent hit areas over the drawing), so the rule changes nothing on a drawn board: its second ring of 6.3 ("may act here") is drawn on a board that is not hydrated yet or is frozen by a prediction as before, since a dashed circle already marks nodes in T9 and in the board editor. What the specification left open: 7.4 asks that a control never look usable before it is, and gives no look; 8.3 [D] "calm, bright, low-chrome". Default used: none. Reason: P4-RT-06-01.
