## 2026-10-24 P5-A1: the sparse helpers, their names and the key format
Decision: `rep.ts` exports `spKey(row, column)`, `spMul(X, Y)`, `spAdd(X, Y, cy = 1n)`, `spComm(X, Y)`, `spScale(X, c)` and `spEq(X, Y)`, ports of `sp_mul`, `sp_add`, `sp_comm`, `sp_scale` and of Python's `==` on zero-free dictionaries. A key is the row and the column as decimal integers joined by one comma, no spaces, no leading zeros (`"0,2"`, `"12,3"`); `spKey` throws `RangeError` unless both are non-negative safe integers. Every operation returns a new `Map` without zero entries (the oracle's final filter, applied after all sums, so the order of the entries is the oracle's insertion order); `spScale` by `0n` gives the empty `Map`. `spMul` parses each key once per entry and throws `RangeError` on a key that `spKey` would not write (for instance `"0, 1"` or `"01,1"`), since such a key would silently miss its partner. What the specification left open: the names and the key format (SPEC 5.2 gives only `Map<string, bigint>`, key "row,column"). Default used (SPEC section 10): none; the plan's names (instruction 5.2). Reason: one key writer for the engine, T12 and phase 7.

## 2026-10-24 P5-A1: spEq ignores explicit zero entries
Decision: `spEq` compares the nonzero entries only: an explicit `0n` in either `Map` counts as absent, and the result does not depend on insertion order. What the specification left open: how to compare a `Map` that a caller built without the zero-free invariant. Default used (SPEC section 10): none; the plan's rule (instruction 5.2). Reason: on zero-free inputs it is exactly the oracle's `==`; on others it still answers the mathematical question.

## 2026-10-24 P5-A1: the RelationCheck list, its order, and the split of the Serre boolean
Decision: `chevalleySerre` returns one record per instance: for `i` from 0 to n-1, then `j` from 0 to n-1, the records `hh`, `he`, `hf`, `ef`, then, when `i != j`, `serre-e` and `serre-f`; that is 6n^2 - 2n records (20 on A2, 88 on D4, 280 on E7). The oracle's single Serre boolean is split into `serre-e` and `serre-f`. `left` and `right` are new `Map`s in every record: the right side of `ef` with `i == j` is a zero-free copy of `H[i]` (`spScale(H[i], 1n)`), `hh`, the other `ef` and both Serre right sides are new empty `Map`s, and the Serre left side starts from a copy of `E[j]` (or `F[j]`) and applies `ad(E[i])` exactly `1 - C[i][j]` times. `holds` is `spEq(left, right)`; the oracle's `chevalley_serre_ok` is true exactly when every record holds. What the specification left open: the order and the granularity of the records (SPEC 5.4: "a RelationCheck for every relation, with both sides"). Default used (SPEC section 10): none; the plan's (instruction 5.5). Reason: the oracle's loop order; T12 can show each Serre relation separately, and its link key `q` (6.6) names one relation with its nodes (`serre-e:2,3`).

## 2026-10-24 P5-A1: moves computed from fire, not as E + F + P0
Decision: `moves[k]` is the oracle's `S[k]`: for every basis vector `a`, the entry `(index of fire(a, k), index of a)` is `1n`, including the diagonal entries where `a_k = 0`. It is never assembled as `E[k] + F[k] + P_k^0`. On the 18 minuscule records the two agree (tested); on node 2 of D4 they differ at every node (tested), because entries 2 and -2 reach `moves` and `H` but neither `E` nor `F`. What the specification left open: the roster's wording "the move matrices E_k + F_k + P_k^0" against the oracle's `S`. Default used (SPEC section 10): none; the oracle (COMMON.md 2, extended by the plan to the roster's wording; SPEC 2.18 states the identity only for minuscule nodes). Reason: T12 shows the firing move for any node, minuscule or not.

## 2026-10-24 P5-A1: how the cap of minusculeMatrices is decided
Decision: `minusculeMatrices(board, i, cap = CAPS.repOrbit)` enumerates `orbit(board, [omega_i], 'firing', cap)` and returns `null` exactly when the result is `truncated`; by SPEC 5.5 an orbit of exactly `cap` positions is not truncated and is built (E7 node 7 at a cap of 56 is built, at 55 it is `null`). `orbitSize` is not consulted first: the enumeration stops at the cap anyway (at most `cap + 1` positions are found), so a second source of truth would only add a guarded play. `cap` must be a positive safe integer (`RangeError`). The oracle has no cap; the cap is the engine's own rule. What the specification left open: the method (the instruction allows either). Default used (SPEC section 10): none. Reason: one decision path, the search's own truncation, which SPEC 5.5 defines exactly.

## 2026-10-24 P5-A1: the guards, and their absence on signedMoves
Decision: `minusculeMatrices`, `chevalleySerre` and `stringThrough` check their arguments first (`RangeError`), then call `requireGcm` and `requireFinite` from `guards.ts`, in P2-A1's order: so a one-way board throws `NeedsTwoWayRoads`, an affine or indefinite board `NotFiniteType`, and a malformed argument `RangeError` even on a one-way board. `signedMoves` takes no board and has no guard: it works as defined on whatever matrices it is given. Each function that takes a board has the `AnyBoard` overload after the generic one, as P2-A1 and P3-A1 did. What the specification left open: 5.6 lists "the representation functions" in its last row without naming the one that takes no board. Default used (SPEC section 10): none; the plan's reading (instruction 5.4). Reason: a guard needs a board.

## 2026-10-24 P5-A1: RangeError cases added
Decision: `RangeError` on: a row or column of `spKey` that is not a non-negative safe integer; a key in an input of `spMul` that is not two decimal integers joined by one comma; a node position outside 0..n-1 (`minusculeMatrices`, `stringThrough`); a `cap` that is not a positive safe integer (`minusculeMatrices`); `E` and `F` of different lengths, or a basis vector shorter than `E` (`signedMoves`); `E`, `F` or `H` without one matrix per node (`chevalleySerre`); `mu` without one entry per node, an entry of `mu` that is not a safe integer, and `mu_i < 0` (`stringThrough`, where the oracle asserts; the message names the node position and the value). What the specification left open: invalid arguments. Default used (SPEC section 10): none; `RangeError`, as every earlier phase did. Reason: E-10 reserves the engine's own classes for the theory; reaching the cap is reported by `null`, never thrown.

## 2026-10-24 P5-A1: stringThrough has no cap and checks each entry
Decision: `stringThrough` returns all `mu_i + 1` positions whatever `mu_i` is; the specification gives no cap, and T12 must bound what a reader can type (requested from P5-A2). Each position is the previous one minus column `i` of `C`, and each entry is checked with `Number.isSafeInteger` as it is computed (`EngineOverflow` otherwise, the `SafeInt` rule of E-2); successive subtraction gives exactly `mu - k * column` while every entry is safe, and fails only at an entry the result cannot hold. `-0` is written as `0`. What the specification left open: the length bound and the arithmetic. Default used (SPEC section 10): none; the plan's (instruction 5.6). Reason: the oracle has no bound; the contract types the result as `number[][]`.

## 2026-10-24 P5-A1: the bigint to number rule for basis
Decision: `basis` is `number[][]` on every board. On a `Board<number>` the entries are taken as they are (with `-0` written as `0`); on a finite `Board<bigint>` (a finite board built by hand) each entry is converted with `Number` after a check that it is a safe integer, and `EngineOverflow` is thrown otherwise, which a finite orbit within the cap never meets. The matrices are `bigint` on every board. The basis is the orbit sorted by a numeric comparator, entry by entry, largest first (never the default string sort), and is indexed by the entries joined with commas; `fire` is applied to the orbit's own vectors in the board's arithmetic, and `join` writes a number and a bigint with the same text. What the specification left open: the contract's `number[][]` on a `Board<bigint>`. Default used (SPEC section 10): none; the plan's (instruction 5.3). Reason: the contract type; the same rule as the overflow rule of `wythoffEdges` (decisions/RT-FIX-P4-engine.md).
