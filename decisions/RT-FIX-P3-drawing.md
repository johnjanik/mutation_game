# Decisions of RT-FIX-P3-drawing (red team round 1, phases 0 to 3, cluster "drawing")

## 2026-10-17 RT-FIX-P3-drawing: how the `roads` style draws more roads than the editor allows
Decision: `roadGlyphs` (site/src/components/draw/roads.ts) draws every road as its own curved arrow up to `CAPS.roadsEachWay` (4) roads in one direction, as before. A direction with more roads is drawn as one arrow (the first curve of that direction) with its count written beyond the apex in `var(--text)`, glyph kind `counted`. A pair therefore has at most 2 x 4 glyphs whatever its counts. What the specification left open: 6.2 [D] says that in the `roads` style "every road is drawn as its own curved arrow", and 5.6 caps the roads between two nodes at 4 each way in the editor only ("the engine accepts any count"); neither says how a board from outside the editor (a link with a `c:` matrix, which the codec accepts with any safe count) is drawn. Followed literally, 6.2 drew 2^53 - 1 arrows and hung the page (P3-RT-03-01). Reason: the orchestrator's direction for this cluster (the drawing must be bounded); the threshold is the editor's cap, so 6.2 holds unchanged for every board the editor, a preset or the golden file can produce (at most 4 roads each way), and the device for "too many to draw" is the one 6.2 already uses for the thick line of the `dynkin` style, which writes the counts as numbers. The `dynkin` style is unchanged (its glyphs were bounded already).

## 2026-10-17 RT-FIX-P3-drawing: T16's import refuses more than four roads each way
Decision: the JSON import of the sandbox (T16BoardIO.svelte, `customSpec`) refuses a custom board with more than `CAPS.roadsEachWay` roads from one node to another, after the checks P2-A5 recorded, with the reason "it has N roads from node A to node B, and the editor allows at most 4 each way" inside P2-A5's sentence "The board could not be read: <reason>. The board was left as it was." The labels are the board's (`toLabels`, E-7). This extends the list of refusals in decisions/P2-A5.md ("JSON import and export of boards") by one item; nothing else of that entry changes, and the BoardEditor contract of decisions/P2-A3.md (props, `maxRoads` at most 4, the road selects 0 to 4) is untouched. What the specification left open: whether the editor's cap of 5.6 applies to an import. Reason: SPEC 4 T16 makes the sandbox "The editor of T4", T4's editor has "between two nodes, 0 to 4 roads each way", and 6.6 Validation refuses "a board that the tool does not offer"; both verifiers of P3-RT-03-01 read the texts the same way.
