## 2026-10-25 RT-FIX-P5-t12-perf: a link's state reads the facts of its node, and the rest is built one engine call per task (P5-RT-07-01)
Decision: `admitLink` validates a link with `new T12Tool(configOf(state), { defer: true })`, the facts of the node only (it used `need: 'staged'`: `minusculeMatrices` and the signed moves of every node at once), and finds the board and node of the link (`targetOf`) before it computes any default, so that a link whose `k` names another node of the board named by `g` no longer computes the defaults of the board's default node too. `load()` builds the tool with the facts only and swaps it at once (the facts line, the string viewer and History show the link's state on hydration, as before); when the panels are drawn from the state (`stage`), the steps of `representationSteps` (decide, enumerate, sign one node per task above 300 positions, the list on the main thread) run first, one per task, the panels waiting meanwhile, then a step that tells the derived values the matrices are there, then the panels piece by piece; on the node shown (a link that changes only the start, the moves or the relation, read on hydration, when the configured state has the facts only) the matrices are built in a task of their own before the relation is drawn. `representationSteps` returns no step when everything it computes is computed, so a load after a pick adds no task. What the specification left open: SPEC 7.6 bounds an engine call at a long task and says nothing of how a load is shaped; decisions/P5-A2.md records that a pick builds the representation one engine call per task and that hydration computes the facts only. Default used: the lens's proposed fix (validate with 'facts', build in `load()` with 'facts', run the steps before the panels). A first variant that built the representation before reading the link (the figure keeping the configured state meanwhile, as a pick keeps the previous one) was dropped: two tests of `T12.spec.ts` read the link's state right after hydration (the dimension of G2 node 1, the end of a play of 2001 moves replayed in the worker). Residual, by design: a link to a node that is not minuscule whose relation list stays on the main thread (at most `RELATIONS_MAIN_WORK`, 2500 units of work, positions times records: node 2 of D4 is 24 by 88) still computes its matrices and that list where the link is read, through `defaultsFor`, because its default relation, a field of the state when the link has no `q`, is the first failing relation of that list; the configured state of an instance does the same through `configuredState`. Measurements (Chromium at full speed, 360 by 800, medians of three runs against a link to E7 node 7 as control, the adopted test): before, at `b6b538d`, load 0.5, the hydration task of a link to E7 node 6 was 77 ms (control 0), C8 node 7 78 (52), B8 node 7 72 (0), D8 node 3 66 (0); after, at load 0.5 to 1.0, it was not a long task in every run, and the lens's script (`redteam-RT-07-t12-link-task.mjs`, run from the scratch directory on the build) found no long task after hydration in 15 link loads of E7:6, C8:7, B8:7, D8:3 and E8:8. With the processor slowed four times the island's hydration task stays long whatever the link (Svelte's hydration, the panels taken down, the facts): E7 node 6 192, 222, 285 ms after against 400, 403, 569 before; E8 node 8 237, 344, 454 after against 291, 312, 356 before (the island's own hydration, about 100 to 150 ms there, dominates the noise).

## 2026-10-25 RT-FIX-P5-t12-perf: one board object per name in T12 (P5-RT-07-02)
Decision: `t12/model.ts` keeps the board object of each name it has resolved (`boardOf`, a map of at most the 32 names of `t12/boards.ts`; boards are frozen), and every board T12 uses comes from it: `representationSteps`, `representationOf`, `defaultsFor`, the `T12Tool` constructor, the link's target and the default node of a picked board. A pick then classifies a board once when it is first loaded and never again on the page; the instances of M8 share the objects. `forgetRepresentations`, the test seam of a new page, empties the map too. `site/src/lib/state.ts` (`resolveBoard`, `resolvedThisRun`) is unchanged, so no other tool changes. What the specification left open: SPEC 5.6 says "once when the board is loaded" and E-11 keeps the verdict per board object; neither says how a tool whose load spans tasks keeps the object. Default used: the lens's second proposal (keep the object), as a map by name rather than per generation, which is smaller and bounded. Test method: the browser test counts the engine's `classifyUncached` with a DevTools breakpoint whose condition counts and never pauses, set by URL on the statement that checks the board, which the test finds in the engine's chunk (`_astro/src.*.js`) by the message that statement throws; the lens's script placed the same logpoint through a source-map build, which the suite does not make. Before: 3 computations per pick (E6), as the lens found; after: 1 for each of E6, E7, D4, B8, G2 and for C8 after a link.
