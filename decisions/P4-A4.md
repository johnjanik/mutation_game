## 2026-10-17 P4-A4: the symmetry picker, the default symmetry, the identity
Decision: `symmetries(board)` is called once per board (default limit); the picker lists every symmetry but the identity, in the engine's order (lexicographic in the image tuples), each shown by its orbits in labels with its order (`{1, 3} {2}, order 2`; option value the images joined by dots, the `y` form). The default symmetry is the first one listed: the flip on A_n and E6, the swap of the last two nodes on D5 to D8, the swap `1.2.4.3` on D4. On D4 the five are `1.2.4.3`, `3.2.1.4` (swaps), `3.2.4.1`, `4.2.1.3` (rotations of order 3, folding to G2) and `4.2.3.1` (swap): three swaps fold to C3 in three orbit orders, two rotations to G2 (the instruction's sentence lists the two rotations last; the engine's order puts `4.2.1.3` fourth). A link whose `y` is the identity loads the default state with the notice (plan: a symmetry the tool does not offer, by analogy with 6.6 "a board that the tool does not offer"). `fold` does not check that its permutation preserves the board (as the oracle), so the tool checks `C[s(i)][s(j)] = C[i][j]` itself before folding (a RangeError, which an author sees as a build error naming the instance; a link never reaches it, the codec's rule 7 refuses first). The picker of boards, the symmetry picker and the view switch each reset the start and the moves; the board picker also resets the symmetry to the new board's default. What the specification left open: the order and default. Default used: the plan's (instruction 5.2).

## 2026-10-17 P4-A4: one entry per symmetric move in `moves`
Decision: a symmetric move is recorded as ONE entry of `moves`, the smallest label of the orbit acted on; on replay each entry expands to the whole orbit in increasing position (E-5), and any label of an orbit in `w` names that orbit and is written back as its smallest label (`/tools/fold?g=A3&w=3` is written back as `w=1`; `?g=D4&y=3.2.4.1&w=4.2` holds two symmetric moves, on `{1, 3, 4}` and on `{2}`, and is written back as `w=1.2`). So `data-moves`, the History strip, undo, redo and reset count symmetric moves, and the folded board's word is the same list read through the orbit map (folded position s is orbit s). This is the one place where a T11 link differs in meaning from a T1 link. What the specification left open: 6.6 defines `w` for single moves only. Default used: the plan's (instruction 5.3), reported as a deviation for MERGE to confirm.

## 2026-10-17 P4-A4: views, coords, the default start, and starts that are not symmetric
Decision: T11 plays one game at a time: `view` is `populations` or `numbers` and `coords` always equals it (the start is a position of the game shown). Default state of `/tools/fold`: `{ schema: 1, tool: 'fold', board: 'A3', view: 'numbers', coords: 'numbers', start: [1, 1, 1], moves: [], symmetry: [3, 2, 1] }`, fold tab. The populations default start is one Martian in every city of the orbit of city 1 (symmetric for every symmetry; on the folded board it is one Martian in the city of that orbit, which is the folded board's city 1 only when the orbit comes first in Bourbaki order, so not on D4 with the swaps `3.2.1.4` and `4.2.3.1`, where it is city 3 of C3, nor with the rotations, where it is city 2 of G2; reworded in the polish of wave 4.3): `(1, 0, 1)` on A3 with the flip, `(1, 0, 0, 0, 0, 1)` on E6, `(1, 0, 0, 0)` on D4 with the swap `1.2.4.3`. Link rules (plan): `v` and `c` name one game; a link with only one of them sets both, a link with both that differ loads the defaults with the notice; a link without `s` takes the tool's default start for the board, view and symmetry in force (the codec's own fallback, one Martian in the first city, is not symmetric); a start that is not constant on the orbits of the symmetry loads the defaults with the notice (an author's such start fails the build naming the instance). What the specification left open: 6.6 lists the codec's failures; these are the tool's. Default used: the plan's (instruction 5.3).

## 2026-10-17 P4-A4: links with `v=l` or `m` (plan rules, for MERGE to rule on)
Decision: `v=l` asks for the linked view, which T11 does not offer: the instance loads its default state with the notice that the link could not be read. An `m` whose value parses (`f`, `l` or `r`) is ignored: it is removed from the query before the codec reads the link (so neither T1's table of views and modes nor the replay of rule 6 can refuse it), the rest of the link is read, there is no notice, and the URL written back has no `m`. An `m` that does not parse (`m=z`) fails in the codec like any known key and gives the defaults with the notice. Tested in `T11.test.ts` and `T11.spec.ts`. What the specification left open: 6.6 says only "An unknown key is ignored", and `v` and `m` are known keys. Default used: the plan's (instruction 5.3); reported under deviations and open questions.

## 2026-10-17 P4-A4: where the replays run (E-9), and the worker's board
Decision: everything T11 computes on load or on a move runs on the main thread (symmetries, fold, identify, averagedRootsType, one engine call per board per symmetric move), except a list of moves read from a link whose big-board word (the expanded word) or folded word exceeds 2000 moves (E-9 rule 2). Hints, built in `t11/model.ts`: `playHint(board, n) = { board, kind: 'play', moves: n }` with n the expanded length for the big board and the number of symmetric moves for the folded board; on A3 with 1001 symmetric moves the big hint says 2002 (worker), with 1000 it says 2000 (main). When either goes to the worker, both replays go through `engineCall('positionsOf', [state], hint)` (the site's replay, which P1-A2 placed in the worker API "so that a long link replay runs in the worker") instead of `applyWord`, because `positionsOf` returns every position of the play, which the History strip and undo need (deviation from the plan's `engineCall('applyWord', ...)`, same rule and hints). The folded board is sent as its Cartan matrix in orbit order (a custom spec, labels 1..m following its positions), not by its name: `workerWire.specOf` serialises a named board by name, and `resolveBoard('G2')` would rebuild G2 with its positions in Bourbaki order, exchanging the two nodes of the rotation of D4. While the worker runs, both boards keep the start, every node has `data-can-act="false"`, the History and the pickers are disabled and nothing is announced; errors are not caught. Moves the reader makes afterwards are played one at a time on the main thread from the positions kept. A configuration given by an author's properties is replayed at once (at build time, where E-9 does not apply, and again at hydration); no default needs the worker. The averaged roots: `whereToRun({ board, kind: 'enumeration', finiteKnown: true, expectedItems: <roots> })` with the number of roots known in advance (A_n: n(n + 1), D_n: 2n(n - 1), E6: 72), always `main` (instruction 5.7). What the specification left open: E-9 names the cases, not the calls. Default used: the plan's (instruction 5.12), with the positionsOf deviation.
