## 2026-10-10 P3-A2: the heapKey text format
Decision: `heapKey(board, word)` is the multiset of (node, level) pairs of `heap`, sorted by node and then by level, each pair written `node:level` over positions, joined by commas; the empty word gives `""`. On A3 the play `[0, 1, 0]` gives `0:1,0:3,1:2`. Two words have equal keys exactly when the oracle's `tuple(sorted(zip(word, heap(C, word))))` are equal. What the specification left open: the text format ("a key that is equal for plays with the same heap"). Default used: the plan's suggestion (P3-A2 instruction 5.3). Reason: T8 (P3-A6) groups games by this string; a deterministic text over positions is enough and is cheap to compute.

## 2026-10-10 P3-A2: cap semantics of allCompleteGames and the bound for plays that do not end
Decision: `allCompleteGames(board, start, cap)` enumerates depth first with the positive nodes in increasing position (the oracle's order, so the items are in lexicographic order and the first is `play`'s word). When the search is about to record game number `cap + 1` it stops at once with exactly `cap` items and `truncated: true`; otherwise `truncated` is `false` (a cap of 0 gives `truncated: true` with no items as soon as one complete game exists). Plan rule for plays that do not end: when a single play reaches `CAPS.playMoves` (20000) moves without ending, the search stops at once with `truncated: true` and the complete games found so far. On a finite-type board every play from one start has the same length (F3; from rho it is N, F5), so there the bound binds only when that length exceeds 20000; on a one-way, affine, indefinite or reader-drawn board SPEC.md 2.7 gives no such guarantee, so the bound can cut a search in which some plays end and others do not (plan assumption): such a result carries `truncated: true` and is never presented as the complete list. A cap that is not a non-negative integer or a start of the wrong length is a `RangeError`. What the specification left open: the oracle raises `OverflowError` at `limit + 1` games and has no bound on the length of a play. Default used: the plan's (5.5, from E-6, E-10 and 5.4 "stops at the cap when the plays do not end"). Reason: a cap is reported, never thrown; "No function loops without a bound".

## 2026-10-10 P3-A2: explicit stack in allCompleteGames
Decision: the search keeps its own stack of frames (the position, its positive nodes in increasing order, and the index of the next one to try) and the current word; no recursion. What the specification left open: the oracle is recursive. Default used: the plan's (5.5). Reason: a 20000-move play on an affine board from all ones would overflow the JavaScript call stack; with the explicit stack `allCompleteGames(boardFromName('A2~'), [1n, 1n, 1n], 100000)` returns `{ items: [], truncated: true }` in well under a second.

## 2026-10-10 P3-A2: bigint masks in commutationClassSize
Decision: the set of bricks already laid is a `bigint` mask (`1n << BigInt(k)` per brick, precomputed once), `below[k]` is a `bigint` mask of the earlier bricks at the same or a joined node, the memo is a `Map<bigint, bigint>` keyed by the mask, and the count is the oracle's memoised recursion (`count(full) = 1`; `count(mask)` sums over the bricks not in the mask whose `below` is inside it; the answer is `count(0n)`); the empty word gives `1n`. Tested with 40 bricks (two unjoined nodes fired 20 times each give C(40, 20) = 137846528820). What the specification left open: the representation of the bit mask ("a bit mask"). Default used: `bigint` (P3-A2 instruction trap 7). Reason: JavaScript's `1 << k` and `&` work on 32-bit signed integers and words longer than 30 moves occur.

## 2026-10-10 P3-A2: "joined" in heap and commutationClassSize
Decision: a brick rests on an earlier brick when the nodes are equal or `C[i][j]` or `C[j][i]` is nonzero, tested through `arith.sign` (never `!== 0`, since `0n !== 0` is true); so on the one-way board `[[2, 0], [-1, 2]]` the two nodes are joined and `heap([0, 1])` is `[1, 2]`. What the specification left open: nothing; this is the oracle's test. Reason: the port must match on `Board<bigint>` boards as well as on named finite boards.

## 2026-10-10 P3-A2: the overflow rule of symbolicPlay
Decision: `symbolicPlay` computes the running matrix exactly in `bigint` (the Cartan entries through `arith.toBig`), records row `i` before each move, then replaces every row `j` by `row j - C[j][i] * row i`, and converts each recorded entry to a `number`, throwing `EngineOverflow` when an entry is not a safe integer. No legality test: any word is played. What the specification left open: CONTRACTS.md 2.4 says `number[][]` without saying what happens when a coefficient passes 2^53. Default used: the plan's reading (5.6). Reason: on every finite type the entries are root coefficients and small; on a `Board<bigint>` board with a long word they can grow, and E-10 names `EngineOverflow` for exactly this.

## 2026-10-10 P3-A2: how choleskyBasis converts rationals to floats, and its guards
Decision: `choleskyBasis` calls `requireGcm` then `requireFinite` before any arithmetic (so a one-way board throws `NeedsTwoWayRoads` and `A2~` or `pentagon` throws `NotFiniteType`), then takes `gram(board)` and converts each entry as `Number(num) / Number(den)`; the result is the oracle's upper triangular `U` as a list of rows with entries below the diagonal exactly `0`. The branch for `gram` returning `null` after the guards cannot be reached (a finite-type board is balanced) and throws `NotFiniteType` rather than using a non-null assertion. What the specification left open: the conversion (2.14 says only that floating point enters here). Default used: the plan's (5.7). Reason: `form.ts` and `classify.ts` are not mine to change; the numerators and denominators of the symmetrizer of a board with at most 12 nodes are tiny, so the quotient is exact to the last bit of a double.

## 2026-10-10 P3-A2: AnyBoard overloads and RangeError cases
Decision: `heap`, `heapKey`, `commutationClassSize`, `symbolicPlay`, `allCompleteGames` and `choleskyBasis` each have the generic overload `<T>(board: Board<T>, ...)` first and an `AnyBoard` overload second (`allCompleteGames` with `Vec<number | bigint>`), the pattern of P1-A1's `transposeBoard` and P2-A1's phase-2 functions. A word entry that is not a position 0..n-1 is a `RangeError` in the four functions of words (as `mutate` and `fire` do). What the specification left open: the contract writes `board` as "`Board<number>` or `Board<bigint>`". Default used: the plan's pattern. Reason: `boardFromName` and the site's `resolveBoard` return `AnyBoard`; without the overloads `tsc` rejects every tool call on one.

## 2026-10-10 P3-A2: the benchmark command, the measured median, and the request for the script
Decision: `packages/engine/vitest.config.ts` includes only `test/golden`, `test/properties` and `test/unit`, Vitest 5.0.3's default include pattern (`**/*.{test,spec}.?(c|m)[jt]s?(x)`) does not collect `*.bench.ts`, `vitest bench` runs benchmark mode (which reports timings and does not fail on a threshold), and the CLI has no top-level `--include` option (only `--dir`, `--exclude`, `--project`). The benchmark is therefore written with `describe`, `it` and `expect`, and run alone, from the repository root, by

    node_modules/.bin/vitest run --root packages/engine --config <scratch>/vitest.bench.config.ts

where the scratch configuration is a plain object (no import, so that it resolves nothing from its own directory): `{ test: { name: 'engine-bench', root: '<worktree>/packages/engine', include: ['test/bench/**/*.bench.ts'], fileParallelism: false } }`. Requested from MERGE (pre-approved by the orchestrator): a script `"bench"` in `packages/engine/package.json` that runs only this file, kept out of `npm test` because timing under the parallel suite is noisy; the one-line form `"bench": "vitest run --config test/bench/vitest.config.ts"` with that same object committed as `packages/engine/test/bench/vitest.config.ts` (a file outside my ownership list, hence the request) is the simplest. Measured on this cloud container (4 processors, shared with P3-A1 and P3-A7; checked quiet with `uptime` and `ps` first, load average 0.90, no other vitest, astro or chromium process): the run that printed its numbers gave a median of 25.79 ms over the seven runs [33.91, 28.34, 28.84, 25.79, 24.33, 22.21, 23.27] ms, with 2000 positions and `truncated: true`, so the test FAILED the 25 ms line by 0.79 ms. An earlier run of the same command, before the print line was changed (see the next entry), PASSED but printed no numbers; it is not counted as the measurement. No retry was made (COMMON.md 4.4, P3-A2 instruction 5.15). For scale, `node reference/bench_orbit.mjs` run alone on the same machine right after gave 21.0 ms in `Big` for the same case, against the 9 ms that SPEC.md 5.5 records for the specification's server processor: this container is about 2.3 times slower than the processor the 25 ms line was sized for, and the engine's `orbitGraph` is about 23 percent slower than the reference script here (the reference skips zero Cartan entries in its mutation and the engine's `mutate` multiplies all twelve, through the `Arith` interface, and copies the vector). `search.ts` and `moves.ts` are P1-A1's and were not changed; the item is reported `partial` with a request through MERGE. What the specification left open: how the file is wired (7.6 names the Vitest benchmark; CONTRACTS.md 3 only its path). Default used: the plan's (5.15). Reason: a benchmark that no command runs fails the G3 item; the threshold is fixed by SPEC.md 7.6 and may not be raised.
