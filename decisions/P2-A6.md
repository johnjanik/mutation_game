## 2026-10-10 P2-A6: the footer line (SPEC 8.3 [D])

## 2026-10-10 P2-A6: footer lines fit the figure (plan detail adapted)

## 2026-10-10 P2-A6: the pixel-unit export root
Decision: the file's root is `<svg width=W height=T viewBox="0 0 W T" role="img">` in CSS pixels, `W` and `H` the `getBoundingClientRect()` size of the live drawing (or the `width` and `height` of a composite); the drawing is a nested `<svg x=0 y=0 width=W height=H>` keeping its own `viewBox` (the inlined clone itself); the note of exact digits and the footer are siblings below it, so the `viewBox` of the drawing clips nothing of them. The exported size is the on-screen size and depends on the viewport (SPEC 6.1 "Size on screen"). First child `<title>`: the board name when a footer is given, else `exported figure`. `aria-hidden`, `tabindex`, `focusable` and `class` are removed from every element; `xlink:href` becomes `href`. Reason: the instruction (5.2 step 3), A-10.

## 2026-10-10 P2-A6: inlined styles, theme and background
Decision: `inlineStyles` walks the live tree and the clone in parallel and writes, as a `style` attribute, these computed properties: `fill`, `fill-opacity`, `fill-rule`, `stroke`, `stroke-width`, `stroke-opacity`, `stroke-dasharray`, `stroke-linecap`, `stroke-linejoin`, `vector-effect` (the board's strokes are non-scaling; without it a 2-pixel stroke in grid units would be enormous), `opacity`, `font-family`, `font-size`, `font-weight`, `font-style`, `font-variant-numeric`, `letter-spacing`, `text-anchor`, `dominant-baseline`, `paint-order`, `visibility`, `color`. To keep the file small a property is written on the drawing's root always and on a descendant only when it differs from what the element would get anyway (the parent's computed value for an inherited property, the initial value for `opacity` and `vector-effect`) or when the element has a presentation attribute of that name. Any attribute whose value still contains `var(` is removed afterwards (`draw/roads.ts` sets `stroke="var(--road)"` and the like as presentation attributes), as are `<style>` elements and comments (Svelte's hydration markers). Running transitions in the drawing (Node.svelte fades fills in 150 ms) are finished before reading, so the export shows the state, not a frame of the fade. The background is a `<rect>` of the root's full pixel size filled with `--page` resolved through a probe element to `rgb(...)`. The export therefore carries the theme in force (system setting or the `data-theme` switch). Reason: the instruction (5.2 steps 2 and 4, 5.7 Theme), SPEC 8.3.

## 2026-10-10 P2-A6: fractions redrawn as SVG text; pairing rule
Decision: a numeral group whose button's `data-value` is `p/q` becomes, in the export, the same `<g>` marked `data-frac="p/q"` holding one `<text>` with two `<tspan>` children (numerator above, with U+2212 when negative; denominator below, at the positions Node.svelte used) and the bar `<line>`, so there is one value text per node. Pairing rule: a drawn numeral `data-numeral="L"` is paired with the single `[data-node="L"]` button inside the drawing's parent element (Board.svelte puts the SVG and its group of buttons in one box), falling back to the tool root (`[data-tool]`) only when the parent holds no node button; when the label is not unique in that scope the node is left as drawn. Reason: the instruction (5.2 step 5).

## 2026-10-10 P2-A6: long numbers in a picture (SPEC 4.0 "Long numbers")

## 2026-10-10 P2-A6: which SVGs make the figure; composites
Decision: ToolFrame binds its existing `<figure>` element (no wrapper added) and takes every `<svg>` in it, in document order, that is not inside another `<svg>`, a `button`, `a`, `label` or `summary` and is at least 32 by 32 CSS pixels (the 16-pixel view icons of T1 and mood glyphs of T9's list stay out). One is exported as it is; several go through `composeFigure`. `composeFigure` keeps drawings that overlap on screen at their relative positions (T9 draws its moods as a second SVG over the board) and stacks separate ones (T1's linked view; T2's board and garden) in document order with a 16-pixel gap, root `width` the widest, `height` the sum plus gaps, both in pixels with a matching `viewBox`. What the plan said: stack all with a 16-pixel gap. Reason: stacking an overlay below its board would misplace T9's moods.

## 2026-10-10 P2-A6: HTML drawn over an SVG (T2's garden vertices)
Decision: the vertices of T2's orbit garden are HTML buttons over the SVG of its edges, so a plain serialisation would export edges without vertices. `inlineStyles` therefore draws every button of the drawing's parent element that lies over the drawing and shows a border, a background, a `::before` dot or text as a rounded `<rect>` (its computed border and background colours and radius) with its text (computed font and colour) and its `title` as a `<title>`, mapped into the drawing's coordinates through `getScreenCTM()`. The transparent, textless hit areas of Board.svelte draw nothing. Exact digits of a shortened garden vertex are in that `<title>` only, not in the `data-exact` note (open question). Reason: the export must be a picture of what is on screen (instruction 5.1).
