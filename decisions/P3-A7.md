## 2026-10-10 P3-A7: the profile as implemented
Decision: every Lighthouse run uses `formFactor: 'mobile'`, `screenEmulation { mobile: true, width: 360, height: 800, deviceScaleFactor: 1, disabled: false }`, `throttlingMethod: 'devtools'` with `throttling.cpuSlowdownMultiplier: 4` (Lighthouse then sends `Emulation.setCPUThrottlingRate` with rate 4 through the DevTools Protocol before the page loads), and `requestLatencyMs`, `downloadThroughputKbps`, `uploadThroughputKbps`, `rttMs`, `throughputKbps` all 0, which Lighthouse 12.6.1 sends as `Network.emulateNetworkConditions` with latency 0 and throughput 0, the same values it uses to clear network throttling. Also `onlyCategories: ['performance']`, `locale: 'en-US'`, `maxWaitForLoad: 30000`, the Chrome flag `--no-sandbox` (Playwright launches Chromium without the sandbox as well; the container runs as root), and Lighthouse's own mobile user agent. Lighthouse CI adds `--headless=new`; each run is a new Chromium process with a new profile, so every run is a first visit with an empty cache. The page is never touched: Lighthouse navigates and records, it does not scroll, so `client:visible` islands below the first view stay unhydrated. What the specification left open: 7.6 [D] names only "360 by 800 pixels, processor slowed four times". Default used: none of SPEC.md section 10. Reason: the plan reads the parenthesis as the whole profile, so the network is not throttled; Lighthouse's default mobile profile (a 412 by 823 screen, a simulated slow 4G network and a simulated processor) is replaced explicitly. Whether the owner wants the network throttled as Lighthouse's own preset does is an open question.

## 2026-10-10 P3-A7: the three numbers and the end of the measurement
Decision: LCP, TBT and CLS are the `numericValue` of Lighthouse's audits `largest-contentful-paint`, `total-blocking-time` and `cumulative-layout-shift` (confirmed in the installed version). A missing or errored value makes the run an error, never zero; zero TBT and zero CLS are legitimate. The end of the measurement is Lighthouse's: under devtools throttling it raises its network quiet window, its processor quiet window and its pauses after FCP and after load to at least 5250 ms (`overrideThrottlingWindows` in `core/config/config.js`), so the plan's quiet window of five seconds is met; `maxWaitForLoad: 30000` is the ceiling, and a run whose report carries Lighthouse's warning "The page loaded too slowly to finish within the time limit" is an error ("did not settle within 30 s"), as is any `runtimeError`. TBT is Lighthouse's: the blocking parts (beyond 50 ms) of the long tasks between FCP and Time to Interactive. CLS is Lighthouse's largest session window (1 s gap, 5 s cap) of shifts without recent input. What the specification left open: 7.6 names the metrics, not their computation; the instruction's 5.6 gives plan definitions "after web-vitals and Lighthouse" for the Playwright fallback. Default used: none of SPEC.md section 10. Reason: on Branch A the tool's own definitions are the measurement; the plan's raw-entry functions (TBT over recorded long tasks, CLS over recorded shifts, the quiet window over a simulated timeline) have no input on this branch, so their unit tests are replaced by tests of the report readers, of the timeout and runtime-error rule and of the settings (a deviation, reported). The long tasks Lighthouse lists (audit `long-tasks`) are kept in the `--json` output as evidence for an OVER on TBT.

## 2026-10-10 P3-A7: runs, median, thresholds, statuses, exit codes, output
Decision: three runs per route by default (`--runs`), each metric's median taken separately (the mean of the two middle values for an even count); a run in error makes the route an error and is never dropped. `THRESHOLDS = { lcpMs: 2500, tbtMs: 200, cls: 0.1 }` and `PROFILE = { width: 360, height: 800, cpuSlowdown: 4 }` are exported constants; a median passes when it is at most its threshold, compared unrounded. A route is `ok`, `OVER` (naming each failing metric), `missing` or `error` (with its reason). Exit 0 when every route is ok, the canary failed all three thresholds and the processor check passed; exit 1 for any other row, no route, no build (`lab: no build found at <dir>; run npm run build first`), a server that does not start, a canary that passes a threshold or a failed processor check; exit 2 for a usage error. Output: a first line with the tool and its versions, Chromium, the profile, the runs, the built directory, the base and the processor check; the table (LCP in s to three decimals, TBT in ms to one, CLS to four, under the headers `LCP (<= 2.5 s)`, `TBT (<= 200 ms)`, `CLS (<= 0.1)`); the canary line; `lab: N routes measured, M over threshold, E missing or in error`. Progress, and Lighthouse CI's own output prefixed `lhci:`, go to standard error. `--json <file>` writes the tool and versions, the profile, the settings, every run's numbers and long tasks, the medians, the statuses, the canary and the settings read from every report; files under `reports/` are never committed. Lighthouse CI itself retries a Lighthouse process that crashes, up to three attempts (`runUntilSuccess`); that is the tool's handling of a crashed process, not a retry of a measured result, and the script never repeats a run. What the specification left open: all of this is plan. Default used: none of SPEC.md section 10. Reason: the instruction's 5.7 and 5.8.

## 2026-10-10 P3-A7: route lists, base, serving, the non-200 rule
Decision: `npm run lab` measures the core path: `/` and, for k from 0 to 5, the one lesson whose slug begins with `m<k>-` (the hyphen keeps `m1-` from matching `m10-`; `/modules/` is not a lesson); no match is a `missing` row and fails the run, two matches an `error` row. `npm run lab -- <route> ...` measures exactly those routes in order, normalising a missing trailing slash to the built form; a route with no HTML file is `missing`. `npm run lab -- --all` measures every route of `routesOf` imported from `scripts/size.mjs`, the same list `npm run size` measures (Astro's `build.format` is the default `directory` in the merged configuration; the `.html` form is handled too). Options `--url`, `--dist`, `--port` (default 4324, beside 4323 of `size.mjs` and 4321 of `playwright.config.ts`), `--runs`, `--json`, `--help`; `--all` with routes, an unknown option or a bad value prints the usage and exits 2. The base is `siteAndBase(process.env).base` imported from `site/astro.config.mjs`, and route URLs come from `routeUrl` imported from `size.mjs`; with `--url` the URL already carries the base. The built directory is `--dist`, else `OUT_DIR` resolved by `outDirFrom` as Astro resolves it, else `site/dist`. `astro preview` is spawned from Astro's own binary in `site/` with `--ignore-lock` (as `size.mjs` does), in its own process group, with the environment passed through, after checking that the port is free; the script waits up to 60 s for a 200 at the base URL, refuses a server that reports another port, and kills the group in a `finally` block and on SIGINT and SIGTERM, together with the Lighthouse CI process group. Each route's status is read with a GET before Lighthouse runs: a status other than 200 (304 counts as 200) makes the route an `error`, except the route `/404` built from `404.html`, which may answer 404 by design and is then measured with Lighthouse's `ignoreStatusCode` (checked live on a copy of the build with a `404.html` added). What the specification left open: all plan, after `P0-A6` 5.1. Default used: none of SPEC.md section 10. Reason: the instruction's 5.3 and 5.4; the index is the plan's addition to "the core path M0 to M5".

## 2026-10-10 P3-A7: the canary and the processor check
Decision: `CANARY_HTML`, exported, is served by a throwaway Node `http` server on a free port of 127.0.0.1 and measured once, first in every command, through Lighthouse CI with the same settings: a short first paint, a large block of text 3.5 s after load, a 600 ms busy loop, then a 320 pixel block inserted above the text; it fetches nothing. If it passes any threshold the script prints `lab: measurement check failed: the slow fixture passed <metric>` and exits 1 before any route. Live it read LCP about 3.6 s, TBT about 554 ms and CLS 0.373 in every command. The processor check on Branch A reads every report, the canary's included: `configSettings.throttlingMethod` must be `devtools`, `configSettings.throttling.cpuSlowdownMultiplier` 4 and the screen 360 by 800, otherwise `lab: the processor slowdown did not take effect (<setting found>)` and exit 1; the first line prints the method and multiplier in place of a ratio. What the specification left open: plan. Default used: none of SPEC.md section 10. Reason: zero TBT and CLS are legitimate, so a broken measurement would read as a perfect page, and a simulated run never slows the processor.
