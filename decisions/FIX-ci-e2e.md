# FIX-ci-e2e decisions (the red Browser tests step of ci.yml on GitHub's runner)

## 2026-11-01 FIX-ci-e2e: the table of solids of M7 reflows at 320 pixels under any font (M7.spec.ts:1248)
Decision: in `site/src/content/modules/m7-geometry.mdx` the cell of each polytope name in `table[data-table="solids"]` carries `overflow-wrap: anywhere`, and the figure's side margin is `clamp(0px, (100vw - 320px) / 5, 16px)` instead of a fixed 16 pixels (0 at 320 pixels, 8 at 360, 16 from 400 up). Nothing else in the table changes: the rings, the face counts and the headers still break at spaces only, every cell keeps its text (the names are still the golden ones, with no soft hyphen or break element inside them), and M7.spec.ts is unchanged.
Root cause: the table could not be narrower than its min-content width, which the longest polytope name sets, because a name is one word: "rhombicuboctahedron" is 170 pixels in Inter (this container's system-ui face) and 176.5 pixels in DejaVu Sans (the system-ui and sans-serif face of GitHub's ubuntu-24.04 runner, where no Inter is installed). With the rings column held at "Rings" and the counts column at "counts", the table measured 280 pixels in Inter and 301 in DejaVu Sans, in a figure 256 pixels wide (the 288-pixel figure column less the two 16-pixel margins). In Inter it ran 24 pixels past its own figure but stopped at x = 312, inside the screen, so the test passed here; in DejaVu Sans it ran to x = 333 and the test read `TABLE[solids]`. Reproduced here with a fontconfig file that drops Inter (`fc-match system-ui` then gives DejaVu Sans): M7.spec.ts:1248 fails exactly as on the runner before the change and passes after it (M7.spec.ts in full, 34 of 34, under DejaVu Sans with CI set and the base /mutation_game/; 47 of 47 for M7.spec.ts and lesson-reflow.spec.ts under Inter). At 20-pixel text the table overflowed in every installed sans-serif face before the change. After it the table spans x = 16 to 304 at 320 pixels in Inter, DejaVu Sans, Liberation Sans and FreeSans, at 16 and at 20 pixels; at 16 pixels "rhombicuboctahedron" is the only name that breaks inside the word (in Inter and DejaVu Sans; none breaks in Liberation Sans or FreeSans), at 360 pixels only DejaVu Sans breaks it, and from 400 pixels up no name breaks in any of the four faces.
What the specification left open: SPEC 7.5 A-11 ("Prose and controls reflow at 320 CSS pixels") names no device. The shell table of the same lesson scrolls in its own region, which A-11 allows for two-dimensional content, but M7.spec.ts asks the table of solids to reflow within the column, so a scroll region was not an option. `overflow-wrap: anywhere` is the device the site already uses for long unbreakable text (ToolFrame, the Atlas, Sources, the credits page). Reason: M7.spec.ts:1248 failed on every ci.yml run that reached the browser tests since 17 October (runs 6, 8, 15 and 16).

## 2026-11-01 FIX-ci-e2e: tool islands that do not hydrate on the runner (T02, T03, T06, T07, T08, T11, T16, history-popstate-sweep): not reproduced here; CI keeps a slim trace of each failed test
Decision: no product change and no change of the worker count. Under CI, `playwright.config.ts` keeps for a failed test a trace of its actions and of the browser console only (`trace: { mode: 'retain-on-failure', snapshots: false, screenshots: false, sources: false }`), so the html report that ci.yml uploads on failure names the cause of the next one. It decides nothing: no retry, no timeout, and a passing test keeps no trace. The eight affected files took 3.2 minutes with it and without it, T03, T12 and T15 4.3 minutes either way.
What the runner logs show: the island's root was in the page and the page answered every poll at the normal cadence (14 polls in 5 s; 55 in 25 s), so neither the runner nor the page's main thread was stalled; in history-popstate-sweep.spec.ts the second page did not hydrate in 25 s while the other worker passed 31 tests. The failures come in clusters across both workers (run 41276642558: five within 100 s; run 41280885872: two within 17 s), and hydration is otherwise fast there (T10 hydrated at 68 to 107 ms in the same runs).
Mechanism found: one failed request for a shared chunk of an island leaves it unhydrated for good. Astro 7.3.8's island retries the component and renderer URLs once (with `?astro-retry=`), but Chromium keeps the failed fetch in the document's module map, so the retried component imports the same failed chunk again. Reproduced on /tools/form/ by dropping one request once (connection reset): with T03FormFinder's own chunk or the Svelte renderer dropped the island hydrates after the retry; with the shared Predict chunk dropped the console reads "[astro-island] Error hydrating ... Failed to fetch dynamically imported module" and data-hydrated never appears. The slim trace of that case keeps both console lines.
Not reproduced, each run with CI set, the base /mutation_game/, DejaVu Sans as the system face and 2 workers: the whole browser suite (1753 tests: no hydration failure; M7.spec.ts:1248 failed, and three timing checks of T12 and T15 failed while other browser jobs of mine ran beside them and pass alone), the eight affected files (166, then 200 tests), 64 to 192 loads of the sixteen tool routes per experiment with up to four extra browsers, during the suite and during the release build that pages.spec.ts runs (longest time to data-hydrated 1.46 s; the idle callback ran 30 to 80 ms after it was asked for), and a second page of the same context opened 4.6 to 5.4 s after the first fell idle, around the preview server's 5 s keep-alive limit (41 tries). Not testable here: this container has no IPv6 (listening on ::1 fails with EAFNOSUPPORT; localhost resolves to 127.0.0.1 only) and runs under gVisor, while the runner has IPv6 loopback, where localhost normally resolves to ::1 first (astro preview then listens on [::1]:4321), behind the Linux TCP stack; the runner also runs Node 22.23.4 (22.22.0 here).
Most likely cause: a transient failure of one module request on the runner, made permanent by the mechanism above; what makes the request fail there is not known. A starved idle callback is less likely, since a tool page is static before hydration and the callback ran within 80 ms under every load tried. What would settle it: the console of a failed test in the uploaded report. "Failed to load resource: net::ERR_..." before "[astro-island] Error hydrating" confirms a failed chunk, and the error code points at the cause (ERR_NETWORK_CHANGED: a network change seen by Chromium; ERR_CONNECTION_RESET or ERR_EMPTY_RESPONSE: the server end of a connection); neither line means the island never started, which a timeout on client:idle would address.
What the specification left open: SPEC 7.7 and 7.8 say which suites ci.yml runs, not how a failure is recorded. Reason: the step is red on main and no failure has a recorded cause.

## 2026-11-01 FIX-ci-e2e: the browser console of each failed browser test is printed into the CI log
Decision: ci.yml gains the step "Browser console of failed tests" (`if: failure()`), right after "Browser tests". It runs `node scripts/trace-console.mjs test-results`, which reads every `trace.zip` that playwright.config.ts keeps under CI for a failed test and prints its navigations, console messages (with their URLs) and page errors. The script uses Node built-ins only (the zip is read through its central directory and inflated with zlib), and it exits 0 whatever it finds, so it can never be the step that turns a run red. No test, timeout, retry or worker count changes.
Why: the first CI run with the slim traces (run 41308396064 on PR #9, head 22beff3) confirmed the M7 fix (M7.spec.ts passed) and failed on six tests, each a tool island that never set data-hydrated (board-load.spec.ts:57 sandbox, embed.spec.ts:187 kostant, T01.spec.ts:783, T03.spec.ts:102, T06.spec.ts:143, T08.spec.ts:270); 1747 passed. The traces were uploaded in the playwright-report artifact, but the orchestrator's container cannot download artifacts (the blob host is outside its network policy), so the cause has to reach the job log. Checked on the trace of the dropped-chunk probe: the script prints the "Failed to load resource: net::ERR_CONNECTION_RESET" line and the "[astro-island] Error hydrating ..." line with their times; on a folder with no trace it prints "0 trace(s)" and exits 0.
Reason: the Browser tests step is red on PR #9 and main with no recorded cause (SPEC 7.8).

## 2026-11-04 FIX-ci-e2e: the tool islands' client:idle carries a 1000 ms timeout, so a tool hydrates even on a page that is never idle
Decision: the sixteen tool islands of `src/tools/ToolIsland.astro` (the routes /tools/<id> and /embed/<id>) and the idle island of `T15Route.astro` use `client:idle={IDLE_HYDRATION}`, `{ timeout: 1000 }` from `src/tools/hydration.ts`, instead of a bare `client:idle`. The browser still hydrates at its first idle period; when none comes, it hydrates 1000 ms after the island is reached. A new browser test, `hydrate-busy.spec.ts`, opens every tool route and embed/board/ on a page whose main thread is never idle (a message loop) and requires data-hydrated within the default 5 s.
Root cause: Astro 7.3.8's client:idle calls `requestIdleCallback(cb, { timeout: undefined })`, so an island waits for as long as its page has no idle period, and nothing is logged. The first CI run with the console step (run 41797490360 on main, 106ccc7) failed one test, T02.spec.ts:404 (/tools/garden/ never hydrated; 1752 passed), and the step printed the navigation at 40 ms and no console line, page error or failed request: the island never started (a failed chunk prints "Failed to load resource" and "[astro-island] Error hydrating", which the probe of 1 November showed). Reproduced here: with a page kept busy by a message loop, /tools/garden/, /tools/board/ and /tools/mirror/ never hydrated in 5 s (the same signature) and hydrated at once on a quiet page; the new spec failed 17 of 17 on the build of 106ccc7 and passed 17 of 17 with the timeout. What keeps the runner's page from an idle period is not known; the timeout removes the dependence on one.
What the specification left open: SPEC 7.6 says a tool is hydrated "when the browser is idle" and names no limit. 1000 ms keeps that order on a quiet page and leaves the 5 s wait of the tests four seconds of margin. The first island of each lesson and the home page's BoardSeed also use a bare client:idle; none has failed on CI, so they are left as they are (the same change would apply).
Reason: the Browser tests step of ci.yml is red on main (SPEC 7.8).
