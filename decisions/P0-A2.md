## 2026-10-10 P0-A2: SafeInt checks every result and normalises -0
Decision: `SafeInt.add`, `sub`, `mul` and `fromInt` check their result with `Number.isSafeInteger` and throw `EngineOverflow` otherwise; `fromInt` of a non-integer (0.5, NaN, Infinity) throws `EngineOverflow` too; `mul`, `neg` and `fromInt` return `0` for `-0`, so `show` gives "0", `sign` gives 0 and `eq` behaves as for integers. What the specification left open: E-1 admits no non-integer and the engine has no other error class for one; `-0` is a JavaScript artefact. Reason: `(-1) * 0` is `-0` and `Math.sign(-0)` is `-0`; the oracle's integers have no such value.

## 2026-10-10 P0-A2: the rank ranges of `cartan`
Decision: `cartan(name)` accepts exactly a letter A to G followed by a decimal rank without leading zeros, with the ranges of SPEC.md 2.8: A for n >= 1, B and C for n >= 2, D for n >= 4, E for n in {6, 7, 8}, F for n = 4, G for n = 2; ranks above 8 are allowed; everything else throws `NotABoard`. What the specification left open: 5.3 says "any rank the families allow". Reason: the oracle's `cartan(letter, n)` does not validate ranks and returns nonsense for B1, D3, E9, G3, A0 and raises IndexError for E5, F3 (instruction, trap 7); the engine must not copy that. A leading zero (`A03`) is rejected so that a board's `name` is always the canonical spelling.

## 2026-10-10 P0-A2: the phase-0 naming rule of `fromAdjacency`
Decision: `fromAdjacency(A)` validates `A` (square, non-negative integers, zero diagonal, at least one node, `boardKind(2I - A^T)` not `not-a-board`; otherwise `NotABoard`), then compares `C` entry by entry with `cartan(X)` for every finite name `X` of size `n` in the family order A, B, C, D, E, F, G; on the first match it returns `boardFromName(X)` (SafeInt, `name: X`), except that the C2 matrix `[[2, -2], [-1, 2]]` gets the same SafeInt board with `name` undefined; otherwise a `Board<bigint>` with `Big`, `kind: boardKind(C)`, labels 1..n and no name. What the specification left open: CONTRACTS.md 2.4 says "SafeInt if identify names a finite type (phase 2), else Big; phase 0: Big unless the matrix equals a named finite type's". Reason: a name derived from a matrix is a computed name, and computed names say B2 (COMMON.md 2, SPEC.md 5.5 "Naming"); naming this matrix B2 without reordering the nodes would put a name on a board whose position order is not the Bourbaki order of `cartan("B2")`, and reordering is `identify`'s job in phase 2. Open question raised to the orchestrator in the report: which name, if any, `fromAdjacency` should give the C2 matrix in phase 0. The phase 2 agent replaces the exact comparison with `identify`.

## 2026-10-10 P0-A2: `boardKind` on non-square input and on the empty matrix
Decision: `boardKind` returns `'not-a-board'` for a value that is not an array, a matrix that is not square, a ragged matrix, or a row holding a non-number (plan additions; the oracle would raise); the empty matrix returns `'gcm'` as in the oracle; `fromAdjacency([])` throws `NotABoard`. What the specification left open: the oracle's `board_kind` assumes a square numeric matrix. Reason: tools receive matrices from parsed links; 2.1 defines a board on nodes 1..n, so no board has no nodes, but `boardKind` follows the oracle on the empty matrix because the roster names the oracle as its specification.
