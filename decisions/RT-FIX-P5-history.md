# RT-FIX-P5-history: decisions of the phase 5 red-team fixer, cluster history (the shared history layer and the popstate path)

## 2026-10-25 RT-FIX-P5-history: on popstate the recorded state is the one the tool shows, and what it loads is not written (P5-RT-04-01)
Decision: site/src/lib/history.ts no longer replaces an instance's recorded state with the codec's reading of the bar on popstate. Each instance's handler still receives `decodeState(location.search, tool, defaults, { prefix })` and its notice, as the P1-A2 record says; the tool re-reads the bar by the codec or by its own rules (T10's `admit`, T11's and T12's `admitLink`) and loads what it admits. The recorded state stays the last state the tool reported through ToolFrame's `stateChanged`, so a tool that finds its state unchanged (T12 and T11 return early in `readLink`, T10 only restarts its load) keeps a recorded state that is on screen, and Copy link and the export footer (both `linkFor`) encode it. A state the tool loads reaches `stateChanged` like any other; history.ts records, for every instance, the count of the reader's actions at the popstate, and a change that arrives before the reader acts again is that instance's load: recorded, not written, on a page opened from a link or not. The next press, key or input inside a tool frame, or an example loaded, makes the next change the reader's, as in the rule of RT-FIX-P4-shared. What the specification left open: SPEC 7.4 says when the bar is written ("after a move") and that Copy link encodes the current state; the plan (P1-A2 5.6) adds "Nothing is written on load or hydration"; neither says how history.ts learns the state a tool shows after the back button. Why: the codec does not know the rules by which T10 to T12 admit a link (P5-A2 records T12's), so its reading was not the state shown: after one press of the skip link Copy link reopened T12 to another start and relation, a bare link, or LINK_NOTICE on T11. The same cause made the back button write: T12 loaded its link's state, which differed from the codec's reading recorded a moment before, so after a move it counted as the reader's change and the bar of the entry the reader returned to was rewritten half a second later (`/tools/rep/?k=2` became `?z=1&g=A2&c=n&s=0,1&w=&k=2&q=ef:2,2`); T10 and T11 share that path. On the plain-codec tools nothing changes: the state they load is the codec's reading, recorded before as it is now, and not written either way. No interface changes: the exports of history.ts, the props of ToolFrame and the handlers of T10, T11 and T12 are unchanged; no tool or ToolFrame needed an edit. The phase 4 rules hold: nothing is written on load or hydration, one replaceState per settled burst, the per-page count of the reader's actions (site/tests/unit/history.test.ts, history-after-action.spec.ts and history-no-write-on-load.spec.ts unchanged and passing).
Known limit, as in RT-FIX-P4-shared: a press inside a tool frame between a popstate and the end of an asynchronous load (T10's facts computed in tasks, T11's or T12's replay in the worker, T8's and T15's async loadLink) makes the rest of that load count as the reader's, so the bar is written with the state then shown, normalised.
Tests: site/tests/unit/history-popstate-copy-link.test.ts (the lens's four cases, T12 back to its link after a move, a plain-codec tool after back), site/tests/e2e/history-popstate.spec.ts (the lens's five T12 cases, the SVG export footer on T12, T11 and T10, and the back button after a move on T12) and site/tests/e2e/history-popstate-sweep.spec.ts (the lens's sixteen tool routes).
