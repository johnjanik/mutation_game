# RT-FIX-P3-test-integrity: decisions

## 2026-10-17 RT-FIX-P3-test-integrity: a scroll is not the first interaction for the worker check
Decision: `worker-on-demand.spec.ts` scrolls every island still waiting into view, in document order, and waits until Astro has hydrated it (`site/tests/e2e/hydrate.ts`), before it reads the worker requests; a scripted scroll is not counted as the reader's first interaction. What the specification left open: 7.6 [D] says the islands other than the first hydrate "when scrolled into view (client:visible)" and that the worker's script "is fetched when a tool first needs it. No tool may need it for its default state" (E-9 repeats the last sentence); it does not say whether a scroll is an interaction. Default used: none of section 10; the reading of P3-RT-06-02, which both verifiers accepted: the rule covers every tool of the page, not only those of the first screen. Reason: a client:visible island hydrates into its default state when it is scrolled into view and acts on nothing. The budget of `npm run size` ("without touching the page") is not changed by this: it still measures only what is fetched before any scroll. This replaces the comment of P1-A2's spec ("the others wait for a scroll, which would be touching the page"), which no decisions entry recorded.

## 2026-10-17 RT-FIX-P3-test-integrity: the worker check waits for the tools of an island
Decision: after the scroll, `worker-on-demand.spec.ts` waits for `data-hydrated="true"` on every tool root inside an `astro-island`, and fails when an island keeps the attribute `ssr`. What the specification left open: nothing; the test's own wording ("left alone until every tool has hydrated"). Reason: the stand-in root of `dev/lesson-check` (MERGE, phase 1 stage 1.1) is static markup, not an island, so nothing hydrates it; the previous spec asked `data-hydrated` only of the tools in the first screen, which the stand-in is not in.

## 2026-10-17 RT-FIX-P3-test-integrity: the default figure of the run without JavaScript
Decision: `nojs.spec.ts` accepts as the default figure of a tool root only the tool's own drawing, outside the table view's `<details>` and any `<noscript>`: a board (a `data-board-group` holding `data-node` buttons, drawn by an `<svg>` with content beside it), a drawing of role `img` with content and a name (`aria-label`, `aria-labelledby` or `<title>`), or a snapshot `<img>` with a source and an `alt`. Any other `<svg>` (a decorative icon) no longer counts. Every node button of a game board carries the four hooks of 4.0 with a non-empty `data-value`; the nodes of the board editor (inside `data-editor`), which show no value (their `data-value` is empty by design), are left out of that check. A prediction's `<details>` must hold a non-empty `.answer-text` (the answer, as the lesson specs read it) and a non-empty reveal. What the specification left open: 7.4 asks the run to check that "every default figure" is present, and 4.0 Predict that the `<details>` holds "the answer and the reveal"; neither names a selector. This strengthens the predicate recorded in "2026-10-10 P1-A2: the run without JavaScript" (a builder's record, not a [D] choice or a default of section 10, as the refuting verifier of P3-RT-06-03 found). Reason: P3-RT-06-03. The entries of DECISIONS.md that made T2's one-vertex garden and T3's linked meter pass the old predicate stay satisfied: both tools have a named drawing of role `img` (the layer chart, the meter dial).

## 2026-10-17 RT-FIX-P3-test-integrity: the default state's values, server markup against the hydrated default
Decision: a sweep test in `nojs.spec.ts`, "the server markup shows the default state's values", compares, for every route and every tool root, the hooks read without JavaScript with those of the hydrated default (every island scrolled into view through `hydrate.ts`, nothing clicked, polled until equal): `data-moves`, the four node hooks of every `data-node`, the caption, and on the tools of ToolFrame (`data-frame`) the text of every `data-out`, all outside `<noscript>`. A root outside ToolFrame is compared without its `data-out`. What the specification left open: how the run checks that "the default state of every tool is rendered to HTML and SVG at build time" (4.0). Reason: P3-RT-06-03 ("it checks that elements exist, not the default state") and its proposed fix. The drawing-time probe of `dev/draw-time` (P4-A2's entry; not a tool of section 4, no `data-frame`) fills its timing outputs only when it hydrates, by design, so outputs are compared on the tools of ToolFrame only.
