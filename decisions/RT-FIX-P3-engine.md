# RT-FIX-P3-engine: decisions of the round 1 fixer for the engine cluster

## 2026-10-17 RT-FIX-P3-engine: the order of the guards of affineExtension (P3-RT-03-06)
Decision: `affineExtension` checks the kind of board (`NeedsTwoWayRoads`), then the class (`NotFiniteType` on every board that is not of finite type, in one piece or several), then connectedness (`NeedsConnectedBoard`, reached only by a finite board in several pieces). What the specification left open: SPEC 5.6 gives `affineExtension` `NotFiniteType` on every `gcm` board that is not of finite type and does not list it among the functions that need a connected board (E-10 names only `cartanClass`, `identify`, `identifyAffine`); it says nothing about a finite board in several pieces. Default used (SPEC section 10): none. The P2-A1 entries "`requireFinite` on a disconnected board" (connectedness for `affineExtension`, stated gap: a disconnected finite board) and "the order of checks inside each function" (connectedness "where required" before class) are kept for the case they were written for; for a board that is not of finite type the order now follows the 5.6 row, as the opening paragraph of COMMON.md requires when the plan and SPEC.md seem to disagree. Reason: SPEC 5.6 row `affineExtension` and E-10; the guard order of `guards.ts` (`requireFinite` itself checks kind, then class). The assertion of `guards.test.ts` row 8 that pinned `NeedsConnectedBoard` on the board "two components: A2 and the triangle" now asserts `NotFiniteType`; the finite board in several pieces keeps its `NeedsConnectedBoard` assertion in row 10.

## 2026-10-17 RT-FIX-P3-engine: request, the return type of symbolicPlay (P3-RT-01-01, needs-decision)
Decision: no source change; the request below is for the owner or `MERGE`. What the specification left open: CONTRACTS.md 2.4 phase 3 fixes `symbolicPlay(board, word): number[][]`, while SPEC 5.6 (second table, first row) says `symbolicPlay` works on one-way boards and on `gcm` boards that are not of finite type, and E-2 gives those boards `Big` because their entries grow without bound. On `[[2,-3],[-3,2]]` in `Big` the oracle's `symbolic_play` returns `(23416728348467685, 8944394323791464)` at move 40, which a `number` cannot hold; the engine throws `EngineOverflow` (the plan reading recorded as "P3-A2: the overflow rule of symbolicPlay"). Default used (SPEC section 10): none. Options: (a) CONTRACTS.md 2.4 becomes `symbolicPlay(board: Board<number>, word): number[][]; symbolicPlay(board: Board<bigint>, word): bigint[][]; symbolicPlay(board: AnyBoard, word): number[][] | bigint[][]` (the forms in the board's arithmetic, as the preamble of 2.4 says of vectors); a prototype made the reproducer pass with the engine type-check clean, and needs two follow-on edits: `packages/engine/test/golden/p3b-kinds.test.ts` (two tests on `Big` boards expect numbers, for example `[[1, 0], [1, 1]]`, and would expect `[[1n, 0n], [1n, 1n]]`) and `site/src/components/tools/T07SymbolicGame.svelte` lines 155 and 156 (`symbolicView` passes the result to `matchRows` and stores it as `number[][]`; T7 offers only the 32 named types, so a narrowing to `Board<number>` suffices); (b) keep `number[][]` and the owner amends the first row of the second table of SPEC 5.6 to say that `symbolicPlay` throws `EngineOverflow` when a coefficient passes 2^53, after which the reproducer is rewritten to expect the throw. Reason for recommending (a): E-2 gives these boards `Big` so that exact values survive, the oracle returns them at every length, and the only reader path (T7 on named finite boards) keeps its numbers.
