## 2026-10-26 RT-FIX-P6-t12-t5: T12 reads a link in the task after hydration, frozen meanwhile (gate G6, T12.spec.ts:1242; P6-RT-07-04 evidence)
Decision: when the address holds a key of the instance's form (a one-letter name after the instance's prefix, the shape of every key of the codec), T12's hydration `$effect` no longer calls `readLink` and `load` itself: it marks the tool frozen (`linkPending`, read by `frozen`, so every control of T12 stays disabled and no pick, move, typed start or relation can arrive) and counts one run of drawing (`data-drawn="false"`), and reads the link in a `setTimeout` task of its own, which ends the freeze, then calls `readLink` and, when the link loads nothing new, `activate`, exactly as hydration did before. A state loaded in between by the back button (popstate, which calls `readLink` and so starts a new generation) is the one shown: the deferred read is dropped when the generation has changed. An address without such a key takes the old path unchanged. The test is over-inclusive on purpose: a key the codec does not know only moves `activate` one task later. What the specification left open: CONTRACTS 5.2 says a tool reads the URL "on hydration"; SPEC 7.6 bounds engine calls on the main thread; neither fixes the task. Default used: "on hydration" read as "in the hydration step, in the task after the island's hydration", as `site/src/lib/history.ts` already allows ("A link is applied by its tool after ToolFrame has registered the instance (a task after hydration for some tools)"): on a page opened from a link the state that arrives before the reader acts is recorded and not written. Reason: MERGE's ruling ("MERGE: the T12 repair after the first run of the G5 rerun") keeps T12's long-task tests as written and asks the product to change; the link's hydration task held the hydration of the server's markup and the re-render to the link's state with the engine facts of its node (14 to 20 ms of 35 to 65). The tool's controls stay disabled one task longer on a page opened from a link; Copy link and Download data (ToolFrame's) are not frozen and, in that one task, give the server's state. Measured on this container (true task lengths from a trace, 9 runs alternated between the base build and this one, load 21 to 25): the hydration task of a link to C8 node 7 has a median of 45.3 ms on the base and 23.0 ms here, of E7 node 7 44.5 and 21.9, of the page without a link 25.4 and 24.2. T12.spec.ts:1242 with --repeat-each 20: on the base 80 of 80 passed at load 6 to 1 and 73 of 80 at load 1 to 28 (long hydration tasks 52 of 240 for the cases, 59 of 240 for the control); here 80 of 80 at load 17 to 31 (9 of 240 and 17 of 240). The tasks still seen are the hydration of the server's markup under a load of five to eight times the four processors. /tools/rep/ measures 85.8 kB (85.7 on the base).

## 2026-10-26 RT-FIX-P6-t12-t5: the tooltip of a shortened list in T5 (P6-RT-03-01)
Decision: in T5's figure every value of more than 12 digits is written through `shortValue` (the tape, the start line, the tape tab's table, the sorted tapes, the ends of games A and B); a single shortened value carries its exact digits as its `title`, and a list (the tape, the start line, an end position) that holds one carries the exact list, comma-separated with the sign as `-`, as the board's tooltip writes a value. The table view keeps every value in full (`display`, `listText`, `tuple` are unchanged there), and the exports are unchanged. The dimension calculator's lambda, its start and its two tapes are not changed: lambda has at most six digits (decisions/P3-A3.md), so they never reach 13. What the specification left open: SPEC 4.0 "Long numbers" names "the tooltip" without saying whether a list has one per value or one for the whole. Default used: one per value where values are cells, one for the whole where the list is one text. Reason: the smallest change that gives every shortened value its digits in a tooltip without changing the markup of the lists.
