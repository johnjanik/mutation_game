# RT-FIX-P4-shared: decisions of the phase 4 red-team fixer, cluster shared (url state, layout, tool routing, credits)

## 2026-10-24 RT-FIX-P4-shared: a link's state is not written before the reader acts (P4-RT-04-03)
Decision: site/src/lib/history.ts tells a link being applied from a reader's change, and writes only instances the reader has changed. An instance whose keys are in the address bar when it registers is "opened from a link". Until the reader acts inside its frame, its changes reaching `stateChanged` are recorded (Copy link and the back button use them) and not written; while such a link waits, the change of an instance the reader has not acted on (a follower that follows the linked tool through `linkTo`) is the link's too. The reader acts by a `pointerdown`, `keydown`, `click`, `input` or `change` event whose target lies inside a ToolFrame root (`[data-frame]`, read through its `data-instance`), heard once per page by capture listeners on the window that history.ts adds with its popstate listener; `exampleLoaded` also counts as the reader acting. A write encodes only the instances the reader has changed; every other instance keeps its keys as the bar holds them, so the bar is never normalised for an instance the reader did not touch. Copy link encodes the instance asked for and every instance the reader changed, and keeps the other instances' link keys, which give the states they show. What the specification left open: SPEC 7.4 says when the bar is written ("after a move") and 6.6 which instances ("only instances the reader has changed"); the plan (P1-A2 5.6) adds "Nothing is written on load or hydration". How history.ts learns that a change is the reader's is not specified. This refines the P1-A2 record ("appends each changed instance's keys"): "changed" now means changed by the reader, and an unchanged instance's keys are kept rather than stripped. No interface changes: the four exports of history.ts keep their signatures, and no tool needed a change (T10 and T11, which apply a link a task after hydration, are covered by the same rule). Reason: ToolFrame registers an instance before the tool applies its link (Svelte runs the child's effects first), so the link's state reached `stateChanged` as a change and was written half a second after load, normalised, on ten routes. Known limit: a touch that scrolls the page over a tool whose link is still being applied asynchronously (T10's facts computed in tasks, T11's long replay in the worker) counts as acting on it, and the link is then written normalised.

## 2026-10-24 RT-FIX-P4-shared: the KaTeX fonts a page uses are preloaded (P4-RT-07-03)
Decision: every generated page with KaTeX markup carries, just before the KaTeX stylesheet link, one `<link rel="preload" href="<BASE_URL>katex/<version>/fonts/<file>.woff2" as="font" type="font/woff2" crossorigin>` per KaTeX font its markup uses; a page without KaTeX markup is unchanged. site/src/lib/katex.ts reads which font a class selects from the installed katex.min.css (its @font-face rules and the rules that set a family, a weight or a style for a KaTeX class; a class that sets only a weight or a style is taken in KaTeX_Main), and site/src/middleware.ts (Astro middleware, which in a static build runs once per page while the build generates it, with `import.meta.env.BASE_URL`) adds the links to the generated HTML. The stylesheet and the fonts stay those of the installed KaTeX (7.2 item 2), with their `font-display: block`. What the specification left open: 7.6 [D] sets the lab thresholds, not how fonts load. Why this changes P3-X1's record ("no repeated layout from late fonts was large in the traces, so no preload was added"): P3-X1 measured M0 to M3, before M6 and M7 existed. On M7 (37079 pixels of lesson) the late fonts relaid and repainted the whole document after the first paint (Layout 62 to 158 ms, PrePaint and Paint 89 to 134 ms in the lens's traces), and the lens and its verifier measured Total Blocking Time 319 to 427 ms as built against 196 to 207 ms with the fonts preloaded (four times slowdown), against the 200 ms of 7.6. A page fetches the fonts its markup uses anyway (the first layout meets all its text), so the preloads move the same requests earlier and add none. The middleware was chosen because a layout writes its head before the page's content is rendered, and rendering the content first in Base.astro (Astro.slots.render) would move the head content Astro emits on first render into the body. Preloads in this build: M7 Main-Regular, Math-Italic, SansSerif-Regular (the lens's three); M0 also Size1 and Size2; M6 also Fraktur; tool routes other than /tools/geometry/, /about/ and /credits/ none.
Measurements (npm run lab -- --port 7652 --dist <dir> /modules/m7-geometry/ /tools/board/, three Lighthouse runs per route, median; /tools/board/ is a page without KaTeX markup, since every lesson has some): one run on the base build at load 17 to 20: M7 TBT 656.3 ms, board 342.6 ms. Then four alternated runs at load 2.7 to 4.3 (the last ended at 12.7): base M7 318.9 and 341.1 ms, fixed M7 146.9 and 162.8 ms; board 209.9 and 188.7 ms on the base, 165.7 and 312.8 ms on the fixed build (the board page is unchanged by this fix; its spread is the machine's). LCP of M7 1.87 to 2.15 s and CLS 0.0000 in all runs. The lens's font-swap script on the fixed build (reload at a restored position, four times slowdown): M6 at y 8178 and 14891 and M7 at y 0 and 19000, CLS 0.0000 in all eight runs, fonts finished at 73 to 156 ms against 947 to 1729 ms as built.

## 2026-10-24 RT-FIX-P4-shared: the credits page lists every package whose code ships, read from the build (P4-RT-08-04)
Decision: site/src/lib/pages/shippedPackages.ts holds an Astro integration (registered in site/astro.config.mjs) that adds a Vite plugin to the client environment and to the worker bundles. At the end of each bundle the plugin records every npm package one of whose modules has code in an emitted chunk (a module under node_modules belongs to the package of its last node_modules segment; the bundler's own modules, `vite/preload-helper.js` and `rolldown/runtime.js`, to vite and rolldown), with the chunks, the importing packages and the rendered length. Astro generates the pages after the client build and in the same process, so the credits page reads the list of that very build (kept on `globalThis` under a registered symbol); a build that publishes /credits/ also writes the list, when it is done, to site/src/generated/shipped-packages-<12 hex digits of the output directory>.json (generated, not committed), which the browser suite compares with the page. The fixture builds of the unit suite (site config, temporary output directory, no credits page) write nothing, so they cannot replace the site build's list. The credits page uses the list: lib/pages/dependencies.ts adds a row for each such package that no package.json names (version, licence and author from its installed package.json, "Used": its code is bundled into the scripts of the pages, imported by ...), and marks a named package that the list contains and SHIPPED does not describe. A production build fails if the list is missing when the credits page is generated. The page's sentence now says "and every other package whose code the build bundles into the scripts of the pages". What the specification left open: 7.9 [D] lists "the licences of bundled libraries" without saying how they are found; P0-A5's record took the three package.json files only. The lockfile's tree of the shipped packages was not used: astro's tree is the build toolchain and would mark hundreds of packages as shipped. Packages found in this build, with the length of their code in the chunks before compression: @astrojs/svelte 1879 bytes, nanostores 2894, svelte 168326 (all three named in site/package.json), and three that no package.json names, now with credits rows: clsx 2.1.1 (MIT, Luke Edwards; imported by svelte) 536 bytes, rolldown 1.2.13 (MIT; its runtime helpers, in the engine worker and one shared chunk) 710 bytes, vite 8.3.4 (MIT; its preload helper) 3221 bytes. The page now says 8 packages reach the reader (5 before). None of the three was added by an agent, so SPEC 9.3's DECISIONS.md record of an added dependency does not apply; MERGE may fold these lines as their record. The tests that read the build (credits-bundled.spec.ts) are browser-suite files, as RT-FIX-P3-perf-b did for registry-outs.spec.ts, because CI runs the unit suite before the build.

## 2026-10-24 RT-FIX-P4-shared: once the reader acts, every instance's change is written, leaders and followers included (P4-RT-04-03)
Decision: site/src/lib/history.ts replaces the per-frame rule of the first entry of this fragment. The page counts the reader's actions: each `pointerdown`, `keydown`, `click`, `input` or `change` event whose target lies inside any tool frame (`[data-frame]`, ToolFrame's root), heard by the capture listeners history.ts adds with its popstate listener, and each `exampleLoaded`. Every instance records that count when it registers. On a page opened from a link (some instance registered while the address bar held its keys), a change that reaches `stateChanged` before the reader has acted since that instance registered is the instance's load (its link applied, or a follower taking the linked state): it is recorded, so Copy link and the back button use it, and it is not written. Every other change is the reader's: the instance is marked changed and the bar is written half a second after the burst, as in the base 967118d. On a page opened without a link every change is written, as in the base. A write still encodes the instances the reader has changed and keeps every other instance's keys as the bar holds them; Copy link still encodes the instance asked for and the changed ones. The per-instance `fromLink` and `acted` flags, the page-wide test "some link still waits" and the walk from a frame to its `data-instance` are removed.
Why: the per-frame rule held a change back while the instance's own frame had not been acted on and any link waited. Through `linkTo` one press changes two instances, so a leader moved from its follower's frame (M5 `?b1.w=1`, a jump in b2's table; M1 `?b1.w=2.1`, a jump to the start in the garden), a follower moved by its leader while another instance's link waited (M1 `?b1.w=2&b3.w=1`, M6 `?b1.w=2&b11.w=1`), and a follower that came with its own link keys were never written, and Copy link gave a link that reopened at another state. That is against SPEC 7.4 ("Copy link always encodes the current state") and 6.6; the phase 4 confirmer found it. Whether the reader has acted is therefore asked of the page, not of a frame. It is asked from each instance's registration and not only once per page (the simplest rule, hold every write until the first action), because a tool that hydrates as the reader scrolls to it applies its link after the reader has acted elsewhere, and would write it at once: the finding again, on lesson pages. The gate "opened from a link" keeps a page without a link on the base rule: nothing is applied there on load (the confirmer found no write on load on all 21 tool and lesson routes without a link), so such a page does not depend on the event listeners at all. Events count only inside a tool frame, not anywhere on the page, because a key that scrolls the page or a touch on a lesson's text acts on no tool, and every control that changes a tool's state lies inside its ToolFrame (CONTRACTS.md 5.1). Why the bar then gives the current state of every instance: an instance the reader has changed is encoded from its recorded state; any other instance shows what loading the page gave it from keys the bar still holds, its own as they were and those of the instance it follows, which are rewritten whenever that instance changes, so the bar reopens to the same state.
Known limits: a press inside a tool frame between an instance's registration and the end of its load (T10's facts computed in tasks, T11's replay in the worker, a follower's later task) makes the rest of that load count as the reader's, so it is written normalised; it then encodes the state shown. A follower that hydrates after the reader moved its leader is not written until the reader acts again, but its leader's keys give it on reopening, and Copy link from it encodes it.
What the specification left open: as in the first entry, how history.ts tells a reader's change from a link being applied. No interface changes: the exports of history.ts keep their signatures, and no tool or ToolFrame changed. Tests: site/tests/e2e/history-after-action.spec.ts (the confirmer's examples: M5 jump in the follower, M1 jump to the start, M1 followers with their own keys and beside an untouched link, Copy link before and after an action) and four cases added to site/tests/unit/history.test.ts; history-no-write-on-load.spec.ts and the earlier cases of history.test.ts are unchanged and pass.
