## 2026-10-17 RT-FIX-P3-duplicates: where the engine timing regression of P3-RT-07-02 lives
Decision: the lens's Node timing of one T4 load on the 12-cycle (four classify computations, the T4 panels and the bounded root counter, median of seven runs, at most 50 ms) is adopted as packages/engine/test/bench/t4-load-path.bench.ts, run by `npm run bench -w packages/engine` through test/bench/vitest.config.ts. What the specification left open: RT-FIX 5.3 puts a non-golden engine test in packages/engine/test/unit/, which `npm test` runs in parallel workers, and no file says where an engine timing check of a tool's load path goes. Default used: none of SPEC section 10 applies; the precedent of the benchmark of SPEC 7.6 (orbit.bench.ts) and of P4-X2's weyl-dimension.bench.ts, which run alone because a duration measured inside the parallel suite measures the load of the suite rather than the engine. Reason: the same; the test body, input, bound and assertion are the lens's.

## 2026-10-17 RT-FIX-P3-duplicates: the fixture-build lock in its own module
Decision: the lock of the Astro fixture builds (MERGE, P4 wave 4.2) moves from build-fixture.mjs into site/tests/fixtures/content/build-lock.mjs (lockPathOf, withBuildLock), keyed by the real path of the site directory; build-fixture.mjs imports it. What the specification left open: how the unit tests serialise their fixture builds (SPEC 7.7 asks only that npm test pass for every merge). Default used: none. Reason: released.test.ts and content-components.test.ts spell the site directory differently (without and with a trailing slash), so a lock keyed by the text gave them two locks; the module lets site/tests/unit/fixture-build-lock.test.ts test the lock without running a build (build-fixture.mjs runs a build, or exits, when it is loaded).
