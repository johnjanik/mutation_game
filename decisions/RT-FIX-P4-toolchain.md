## 2026-10-24 RT-FIX-P4-toolchain: the postbuild holds the release report (P4-RT-12-04)
Decision: the open-items report gains an optional field `linkCheck` (`running`, `passed`, `failed`). In a release build (`RELEASE` set, the rule of `isReleaseBuild`), `scripts/links.mjs` first marks a report that the Astro build marked complete as incomplete with `linkCheck: 'running'`, runs the check, and then marks it complete with `linkCheck: 'passed'` when the check passed, or leaves it incomplete with `linkCheck: 'failed'`; a check that stops on the way leaves `running` and the report incomplete. A report that the Astro build left incomplete is never touched, so a link check never completes the report of a build that failed. The build-done hook also marks the report of its build incomplete again when the build process exits with a code other than 0 after the hook. The Markdown report is rewritten each time, so it says "Incomplete" whenever the JSON does. To let plain Node do this, the report's file code (`isReleaseBuild`, the reports directory, the JSON and Markdown writers) moves unchanged from `unverifiedRegistry.ts` into `site/src/lib/openItemsReport.mjs`, which the registry imports and whose `isReleaseBuild` and `reportPath` it re-exports. `scripts/report.mjs` is unchanged: it refuses every report whose `complete` is not `true`. What the specification left open: what `npm run report` does after a release build that failed in postbuild (SPEC 7.3, 7.7 are silent; the decision RT-FIX-P3-toolchain-b "a complete release report" gives the reason). Default used: none. Reason: a release build is prebuild, the Astro build and the postbuild, and a failed release build is never presented as the release report; the existing assertions that the Astro build alone completes the report (the fixture build and the hooks test of `report-partial-release.test.ts`) still hold.

## 2026-10-24 RT-FIX-P4-toolchain: the lines of the release report, per item and page (P4-RT-08-10)
Decision: the registry records, per item, the pages on which at least one use shows the fallback; the report's entries gain an optional field `fallbackPages` (present when not empty; `fallbackShown` is true exactly when it is), which carries this between module instances of one build. The lines on standard error are printed once, by the build-done hook, one per (item, page) as P0-A4 decided (`open item E7 used on /modules/m7-geometry/ (fallback shown)` or `(nothing shown)`, none for a closed item), in the order of `unverified.json` and then the unknown items, pages sorted, and say "fallback shown" when any use of the item on the page shows its fallback. `registerUsage` no longer prints: the line of a pair is printed at the end of the build, not when the pair is first registered as P0-A4's instruction (5.8) has it, because only then are all the uses of the page known; its form, one line per pair, is unchanged. What the specification left open: the form of the printed report (SPEC 7.3). Default used: none. Reason: a line decided by the first use only said "nothing shown" for E7 on M7, whose Seen box shows the E7 fallback; reports/gate-G4.md section 11 repeats that line, which GATE corrects at the next gate run (no report is edited here).
