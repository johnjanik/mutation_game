## 2026-10-10 P2-A3: the editor draws its own nodes instead of composing Board.svelte (deviation)
Decision: BoardEditor.svelte reuses the Board family's parts (Roads.svelte, Node.svelte when the host passes `values`, nodePositions, toPixels, the CSS size rule of 6.1, keyboard.ts arrowTarget for A-1) but renders its own node buttons and discs rather than Board.svelte. Reason: Board.svelte (not mine to edit) names every node with the game template of A-3 ("Node 3, value 2, can be fired"), requires a decimal value on every node (signOf throws on an empty value) and cannot mark nodes or report a selection, while the editor needs "Node 3, selected" names, value-free nodes in T4 and a marked sub-board. Listed under deviations in the report.

## 2026-10-10 P2-A3: the keyboard model of the editor
Decision: the nodes are one tab stop (roving tabindex); bare arrows, Home and End move the focus as A-1 says (on a custom layout they follow the labels and wrap); Enter or Space selects the focused node as the subject of the road and move controls (the previous subject becomes the other end of the road); Ctrl, Alt or Meta with an arrow moves the focused node by one grid point; Delete or Backspace removes it; `+` adds a node; `u` and `r` undo and redo (keyboard.ts shortcutOf, inside the `data-board-group`). After the drawing: Add node, Remove node N, four Move buttons, three selects for the roads (the other node, the count from the subject to it, the count back, each 0 to 4), and the board picker with a Load board button. What the specification left open: the keys (A-1 reserves the bare arrows for focus). Default used: the plan's suggestion of a modifier plus arrow. Reason: A-8, P10; the GATE keyboard-only test draws the triangle with `keyboard.press` alone.

## 2026-10-10 P2-A3: drag, the taken-point rule and the grid adoption
Decision: dragging a node (pointer events with capture, more than 6 pixels) moves it by the dragged distance in grid units, snapped to whole points and clamped to 0..11; a point that holds another node is refused (never swapped). An unedited preset whose layout is not whole grid points (the D fork at 0.6, polygons, the circle of a test board) adopts whole points on its first edit (editor/model.ts gridOf: rows rounded and shifted to start at 0, so D4 becomes (0,1), (1,1), (2,2), (2,0); a circle scaled to the least whole radius at which the rounded corners differ). What the specification left open: the plan's "refuse or swap" and how a named layout becomes grid points. Reason: 6.1 Custom boards.

## 2026-10-10 P2-A3: the counter's two calls and the keep-counting rule
Decision: the bounded search runs synchronously through t04/counter.ts `rootSearch` (cap 2000; no layer bound on a board classify calls finite, `layers` otherwise), whose hint `counterHint(board, 2000, finiteKnown)` `whereToRun` sends to the main thread (tested); it is not routed through `engineCall` because the build-time render needs the result synchronously and engineCall answers with a promise. "keep counting" calls `engineCall('orbitGraph', [board, seeds, 'mutation', 100000, maxDepth], counterHint(board, 100000, false))`, a new search in the worker; its result replaces the main one for that board object and is dropped if the board changed meanwhile. The button is offered only after a position-cap stop (`truncated` and not finite): after a layer stop a 100000 search with the same layer bound would return the same count. Seeds are the unit vectors in the board's arithmetic. The stop sentences are T2's own function (t02/limits.ts stopMessage), so the words match character for character. No helper was requested from P1-A2; the 100000 positions come back serialised, which costs a moment after the button press and none on the main thread before it. What the specification left open: plan points of 5.6 and 5.8. Reason: E-9 ("A call is never started in one place and continued in the other").

## 2026-10-10 P2-A3: the hunter's sentences

## 2026-10-10 P2-A3: undo, redo and reset of edits
Decision: editor/history.ts EditHistory keeps the board specs of the edits since the board was loaded; undo steps back one edit, redo forward, an edit after an undo discards the redo, reset returns to the loaded board (the preset, the link or the author's board) and empties the history; loading a preset or a link starts a new history. Wired through ToolFrame's onUndo, onRedo, onReset, and `u` and `r` on a focused node. Announcements: "Undid an edit. Verdict: ...", "Redid an edit. Verdict: ...", "Back to the board that was loaded. Verdict: ...". Reason: SPEC 9.2 "undo, reset" for a tool with no move list (plan semantics).
