## 2026-10-17 P4-A1: the folded board's labels and name (plan reading of E-7)
Decision: `fold` builds the folded board directly, not through `fromAdjacency`: `{ n: m, cartan: Cf, labels, kind, arith: SafeInt, name }`, frozen like every engine board. `cartan` stays in the order of the orbits, so `cartanNumbers(folded)` is the golden `folded_cartan`. With `id = identify(folded)`, `labels[id.order[k]] = k + 1` (position `id.order[k]` plays Bourbaki node `k + 1`) and `name = id.name`; `kind` is `boardKind(Cf)` (always `gcm` for a symmetry of a finite board). Fallback: when the folded board is in several pieces (possible because `requireFinite` admits a disconnected board whose pieces are finite, for instance three A1 nodes folded by the identity) or `identify` returns `null`, `identify` is not called or not used, the labels are `1..m` in the order of the orbits and `name` is absent. The eight rows that fold give: A3 flip `B2` labels `[1, 2]`; A5 flip `B3` `[1, 2, 3]`; A7 flip `B4` `[1, 2, 3, 4]`; D4 swap `C3` `[1, 2, 3]`; D5 swap `C4` `[1, 2, 3, 4]`; D6 swap `C5` `[1, 2, 3, 4, 5]`; E6 flip `F4` `[1, 4, 2, 3]`; D4 rotation `G2` `[2, 1]`. Listing the orbits in increasing label reproduces `folded_orbits_in_bourbaki_order` on all eight (tested). What the specification left open: E-7's row "folded board" says labels are in the Bourbaki order of the type `identify` names, without saying how the board object is built. Default used: the plan's (instruction 5.3, traps 18, 19). Reason: `fromAdjacency` would give labels `1..m` in position order.

## 2026-10-17 P4-A1: guards of averagedSimpleCartan and applyWordFloat; no guard on symEig and classifyRestricted
Decision: `averagedSimpleCartan` and `applyWordFloat` call `requireGcm` then `requireFinite` (NeedsTwoWayRoads on a one-way board, NotFiniteType off the finite types), like `fold`, `averagedRootsType`, the geometry and the Wythoff functions. `symEig` (a matrix) and `classifyRestricted` (a set of vectors and a Gram matrix) have no guard; the board-taking functions that call them carry it. In every guarded function the argument shape is checked first (RangeError: a symmetry that is not a permutation of `0..n-1`, a vector of the wrong length, an unknown game, a position outside `0..n-1`, a bad `rings` or cap), then `requireGcm`, then `requireFinite`, the order P2-A1 and P3-A1 used. `symEig` throws RangeError on a matrix that is not square and does not check symmetry (as the oracle). What the specification left open: 5.6 names "fold, averagedRootsType, the Wythoff, Satake, representation and geometry functions" but not `averagedSimpleCartan`, and two of the functions take no board. Default used: the plan's readings (instruction 5.5, 5.6, 5.10, 5.13). Reason: `averagedSimpleCartan` belongs with `fold` and `averagedRootsType` in the 5.4 table; `applyWordFloat` stands in the Geometry table; finiteness is decided through `guards.ts` only (E-11).

## 2026-10-17 P4-A1: classifyRestricted's parameter type (a supertype of the contract)
Decision: `classifyRestricted(S, B, r)` in `src/restrictedType.ts` accepts vectors whose entries are `number`, `bigint` or `Rational` (exported type `RestrictedEntry`) and converts each entry to a `Rational` on entry; `B` is `readonly (readonly Rational[])[]`. S is treated as a set: a vector given twice counts once (the oracle's argument is a Python set; keyed by the rational text in lowest terms). It returns `RestrictedType = { name: string; classes: { class: string; roots: number; form_value: string }[] }`, classes in ascending squared length, `form_value` as `ratToString` text (rule 4). The oracle's decision table is ported in its order (non-reduced first; one norm A, D, E; two norms with the ratio 3 test for G2 before the rank 2 rule, which always says `B2`, and F4 before the B and C counts); every `assert` and `raise ValueError` becomes `throw new EngineError('classifyRestricted: ...')` with the oracle's message text (`unrecognised simply-laced system`, `unrecognised system`) or a sentence starting `not a root system` for the bare asserts, followed by the oracle's tuple values. What the specification left open: CONTRACTS.md 2.4 phase 6 writes `S: number[][]`, but `averagedRootsType` passes rational averages. Default used: the plan's (instruction 5.4): a supertype of the contracted parameter, so both callers type-check. Reason: reported under `openQuestions` as a contract amendment to confirm, not as a deviation.

## 2026-10-17 P4-A1: wythoffFVector returns n + 1 entries
Decision: `wythoffFVector(board, rings)` returns `n + 1` bigint entries as the oracle does: `f[0]` vertices, `f[1]` edges, ..., `f[n]` = `1n` when some node is ringed and `0n` when none is; with no ring the result is `[1n, 0n, ..., 0n]`. ## 2026-10-17 P4-A1: wythoffEdges items, order and truncation
Decision: each item is `[u, v]` with `u` before `v` in the lexicographic order of their entries compared as integers (through `arith.sign(arith.sub(...))`, never as strings), entries converted to `number`; the visited set is keyed by the decimal text of both ends in canonical order (`u|v`); items are in discovery order: the seeds `{lambda, R_i lambda}` for `i` from 0 to n - 1 with `lambda_i != 0`, then breadth first over the pairs in the order found, firing both ends at each node in increasing position through `fire`. The cap acts when the search is about to add item number `cap + 1` (seeds included): `{ items, truncated: true }` with exactly `cap` items; otherwise every edge with `truncated: false`; a cap that is not a non-negative integer is a RangeError; cap 0 with a ringed node gives `{ items: [], truncated: true }`. On E8 with rings `(0, 1, 0, 0, 0, 0, 0, 0)` (1_42) and `CAPS.edgesAtRest` the result is truncated with exactly 70000 items. What the specification left open: the oracle's set has no order and raises at the cap. Default used: the plan's (instruction 5.12, traps 11, 12). Reason: E-6, E-10.

## 2026-10-17 P4-A1: the rounding helper and the minus-zero rule
Decision: `round6(x) = Math.round(x * 1e6) / 1e6`, then `-0` normalised to `0` (`r === 0 ? 0 : r`); radii are `round6(Math.hypot(x, y))`, grouped in a `Map` and sorted ascending; distinct points are counted on the text key `${round6(x)},${round6(y)}`. The body of `coxeterPlaneRings` is the helper `ringsOfPoints(points, h)`. Both `round6` and `ringsOfPoints` are exported from `geometry.ts` for the unit test of the rule and are not part of the public API (`index.ts` does not export them). The computed radii equal the golden radii exactly (not only within 1e-5) on all 31 types, checked once with a throwaway test. What the specification left open: the helper (5.4 says "rounded to 6 decimals and -0 counted as 0"). Default used: the plan's (instruction 5.8, traps 13, 14). Reason: `toFixed` would count `-0.000000` and `0.000000` apart.

## 2026-10-17 P4-A1: the order of a sub-board's Weyl group
Decision: `|W_K|` in `wythoffFaceTypes` is `1n` for the empty set and otherwise the product over the connected components of K (the oracle's `induced_components`, joined in either direction) of `BigInt(weylOrder(subBoard(board, component)))`, with the components' orders kept in a `Map` for the length of one call only (nothing is cached across calls, E-5). Counts are `W / (|W_K| |W_K'|)` in bigint with exact division (EngineError on a remainder, which cannot happen). What the specification left open: the oracle calls `weyl_order(sub_matrix(C, K))`, which equals this product on a disconnected K. Default used: the plan's (instruction 5.11, trap 8). Reason: no `weylOrder` on an empty or disconnected board; `TypeError: Cannot mix BigInt and other types` avoided by converting first.
